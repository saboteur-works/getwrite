### Task 1: Add `removeEntityRelationshipsForEntity` to the entity-relationships model
**What:** Adds `removeEntityRelationshipsForEntity(projectRoot, entityId)` to `frontend/src/lib/models/entity-relationships.ts`, alongside the existing `createEntityRelationship`/`removeEntityRelationship`. Removes every persisted edge in which `entityId` is `sourceEntityId` or `targetEntityId`, returning the count of edges removed. The entire read-modify-write sequence runs inside a single `withMetaLock(projectRoot, ...)` call, mirroring the two existing mutators exactly — never a read outside the lock followed by a locked write. Calling it for an entity with no matching edges is a no-op that returns `0` rather than throwing or writing an unchanged file (FR-8, FR-12 — deletion here is permanent with no trash-like holding area, so this function's only failure mode is "removed nothing," never a partial or recoverable state).
**Files:** frontend/src/lib/models/entity-relationships.ts, frontend/tests/unit/entity-relationships.test.ts
**Done when:** a unit test confirms an entity with two edges naming it as source, one as target, and one unrelated edge results in exactly the three matching edges removed and the unrelated edge untouched, with the function returning `3`; a test confirms calling it for an entity with zero matching edges returns `0` and leaves `meta/relationships.json` byte-for-byte unchanged; a test using two concurrently-started (not sequentially-awaited) calls — one `removeEntityRelationshipsForEntity` and one `createEntityRelationship` for an unrelated triple, fired together — confirms both complete correctly with no interleaved write, mirroring `entity-relationships.test.ts`'s existing concurrent-write test for the two other mutators.
**Depends on:** none
**Estimate:** 3
**Notes:** This is FR-8's entire model-layer scope. No cleanup/migration/sweep of edges is introduced beyond exactly what this function is called to do (non-goal).

### Task 7: Wire the confirm handler — ordering, sidecar write, pending state, error/retry, refresh, and focus
**What:** Extends `RemoveEntityControl.tsx`'s confirm handler to perform the feature's actual write sequence, deliberately not using `EntitySection.tsx`'s optimistic-dispatch-then-swallow `persist()` pattern (FR-15). When the writer checked the delete-edges box: awaits Task 3's `removeEntityRelationshipsForEntity(projectId, entityId)` first; only after it resolves successfully does it perform the sidecar write — `updateSidecar` with the resource's `entityKind` and `aliases` both set to the explicit-`undefined`-key pattern `withEntityKind` already documents (FR-1, FR-4, FR-11). When the box was left unchecked, or was never shown (zero edges), no call to the edge-delete route is made and the sidecar write runs alone. While either call is pending, `isConfirmDisabled` is `true` and the dialog does not accept a repeat confirmation. If either call fails, the dialog stays open, shows an inline error in `details`, and offers retry/cancel; no Redux dispatch occurs on failure. Only after both calls (or the sidecar write alone) succeed does the handler dispatch `updateResource`, call `useEntityRelationshipsRefresh()`'s `notifyRelationshipsChanged()` (but only when the delete path ran — a keep-path success has nothing new for that list to show), dispatch `fetchEntityAliasTable(projectId)`, and close the dialog. Because Task 6 gates `RemoveEntityControl` (and the `ConfirmDialog` it renders) on `isEntity`, the `updateResource` dispatch that clears `entityKind` unmounts the control immediately — so the success sequence is ordered to survive that unmount: closing the dialog and completing the refresh calls (`notifyRelationshipsChanged`, `fetchEntityAliasTable`) do not depend on the control still being mounted once `updateResource` has been dispatched, and moving focus to the Entity Kind input (`[aria-label="entity-kind-input"]`, which lives in `EntitySection.tsx` and stays mounted throughout) is done in a way that does not rely on `RemoveEntityControl` still being mounted (FR-19); the exact mechanism (e.g. reordering the dispatch to run last, or decoupling the close/focus/refresh calls from the component's own lifecycle) is left to the implementor. On cancel, no explicit focus handling is added, relying on Radix's default `onCloseAutoFocus` to return focus to the trigger.
**Files:** frontend/components/Sidebar/RemoveEntityControl.tsx, frontend/tests/component/RemoveEntityControl.test.tsx
**Done when:** a test confirms, for the delete-chosen path, `removeEntityRelationshipsForEntity` is called and resolves before the sidecar `updateSidecar` call is made (asserted via call-order, not just both-eventually-called); a test confirms the sidecar write clears both `entityKind` and `aliases` to `undefined` while every other resource field is unchanged, matching the on-disk shape of a resource never declared an entity; a test confirms the keep-path (or zero-edge) case never calls the edge-delete transport function at all; a test confirms `isConfirmDisabled` is `true` for the duration of either in-flight call and a second confirm click during that window has no additional effect; a test confirms a rejected edge-delete call or a rejected sidecar write leaves the dialog open with an inline error, dispatches no `updateResource`, and lets the writer retry (a subsequent successful retry then completes normally) or cancel; a test confirms `updateResource`, `notifyRelationshipsChanged`, and `fetchEntityAliasTable` are all called, and the dialog closes, only after the relevant call(s) resolve, never before; a test confirms `notifyRelationshipsChanged` is NOT called on a keep-path success; a test confirms that after a successful confirm — which unmounts `RemoveEntityControl` and its `ConfirmDialog` once `updateResource` dispatches — the dialog is gone, no React unmounted-state warning is logged, and `document.activeElement` is the `[aria-label="entity-kind-input"]` element; a test confirms focus lands on the `entity-kind-input` element after a successful confirm and relies on the dialog's own cancel behavior (no custom handler) for the cancel case.
**Depends on:** 1, 5, 6
**Estimate:** 5
**Notes:** This is FR-1, FR-3 (verified as a non-regression — `withEntityKind`'s own existing tests are unmodified by this task), FR-4, FR-5 (verified by confirming no new cleanup mechanism is introduced — the write reuses the identical `updateSidecar` path `withEntityKind` already triggers, so `enqueueEntityRescan`/`indexer-queue.ts`/`entity-alias-table.ts` fire exactly as they do today), FR-11, FR-12 (verified by confirming no trash/holding-area code is added), FR-15, FR-16 (invocation half), and FR-19's entire scope. ## Summary
- Total tasks: 9
- Total estimated effort: 26 points
- Critical path: 1 -> 2 -> 3 -> 6 -> 7 -> 8 -> 9, with Task 4 and Task 5 each feeding into Task 6/Task 7 independently (Task 4 -> 6; Task 5 -> 7) and no dependency on one another, so both can proceed in parallel with Tasks 1-3
- Risks: Task 7 (the confirm handler's ordering) is the single highest-risk task in this list — the resolved OQ-1 ordering exists precisely because the reverse order can leave a resource no longer a declared entity while its edges remain, so a call-order regression here would silently violate FR-11's own stated guarantee; its done-when requires an explicit call-order assertion rather than trusting a both-eventually-called test. Task 6's fail-closed behavior on a failed relationship-count fetch (FR-17) is the second-highest risk: defaulting the wrong way (rendering the checkbox on an unconfirmed count, or silently calling the delete route without one) would either surprise a writer with an unreviewed deletion or block removal entirely on a failure unrelated to the sidecar write itself. Task 4's `isConfirmDisabled` addition is scoped narrowly and reviewed against the resolved OQ-5 text specifically to avoid it becoming a second, broader `ConfirmDialog` prop surface by accretion.
