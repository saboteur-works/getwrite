### The one slot kind

`view` is the only slot kind, on both sides (`MODULE_SLOT_KINDS`, `UI_SLOT_KINDS`). There is no field for resource types, Trash kinds, importers, permissions or project-type keys. Tests pin this (section 2, FR-3 and FR-11).

### How the Sources view registers (reading)

- `ViewName` in `frontend/src/lib/models/types.ts` gained the literal `"sources"`. It is a typed literal, not derived from the manifest (the manifest is not `as const`). `work-area-view-gating.test.tsx` has a test that pins the literal to `MODULE_MANIFEST[0].view?.id`.
- `AppShell.tsx` calls `useModuleViews()` and passes the enabled slots to `ViewSwitcher` as `moduleViews`. `ViewSwitcher` appends them after the built-in tabs (icon `Library`). A module whose switch is off has no tab at all: it is absent, not disabled, and never appears in `disabledViews` or `disabledReasons`.
- `view === "sources"` was added to the project-wide outer condition, and the branch renders before the `!selectedResource` guard. It calls `slot.render({ openInEditor })`, which `AppShell` supplies as `() => setView("edit")`. `SourcesView` itself selects the Source in the store.
- A `useEffect` in `AppShell.tsx` sets the view to `"edit"` when the current view belongs to a registered module that is not enabled.

### `config.modules` and `isModuleEnabled` (reading)

- Declared in `ProjectConfigSchema` (`schemas.ts:388`, `z.record(z.string(), z.boolean()).optional()`), in `ApiProjectSchema` (`lib/api/schemas.ts:218`, same shape) and in the `ProjectConfig` type (`types.ts:156`). `config.features` and its schemas are not edited by Task 2.
- `isModuleEnabled(config, id)` is `true` when `config`, `config.modules` or the entry is absent, and `false` only when the entry is an explicit `false`. It uses `hasOwnProperty`, so an inherited property is not read as an entry. An id no registered module has is handled the same way.

### The index-step seam (reading)

- `ModuleIndexStep` is `{ id, run(projectRoot) }`. A module owns zero or more in `indexSteps`.
- `registry.indexSteps(config)` returns the steps of modules enabled for that config.
- `rebuildDerivedIndexes` rebuilds, in order: the inverted index, the annotation-body index (`meta/index/annotations.json`), backlinks and the mention index. It then runs the index steps of enabled modules. It does not rebuild prose diagnostics (OQ-11).
- It reads `config.modules` (plain `readFile` of `project.json` through `readModulesConfig`, not `updateProjectJson`) only when some registered module owns a step. A missing `project.json` reads as no config. Any other read failure, a locked project included, is rethrown.
- `runModuleIndexSteps(projectRoot)` in `indexer-queue.ts` does the same per save, inside `runTask`'s `runForTenant` scope, using the same `readModulesConfig`. A locked-access error is rethrown (and `runTask`'s outer catch logs it as a failed task). Any other read failure logs `[indexer-queue] config.modules read failed:` and skips the module steps. A step that throws a non-locked error is logged and the next step runs.
- The Sources module owns no index: its manifest `indexSteps` is empty (OQ-9). With the real manifest, a save performs no `config.modules` read (the early return in `runModuleIndexSteps`; a test pins it). Cases FR-6 (b) and (c) are therefore tested on a module registered only in tests. No document under `docs/` or `CLAUDE.md` yet says plainly that the Sources module owns no index (a grep for "owns no index" and "owns no derived" in `docs/`, `frontend/CLAUDE.md` and `CLAUDE.md` found nothing). That is part of the documentation tasks (FR-33), not yet done.
- `entities` indexing is untouched: it still indexes while its feature flag is off (a test pins it).

## 5. The per-save cost of the `config.modules` read (Task 1)

From `experiments.md`. Test: `tests/unit/indexer-queue.test.ts`, describe "indexer queue per-save time with an extra project.json read (F103 Task 1)" in `experiments.md`. In the file as committed, the describe and test titles read "with an isExtra project.json read" and "with and without one isExtra unlocked project.json read". It records; it asserts no timing threshold.

Method, as recorded: `runTask` is not exported, so each save is one `enqueueIndex` followed by `flushIndexer`, over a real-filesystem adapter wrapped to timestamp every adapter call. The span measured runs from the start of the first adapter call to the end of the last adapter call of that one task. In the "with" condition the wrapper, at the sidecar read that opens `runTask`, first awaits one plain `readFile` of `project.json` followed by `JSON.parse`, inside the measured span. The extra read is issued from the wrapper adapter, not from inside `runTask` (Task 1 made no product source change). No lock is taken for that read. The two conditions alternate (order flipped each iteration); 5 unmeasured warm-up saves precede them. Project: 40 text resources of 400 words each, no entities, no authored backlinks; `project.json` 5252 bytes (200 statuses and 200 subtypes in `config`). 30 saves per condition per test run; three test processes. Base commit `32924842`; Node v24.15.0; Darwin arm64; run inside the Bash sandbox; no build.

Observed medians, with min and max over 30 saves, in milliseconds:

| Test run | Without extra read (median / min / max) | With one extra `project.json` read (median / min / max) |
| -------- | --------------------------------------- | ------------------------------------------------------- |
| 1        | 10.76 / 9.36 / 19.75                    | 11.11 / 10.13 / 19.82                                   |
| 2        | 11.10 / 10.20 / 12.51                   | 10.92 / 9.68 / 12.28                                    |
| 3        | 10.94 / 10.12 / 20.39                   | 11.18 / 9.62 / 19.68                                    |

Recorded observation: across these runs the per-save median is about 10.7 to 11.2 ms in both conditions, and the difference between the two medians within a run ranges from -0.2 to +0.4 ms. An earlier set of 3 runs with a 46-byte `project.json` gave medians of 10.72, 10.89, 10.92 ms without and 11.06, 10.82, 10.77 ms with the read; an intermediate set of 3 runs at 5252 bytes gave 11.06, 11.22, 11.15 ms without and 10.97, 11.11, 11.04 ms with it. These are values from one machine and one project size. No cause is stated for them, and the 30-run samples were not tested statistically.
