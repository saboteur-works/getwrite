## Overview

Five places in GetWrite show a writer an absence where something is hidden or lost. One project with a damaged `project.json` can hide every project on the start page, and a project the server skips is not shown at all. Deleting a folder that contains folders was seen to fail with a 404. A field the writer deprecated may still appear in the sidebar although the dialog says it is hidden. A resource's entity kind may be left out of a later save. And a locked or keyless project may be read as an empty folder tree. This feature makes each failure visible or removes it: an unusable project is listed as a card that cannot be opened and says why, a folder delete moves the whole subtree to Trash as one restorable unit, a deprecated field is not shown and keeps its values, the entity declaration persists, and a locked-access error is no longer discarded. Each part starts from a reproduction on `main`, because several causes are readings or hypotheses.

## Goals

- A project whose `project.json` cannot be used no longer hides any other project, and is itself listed as a card that cannot be opened, with a reason.
- Deleting a folder with nested folders, at any depth, moves the whole subtree to Trash and it restores as one unit.
- A deprecated field is not shown in the resource sidebar, its stored values stay on the resource, and they reappear when the field is restored; the four places that say so remain true.
- What the server stores for `entityKind` after a later custom-field edit is measured, and a stored entity declaration is not lost by that edit.
- A locked-access error is not swallowed on the way to an empty folder tree, in every caller the survey shows is exposed.

## Non-goals

- Folders with no `project.json` (note_3c11e2c4): they stay skipped and unlisted.
- A repair, rename or delete action on an unusable project's card.
- The locked-encrypted project card (already fixed, 96b4bff7).
- The wider stale-save family. `aliases` and `wordCountGoal` were not measured; this feature does not claim to fix them, and does not measure them except as FR-24 permits.
- Un-deprecating from the sidebar, or any change to how a deprecated field is queried (it stays queryable, flagged).
- Any new route, feature flag or setting.

## User stories

- US-1: As a writer with several projects, I want to see one damaged project as a card that says it cannot be opened, with the rest still listed and openable, so that I never think my other work has disappeared. (Product spec US-15.)
- US-2: As a writer who deletes a folder of folders, I want to have the whole tree go to Trash and come back together so that I can undo a delete. (Product spec US-11.)
- US-3: As a writer who deprecated a metadata field, I want to have it gone from the sidebar with its values kept so that I can restore it without losing data. (Product spec US-14.)
- US-4: As a novelist who declares entities, I want to keep a resource's entity kind through later edits to the same resource so that my characters and places do not silently stop being entities. (Product spec US-3.)
- US-5: As a writer whose project is locked or whose files cannot be read, I want to be told so, instead of being shown an empty project or folder tree, so that I do not mistake locked or unreadable work for lost work. (Product spec US-30, owner decision Gate 3, 2026-10-18; the locked-access constraint.)
