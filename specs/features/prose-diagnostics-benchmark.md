# Feature: Prose diagnostics — cost benchmark (measurement)

Parent: `specs/product/getwrite.md` FR-49, US-22; `specs/product/getwrite.features.md` Feature 63. Mirrors Feature 57's shape (measurement-only, no code change) — the difference is this measurement has not yet been taken.

## Overview

FR-49 requires each of prose diagnostics' three scalar metrics (dialogue ratio, average sentence length, top repeated words) to be benchmarked at 1k, 10k and 100k words before Feature 62's design — "computed by the existing indexer at save time" — is committed. This feature is that benchmark and nothing else: it produces a written cost finding, not product code. As measured 2026-09-26 (FR-49's own note), no prose-diagnostic code exists yet.

## Goals

- Measure each of the three metrics' wall-clock cost, independently and combined, at 1k/10k/100k words of realistic prose.
- Produce a written finding — numbers plus a recommendation (safe to compute synchronously in the indexer at save time, or needs to move async/background) — recorded back onto FR-49/Feature 62.
- Leave Feature 62 blocked on this finding, per Feature 63's own Notes in the features doc.

## Non-goals

- No product code, no schema change, no transport, no UI (matches Feature 57).
- No decision on where in the indexer the metrics eventually run — that is Feature 62's design, gated on this finding.
- No pass/fail threshold for the measured numbers — resolved at Gate 3 (OQ-3): setting a threshold is left to Feature 62's design owner, since no existing indexer timing budget is documented to compare against.
- No decision on which of Feature 62's designs (metrics computed together vs. split) the project takes — resolved at Gate 3 (OQ-4): the finding reports both combined and individual costs and states the recommendation conditionally on that undecided design choice.

## User stories

- US-1: As a product engineer preparing Feature 62's design, I want to measure the cost of each of FR-49's three scalar metrics at 1k/10k/100k words so that I do not size the "computed by the existing indexer at save time" design against an unmeasured cost.

## Functional requirements

- FR-1: The benchmark MUST measure the wall-clock cost of each of the three named metrics (dialogue ratio, average sentence length, top repeated words) independently, at 1k, 10k and 100k words. [US-1]
- FR-2: The benchmark MUST also measure the combined cost of running all three metrics together at each of the three sizes, since Feature 62's design runs them together inside one indexer task (`indexer-queue.ts`'s `runTask`, verified at lines 177-239 to already chain inverted-index, backlinks, and mention-index work per resource). Resolved at Gate 3 by the user ("take your recs"), 2026-09-27 (OQ-4): the finding MUST report both the combined cost (the primary number, per FR-5) and each metric's individual cost (per FR-1) at each size, and MUST NOT collapse either measurement into the other. [US-1]
- FR-3: The benchmark MUST run against realistic prose fixtures, not synthetic repeated text — repeated text would not exercise dialogue/sentence-boundary detection cost realistically. Resolved at Gate 3 by the user ("take your recs"), 2026-09-27 (OQ-1): the fixture is a small public-domain prose excerpt (e.g. from Project Gutenberg) trimmed to exact word counts for the 1k/10k/100k sizes, checked into a new `frontend/tests/fixtures/prose-diagnostics-benchmark/` directory alongside a license/attribution note; the source text MUST contain actual dialogue (quoted speech), so the dialogue-ratio metric's cost is measured against real variance rather than a dialogue-light or dialogue-only excerpt. Sourcing and licensing this excerpt is part of this feature's own scope, not a deferred decision. [US-1]
- FR-4: The benchmark MUST run as a standalone script or test, producing no product code change, no schema change (`schemas.ts` untouched), no new transport, and no UI — matching Feature 57's "measurement only, no feature branch expected." [US-1]
- FR-5: The finding MUST be recorded as a written report against FR-49/Feature 62. Resolved at Gate 3 by the user ("take your recs"), 2026-09-27 (OQ-2): recorded by mirroring Feature 57's exact recording pattern — a Notes update on Feature 63's own entry in `specs/product/getwrite.features.md`, plus a resolution appended to FR-49's text in `specs/product/getwrite.md` (replacing the "no cost is claimed here" placeholder) once measured — including the measured numbers per metric per size (FR-1), the combined cost at each size (FR-2), and a recommendation stated conditionally per FR-2's resolution rather than a single "safe synchronously" / "needs to move async" verdict independent of Feature 62's eventual design shape. Recording this is a future step for whoever runs the benchmark, not performed as part of this spec amendment; no new open question in the parent spec is needed for it. [US-1]
- FR-6: The finding MUST report raw wall-clock measurements only (per-metric and combined, at each of the three sizes) and MUST NOT assert or recommend a fixed pass/fail threshold. As verified 2026-09-26, neither `indexer-queue.ts` nor `mention-index.ts` documents a per-resource timing budget, threshold, or SLA for the background indexing queue (`indexer-queue.ts`'s `runTask`/`processQueue`, `mention-index.ts`'s load/persist functions). Resolved at Gate 3 by the user ("take your recs"), 2026-09-27 (OQ-3): setting any threshold is explicitly left to Feature 62's design owner — inventing one now would present a judgment as a finding, not a measurement. [US-1]
- FR-7: The finding MUST state, as verified fact, that indexing today is fire-and-forget and out of the save's response path: `revision-manager.ts:63-66` awaits nothing after `void enqueueIndex(...)` (commented "do not await"), and `sidecar.ts:181-199`'s `writeSidecar` schedules indexing via `setImmediate` after its own write returns. The canonical-autosave path (`revision-core.ts:422-501`, `updateRevisionInPlace`) reaches indexing only indirectly, through its own call to `writeSidecar` at line 481. This means a new synchronous cost inside `runTask` would not block the save's HTTP/native response, but — because `processQueue` runs tasks strictly sequentially (verified at `indexer-queue.ts:241-255`) — would extend that resource's own background task and delay every resource queued behind it. [US-1]

## Out of scope (deferred)

- Prose diagnostics' full design, persistence, transport, and UI (Feature 62) — gated on this feature's closed finding.
- Any optimization of the metrics' algorithms; this benchmark measures cost, it does not reduce it.
- Native-platform-specific cost measurement (Android); no evidence was sought on whether native's compute characteristics differ, and this is not claimed either way.
