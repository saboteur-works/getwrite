Settled decisions, not reopened here (Gate 1, 2026-11-16, and Gate 2 of the same date). The 20 questions this spec raised were resolved at Gate 3, 2026-11-18, and are recorded under "Open questions" and in the requirements they affect:

- The target is the first selected document, the others are appended after it in tree order, the dialog shows which document is the target, and a joint is one empty paragraph (OQ-257, OQ-256, FR-237).
- An absorbed document is never deleted: it stays in the tree, marked as merged into its target, until the writer removes it through the existing delete to Trash (FR-238, FR-239). Every revision of every absorbed document is kept.
- While marked as merged, a document is excluded automatically from compile, the project total goal, the daily goal, the Goal filter and word counts; it stays searchable and is still exported; the rule is stated to the writer where the mark is shown (OQ-251, FR-240).

## Overview

A writer who has drafted three captures or fragments that turned out to be one piece can fold them together today only by copy and paste, which leaves each passage's revisions, notes, citations and claims behind and records nothing about where the text came from. This feature lets a writer select two or more text documents in the tree and merge them into the first selected one: the target keeps its text and gains the text of the others, appended in tree order with one empty paragraph at each joint. A dialog shows which document is the target and asks each time which notes, citations, claims and metadata travel with the text. Nothing is deleted: every absorbed document stays in the tree, marked as merged into the target, with all its revisions, until the writer removes it, and while marked it is left out of compile, the goals and word counts so that the text is not compiled or counted twice, but it stays searchable and is still exported. The latest merge can be undone without losing text. It covers desktop and hosted web.

## Goals

- A writer can merge an eligible selection of two or more text documents and, in one operation, end up with the first selected document holding its own text followed by the others' text in tree order, each absorbed document unchanged in its place in the tree except for a mark naming its target, and every other document unchanged.
- Every absorbed document keeps every revision it had, the target and each absorbed document gain one preserved snapshot of their pre-merge text, and each document has exactly one canonical revision.
- The writer sees which document is the target before the merge, chooses each time and from the same fixed starting choices what travels with the text, and the target's own values never change unless chosen.
- While a document is marked as merged, each of compile, export, the project and daily goals, the Goal filter, search and word counts has one stated and tested rule, shown to the writer where the mark is shown, and moved text adds nothing to the writing log.
- The writer can undo the latest merge after a reload without losing any text, including edits made since, and a failure at any step of a merge or an Undo leaves no document half-changed and is reported.

## Non-goals

- Split, the lineage record of a split-off document, and Undo split (Feature 120, shipped); this feature changes Undo only to add the merge branch and leaves the split branch behaviour unchanged.
- Showing lineage in a document's history, including "merged into Y" with a way to open the target (Feature 122). The mark shown in the tree (FR-16) is this feature's.
- Unmerge (Product FR-259, v2): restoring absorbed documents and removing their text from the target by the recorded lineage. Undo merge of the latest operation is the only way back.
- Undo of any operation but the latest, editor-level undo across documents, and a time window on Undo. A later split or merge replaces the latest-operation record, so an earlier operation can no longer be undone.
- Merging Sources (Product FR-265, v2), entity documents (Feature 125), folders and image or audio resources, and merging a document marked as merged.
- Merge on Android or on a paired device and any claim for either (Features 128 and 124); a remembered carry-over default; a sixth paired-device limit switch.
- Alternates, reconciling edits between devices, any other way of moving text between documents, any change to how canonical revisions work (Product FR-255), and moving or renaming an absorbed document as part of a merge.

## User stories

- US-1: As a writer who has drafted several captures or fragments that turned out to be one piece, I want to select them in the tree and merge them into the first one I selected, seeing which document is the target and keeping the others in the tree marked as merged until I remove them, so that I can fold text together without anything silently disappearing. (Product US-56; FR-237 to FR-239.)
- US-2: As a writer merging documents whose passages carry notes, citations and claims and whose fields carry status and point of view, I want to be asked each time what travels with the text and to have the target's own values stay as they are unless I choose otherwise, so that nothing is invented, nothing is deleted and my notes do not come loose. (Product US-56; FR-241 to FR-243.)
- US-3: As a writer who has merged documents, I want to have a stated rule for how a merged-away document is treated by compile, export, my goals, the Goal filter, search and word counts, shown where the mark is shown, so that the same text is not compiled or counted twice by surprise and I can still find and export it. (Product US-56; FR-240.)
- US-4: As a writer who merged and changed my mind, I want to undo the latest merge after closing and reopening the project, so that the target and every absorbed document are back as they were and nothing I typed since is lost. (Product US-56; FR-246, FR-262.)
- US-5: As a writer who selects something that cannot be merged, such as a folder, a Source, an entity document, an image or a document already merged away, I want to get a clear stated reason and no change, so that I never find a half-merged project. (Product US-56; FR-261.)
- US-6: As a product owner, I want to have the unknowns about tree selection, the surfaces the merged-away rule touches, locking of many documents and Undo of many documents measured first, and a desktop and a hosted run recorded by the lead, so that no claim outruns what was observed. (Product FR-237 to FR-263 as a whole.)
