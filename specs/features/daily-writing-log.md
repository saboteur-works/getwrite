# Feature: Daily writing log and daily goal

> Scope note: over the 500-word guideline because it carries decisions already
> resolved in the parent spec as requirements. The feature is one log plus one goal.

## Overview

Nothing records when words were written. As measured 2026-09-26, sidecars carry only `createdAt`/`updatedAt`, so a per-day count cannot be derived from stored data, and history before this feature ships cannot be backfilled. This feature keeps an append-only, per-project, per-day log of words added, deleted and net, and lets a writer set a daily goal and compare the day's figures against it. Progress is then measured in writing done rather than total length.

Parent: `specs/product/getwrite.md` FR-48, FR-50, US-21 (OQ-42 to OQ-49 resolved); `specs/product/getwrite.features.md` Feature 59.

## Goals

- A writer can see, per project per day, words added, deleted and net.
- A writer can set a daily goal and see today's figures against it.
- Imported words are visible but never counted toward the daily goal.
- A save whose previous content is unreadable is visibly reported, never silently logged as zero.
- Behaviour is identical on web/desktop and native.

## Non-goals

- No backfill of history before the log ships.
- No capture of a word added and then deleted between two saves.
- No log entries for non-canonical revision saves.
- No change to the existing red "Unsaved edits" text at `EditView.tsx:419`; FR-8 applies only to the goal display.
- No logging of plain-text import (see FR-10).

## User stories

- US-1: As a writer on deadline, I want to keep a per-project, per-day record of words added, deleted and netted so that I can see whether I wrote today.
- US-2: As a writer, I want to set a daily goal and compare today's figures against it so that I know when I have met it.
- US-3: As a writer, I want to see imported words separately from my writing so that an import does not count as a day's work.

## Functional requirements

- FR-1: The product MUST append, per project per day, entries recording words added, words deleted and net, each carrying its full ISO timestamp. Each word entry MUST store `added`, `deleted` and `net`, and `net` MUST equal `added` minus `deleted`, validated in the schema (amended at Gate 4, 2026-09-26). The entries are filed by the UTC date of that timestamp (FR-4); the writer's local calendar day is derived from the timestamp at read time (OQ-1, OQ-8). [US-1]
- FR-2: On each debounced canonical autosave via `updateRevisionInPlace`, the product MUST log one entry, with additions being words added since the previous save by before/after comparison. Non-canonical saves MUST NOT be logged. Word counts MUST use `countWords` (`frontend/src/lib/word-count.ts`) on `tiptapToPlainText(doc)`, matching sidecar `wordCount`, and MUST NOT use the counter at `previews.ts:97` (OQ-3). [US-1]
- FR-3: A docx or Scrivener import MUST log one additions entry on the import day under the new project's id, with a `source` field marking it as an import. [US-3]
- FR-4: The log MUST be append-only, meaning entries are only ever appended and never edited or removed, even though the containing day file is rewritten on each append. It MUST be validated in `schemas.ts`, persisted through the storage adapter as one file per day at `meta/writing-log/YYYY-MM-DD.json`, and each append MUST be a read-modify-write inside `withMetaLock(projectRoot, ...)`, as `mention-index.ts` does. It MUST rethrow `isLockedAccessError` and fail closed when locked rather than degrading to empty. The file key `YYYY-MM-DD` MUST be the UTC date of the entry's ISO timestamp, computed on the server or native side, and MUST NEVER be accepted from a client (path safety: a client-supplied date would be a path-affecting field on the save request); a malformed key MUST NOT be producible. Each entry keeps its ISO timestamp, so the file key encodes no day definition (OQ-2, OQ-8; amended at Gate 4, 2026-09-26). [US-1]
- FR-5: When previous content cannot be read, or is non-TipTap (legacy plain-text) content for which `syncDerivedResourceContent` returns undefined, the word entry MUST be skipped, a marker entry of a distinct kind (`skipped: true`, with its ISO timestamp and no word counts) MUST be appended to the log instead, and a visible failure signal surfaced per `docs/standards/failure-visibility.md`. The signal MUST be a deduplicated toast (stable id via `toastService`, as `reportTransportValidationFailure` does) plus a "today's count may be incomplete" marker on the goal display for any local day containing a marker entry (OQ-4). If the marker append itself fails, the fallback is the toast plus an in-memory session flag driving the same display text (amended at Gate 4, 2026-09-26). The check MUST use its own read, because `snapshotBeforeDestructiveWrite` returns null for both unreadable and non-destructive cases. [US-1]
- FR-6: A writer MUST be able to set and clear an optional `dailyWordGoal` in project config, distinct from `wordCountGoal`, from the project settings dialog (`frontend/components/Layout/ProjectSettingsDialog.tsx`). [US-2]
- FR-7: The display MUST compare today's non-import figures against `dailyWordGoal`, aggregated at read time by deriving the writer's local day from entry timestamps across the UTC day files overlapping that local day (at most 2-3 files), and show import entries on a separate line excluded from the comparison. It MUST be a read-only today-versus-goal display in the editor footer (the `<footer id="editview-footer">` in `frontend/components/WorkArea/EditView.tsx`, OQ-9), always visible, and the footer display MUST be expandable (user decision at Gate 3, 2026-09-26). Collapsed (the default) it MUST show the today-versus-goal figure as text (for example "Today: 420 / 1000"), or just today's net when no goal is set; expanded it MUST add words added, deleted and net, and the separate import line (OQ-10, OQ-11). The expanded/collapsed state MUST persist in global `localStorage` under a `getwrite.*` key (for example `getwrite.editFooter.expanded`), guarded for `typeof window` and try/catch like `frontend/src/lib/update-notice-suppression.ts` and `user-preferences.ts`, MUST render correctly with no stored value, and MUST NOT use a project-preference schema or transport (OQ-12). The toggle MUST be a native `<button type="button">` with `aria-expanded` and `aria-controls` and a visible accessible name (for example "Today's writing"), the expanded content MUST be in a region with that id, there MUST be no custom Esc binding and no Radix, and the goal display MUST sit outside the footer's `aria-live` region (`EditView.tsx:423`) (OQ-13). The read MUST take REQUIRED `from` and `to` parameters, the ISO start and end instants of the writer's local day, computed by the client (not a UTC offset and not an IANA zone name), with no server-timezone or server-UTC-day fallback. The window is a read parameter only selecting which UTC day files load and MUST NEVER be a path component (FR-4 unaffected). The shared core (`writing-log-core.ts`) MUST validate it so HTTP and native behave identically: both parse as ISO instants (Zod datetime), `to` is after `from`, the window length is at most 26 hours, and at most 3 or 4 UTC day files are loaded; a window that fails validation or exceeds the cap MUST be REJECTED (HTTP 400, a thrown error on native), never clamped. A 23-hour and a 25-hour (DST) local day MUST be accepted (OQ-14). Because the day is derived at read time, the day definition is reversible and can change retroactively. [US-2] [US-3]
- FR-8: The goal display MUST NOT be indicated in red. [US-2]
- FR-9: Every new client transport (read log, set goal) MUST resolve through `createTransport` with a native backend and a web-stub, and MUST validate HTTP response bodies (FR-50). The read transport carries the required `from`/`to` window of FR-7 as query parameters on HTTP (read via `new URL(req.url).searchParams`, as `frontend/app/api/project/[project-id]/search/route.ts:51-59` does) and as arguments on native, with the client computing the local-day instants; a rejected window maps to HTTP 400 and to the same thrown error on native (OQ-14). [US-1] [US-2]
- FR-10: Plain-text file import MUST NOT be logged; it does not exist today. [US-3]
- FR-11: Additions and deletions MUST be computed as a word-bag (multiset) difference: added is the words in the after text not matched in the before text; deleted is the reverse; net is added minus deleted. Known blind spots: a moved paragraph logs nothing, and a rewrite that reuses common words undercounts. Compute cost is unmeasured. [US-1]
- FR-12: The log is not rebuildable from resources, so the `reindex` CLI MUST NOT clear or rebuild it. [US-1]
- FR-13: Feature 59 is sequenced before Feature 61. The task list MUST flag adding `dailyWordGoal` beside `wordCountGoal` at `schemas.ts:237` and `:615`, plus `api/schemas.ts:159`, `types.ts:95`, `project.ts:13`, and `project-creator.ts` (`:148`, `:233`) if it must round-trip. These lines were verified to exist on 2026-09-26. [US-2]

## Open questions

- OQ-1: How is the day boundary defined (local time or UTC) and stored? — Impact: FR-1, FR-2, FR-3, FR-7. Resolved 2026-09-26. Resolved at Gate 3 by the user: store the full ISO timestamp per entry; the local calendar day is derived at read time and goal display aggregates at read time. The day definition is therefore reversible and can change retroactively.
- OQ-2: What is the log's file layout and shape, and how is concurrent append serialized? — Impact: FR-1, FR-4. Resolved 2026-09-26. Resolved at Gate 3 by the user: one file per day at `meta/writing-log/YYYY-MM-DD.json`, serialized by read-modify-write inside `withMetaLock(projectRoot, ...)` rethrowing `isLockedAccessError`; "append-only" means entries are only appended; `reindex` must not clear the log (FR-12). The file-key rule was raised as OQ-8. Amended at Gate 4 by the user (2026-09-26): the file key is the UTC date of the entry's ISO timestamp, computed server/native side and never client-supplied; this supersedes the local-date file key implied in the Gate 3 resolution.
- OQ-3: Which word-counting function is used for before/after comparison, and does it match sidecar `wordCount`? — Impact: FR-2. Resolved 2026-09-26. Resolved at Gate 3 by the user: `countWords` on `tiptapToPlainText(doc)`, matching sidecar `wordCount`; not `previews.ts:97`. FR-5 also covers non-TipTap content. Amended at Gate 4 by the user (2026-09-26): each entry stores added, deleted and net, with net validated to equal added minus deleted (FR-1); FR-5's skip now also records a marker entry, superseding the Gate 3 "skip the entry" and "persistent marker" wording (see OQ-4).
- OQ-4: How is the FR-5 failure signal surfaced? — Impact: FR-5. Resolved 2026-09-26. Resolved at Gate 3 by the user: a deduplicated toast plus a persistent "today's count may be incomplete" marker on the goal display. Verified 2026-09-26 in `frontend/src/lib/toast-service.ts`: the error toast accepts an optional `{ id?: string }` options parameter. Amended at Gate 4 by the user (2026-09-26): the marker is derived from marker entries in the log per local day, not a session-persistent flag; the session flag is only the fallback if the marker append fails. This supersedes part of the Gate 3 resolution.
- OQ-5: Where does the today-versus-goal display live in the UI? — Impact: FR-7, FR-8. Resolved 2026-09-26. Resolved at Gate 3 by the user: goal setter in the project settings dialog (`ProjectSettingsDialog.tsx`, path verified to exist); read-only display in the editor footer, always visible, non-red, imports on a separate line. The footer component's path is raised as OQ-9.
- OQ-6: How are deletions vs additions computed from a before/after comparison? — Impact: FR-2, FR-11. Resolved 2026-09-26. Resolved at Gate 3 by the user: word-bag (multiset) difference, defined with its blind spots in FR-11.
- OQ-7: Do the `schemas.ts` edits collide with Feature 61's edits, and how are they sequenced? — Impact: FR-4, FR-6, FR-13. Resolved 2026-09-26. Resolved at Gate 3 by the user: Feature 59 first; the task list flags the touch points in FR-13.
- OQ-8: The day file key is chosen at write time (local date), but OQ-1 derives the day at read time. If the day definition later changes, entries already filed under a local-date key could be misfiled; how is that reconciled (re-key on read, or accept)? Resolved 2026-09-26. Resolved at Gate 3 by the user ("use your recs"): accept, keying the day file at write time by local date with no re-keying on read. Amended at Gate 4 by the user (2026-09-26): this supersedes the Gate 3 acceptance. Day files are keyed by the UTC date of the entry's ISO timestamp, computed server/native side, never client-supplied. Reason: the server timezone on hosted web is not the writer's, and a client-supplied date would add a path-affecting field to the save request. The writer's local day is derived at read time from timestamps by loading the UTC day files overlapping it (at most 2-3). The file key therefore encodes no day definition, and this question's concern (a changed day definition leaving entries under the wrong key) no longer applies. — Impact: FR-1, FR-4, FR-7

- OQ-14: How does the read path learn the writer's local day window, given that the server timezone on hosted web is not the writer's? The window is a read parameter that only selects which UTC day files to load, not a path component, so FR-4's no-client-supplied-date rule is not affected. Resolved 2026-09-26. Resolved at Gate 4 by the user ("take your recs"): the client sends the ISO start and end instants of its local day (`from`, `to`), not a UTC offset and not an IANA zone name. Validation lives in the shared core (`writing-log-core.ts`) so HTTP and native validate identically: both parse as ISO instants (Zod datetime), `to` is after `from`, the window is capped at 26 hours, and at most 3 or 4 UTC day files are loaded; a failing or over-cap window is rejected (HTTP 400 / thrown error on native), never clamped. `from`/`to` are required, with no server-timezone or server-UTC-day fallback. Evidence: existing GET routes read `new URL(req.url).searchParams` (e.g. `frontend/app/api/project/[project-id]/search/route.ts:51-59`); there is no existing timezone or window precedent (`timestamp-utils.ts:25` is display-only). — Impact: FR-1, FR-7, FR-9
