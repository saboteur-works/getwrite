# Feature: Daily writing log and daily goal

> Scope note: over the 500-word guideline because it carries decisions already
> resolved in the parent spec as requirements. The feature is one log plus one goal.

## Overview

Nothing records when words were written. As measured 2026-09-26, sidecars carry only `createdAt`/`updatedAt`, so a per-day count cannot be derived from stored data, and history before this feature ships cannot be backfilled. This feature keeps an append-only, per-project, per-day log of words added, deleted and net, and lets a writer set a daily goal and compare the day's figures against it. Progress is then measured in writing done rather than total length.

Parent: `specs/product/getwrite.md` FR-48, FR-50, US-21 (OQ-42 to OQ-49 resolved); `specs/product/getwrite.features.md` Feature 59.

## Goals

- A writer can see, per project per day, words added, deleted and net.
- A writer can set a daily goal and see today's figures against it.
- Imported words are visible but never counted toward the daily goal.
- A save whose previous content is unreadable is visibly reported, never silently logged as zero.
- Behaviour is identical on web/desktop and native.

## Non-goals

- No backfill of history before the log ships.
- No capture of a word added and then deleted between two saves.
- No log entries for non-canonical revision saves.
- No change to the existing red "Unsaved edits" text at `EditView.tsx:419`; FR-8 applies only to the goal display.
- No logging of plain-text import (see FR-10).
- Amended at Gate 6 (2026-09-26): this pass builds only Feature 59's own content in the writing-details overlay (added, deleted, net, import line, incomplete marker). Nothing from Feature 60 (status roll-up) or Feature 62 (prose diagnostics) is built here, though the overlay is intended as the later home for writing diagnostics of this and related features, so its surface should not preclude adding them.

## User stories

- US-1: As a writer on deadline, I want to keep a per-project, per-day record of words added, deleted and netted so that I can see whether I wrote today.
- US-2: As a writer, I want to set a daily goal and compare today's figures against it so that I know when I have met it.
- US-3: As a writer, I want to see imported words separately from my writing so that an import does not count as a day's work.

## Functional requirements

- FR-1: The product MUST append, per project per day, entries recording words added, words deleted and net, each carrying its full ISO timestamp. Each word entry MUST store `added`, `deleted` and `net`, and `net` MUST equal `added` minus `deleted`, validated in the schema (amended at Gate 4, 2026-09-26). The entries are filed by the UTC date of that timestamp (FR-4); the writer's local calendar day is derived from the timestamp at read time (OQ-1, OQ-8). [US-1]
- FR-2: On each debounced canonical autosave via `updateRevisionInPlace`, the product MUST log one entry, with additions being words added since the previous save by before/after comparison. Non-canonical saves MUST NOT be logged. Word counts MUST use `countWords` (`frontend/src/lib/word-count.ts`) on `tiptapToPlainText(doc)`, matching sidecar `wordCount`, and MUST NOT use the counter at `previews.ts:97` (OQ-3). Amended at Gate 6 by the user ("Both, take your recs"), 2026-09-26 (OQ-23; supersedes the earlier reading that every debounced canonical autosave logs one entry): a canonical save whose before/after comparison gives `added` == 0 AND `deleted` == 0 MUST NOT append a log entry and MUST NOT signal a skip; a save with `added` > 0 or `deleted` > 0 MUST be logged even when `net` is 0 (for example a same-size word replacement). The FR-5 skipped-save marker (unreadable or non-TipTap previous content) is unaffected and is still recorded. This rule applies to the save path only; imports (FR-3) are unchanged (OQ-24, resolved at Gate 6 by the user, 2026-09-26): a zero-word docx or Scrivener import still writes its one entry (added 0, source-tagged), because an import is a deliberate event and the entry records that it happened. [US-1]
- FR-3: A docx or Scrivener import MUST log one additions entry on the import day under the new project's id, with a `source` field marking it as an import. [US-3]
- FR-4: The log MUST be append-only, meaning entries are only ever appended and never edited or removed, even though the containing day file is rewritten on each append. It MUST be validated in `schemas.ts`, persisted through the storage adapter as one file per day at `meta/writing-log/YYYY-MM-DD.json`, and each append MUST be a read-modify-write inside `withMetaLock(projectRoot, ...)`, as `mention-index.ts` does. It MUST rethrow `isLockedAccessError` and fail closed when locked rather than degrading to empty. The file key `YYYY-MM-DD` MUST be the UTC date of the entry's ISO timestamp, computed on the server or native side, and MUST NEVER be accepted from a client (path safety: a client-supplied date would be a path-affecting field on the save request); a malformed key MUST NOT be producible. Each entry keeps its ISO timestamp, so the file key encodes no day definition (OQ-2, OQ-8; amended at Gate 4, 2026-09-26). [US-1]
- FR-5: When previous content cannot be read, or is non-TipTap (legacy plain-text) content for which `syncDerivedResourceContent` returns undefined, the word entry MUST be skipped, a marker entry of a distinct kind (`skipped: true`, with its ISO timestamp and no word counts) MUST be appended to the log instead, and a visible failure signal surfaced per `docs/standards/failure-visibility.md`. The signal MUST be a deduplicated toast (stable id via `toastService`, as `reportTransportValidationFailure` does) plus a "today's count may be incomplete" marker on the goal display for any local day containing a marker entry (OQ-4). If the marker append itself fails, the fallback is the toast plus an in-memory session flag driving the same display text (amended at Gate 4, 2026-09-26). The check MUST use its own read, because `snapshotBeforeDestructiveWrite` returns null for both unreadable and non-destructive cases. [US-1]
- FR-6: A writer MUST be able to set and clear an optional `dailyWordGoal` in project config, distinct from `wordCountGoal`, from the project settings dialog (`frontend/components/Layout/ProjectSettingsDialog.tsx`). Amended at Gate 6 by the user (2026-09-26): the goal MUST be set from its own "Writing Goals" tab in Project Settings, and the Default Revision Name tab MUST NOT contain it; the user's words were "the writing goal is buried in the default revision name tab and should be in its own 'Writing Goals' tab." The tab is appended last, after Metadata, is labelled "Writing Goals", and hosts the existing "Daily writing goal" section unchanged with no extra description; the dialog test's tab count goes from five to six. It hosts the daily goal field only for now; it is intended as the later home for the total-length goal (`wordCountGoal`, Feature 61), but nothing from Feature 61 is built in this pass (OQ-20 to OQ-22, resolved at Gate 6, 2026-09-26). [US-2]
- FR-7: The display MUST compare today's non-import figures against `dailyWordGoal`, aggregated at read time by deriving the writer's local day from entry timestamps across the UTC day files overlapping that local day (at most 2-3 files), and show import entries on a separate line excluded from the comparison. It MUST be a read-only today-versus-goal display in the editor footer (the `<footer id="editview-footer">` in `frontend/components/WorkArea/EditView.tsx`, OQ-9), always visible. Amended at Gate 6 by the user (2026-09-26; supersedes the Gate 3 expandable-footer decision): the footer MUST keep the existing "Today's writing" text button plus the collapsed figure as text (for example "Today: 420 / 1000", or just today's net when no goal is set) and the "today's count may be incomplete" marker; it MUST NOT expand inline. Activating the button MUST open a closeable modal/overlay holding the writing details: words added, deleted and net, the separate import line (excluded from the comparison), and the incomplete marker (OQ-10 to OQ-13, OQ-15 to OQ-19). The button's tooltip MUST read "Show today's writing details", via `frontend/components/common/UI/HoverTip.tsx`; because that tooltip is hover-only and does not appear on touch or native, the details MUST NOT live only in the tooltip. The inline expand/collapse, the collapsed-by-default rule and the `getwrite.editFooter.expanded` `localStorage` persistence MUST be removed, and `frontend/src/lib/edit-footer-state.ts` and its tests (`frontend/tests/unit/edit-footer-state.test.ts`) MUST be removed or repurposed by the task that replaces the disclosure (Task 17); nothing may read or write that key afterwards. The overlay is a dialog, not a disclosure: it MUST have modal dialog semantics per `docs/standards/accessibility.md` (section 2, use the Radix primitive already in the dependency tree, not a hand-rolled one; section 3, focus is managed on open, Esc closes, focus returns to the "Today's writing" button on close) and a title that names it; `aria-expanded`/`aria-controls` no longer apply. Resolved at Gate 6 by the user ("Take your recs"), 2026-09-26 (OQ-15 to OQ-19): the overlay MUST be a blocking, focus-trapped modal built directly on `frontend/components/common/UI/Dialog` (`Dialog`, `DialogContent` following the `UnlockModal.tsx` layout, `DialogTitle`, `DialogDescription`, and a single close button in `DialogFooter`); it MUST NOT use `ConfirmDialog`. If no `DialogDescription` is rendered, the Radix describedby warning MUST be suppressed as `ConfirmDialog` does. The title MUST be "Today's writing"; the description MUST name the goal ("No daily goal set" when none); the body MUST show exactly the details above using the existing labels (Added, Deleted, Net, "Imported (not counted toward goal)") plus the incomplete marker, with no progress bar, local date or explanation text. The overlay MUST be read-only: the goal is set only in Project Settings (FR-6), and the overlay MAY show a plain-text hint pointing there but MUST NOT contain an editor. The goal display MUST sit outside the footer's `aria-live` region (`EditView.tsx:423`) (OQ-13). The read MUST take REQUIRED `from` and `to` parameters, the ISO start and end instants of the writer's local day, computed by the client (not a UTC offset and not an IANA zone name), with no server-timezone or server-UTC-day fallback. The window is a read parameter only selecting which UTC day files load and MUST NEVER be a path component (FR-4 unaffected). The shared core (`writing-log-core.ts`) MUST validate it so HTTP and native behave identically: both parse as ISO instants (Zod datetime), `to` is after `from`, the window length is at most 26 hours, and at most 3 or 4 UTC day files are loaded; a window that fails validation or exceeds the cap MUST be REJECTED (HTTP 400, a thrown error on native), never clamped. A 23-hour and a 25-hour (DST) local day MUST be accepted (OQ-14). Because the day is derived at read time, the day definition is reversible and can change retroactively. [US-2] [US-3]
- FR-8: The goal display MUST NOT be indicated in red. [US-2]

[US-1] [US-2]

Known blind spots: a moved paragraph logs nothing, and a rewrite that reuses common words undercounts. Compute cost is unmeasured. [US-1]
