## Overview

A writer who saves a template and creates a resource from it expects an
ordinary resource. Measured on 2026-10-08, they do not get one: after
`createResourceFromTemplate` the project's two loaders both fail for the
whole project (see "Measured"). This feature makes template creation write a
resource the way the app's own create path writes one, adds a shipped CLI
command to save a template from an existing resource (capturing the resource's
own metadata and subtype), and makes a resource made from a template, and a
copy or duplicate of a resource, carry the source's subtype so the fields a
writer scoped to a subtype appear without relabelling. A resource created
blank has no subtype. A second measurement the same day (see "Measured")
showed that a copy or duplicate of a text resource has no revision and drops
the writer's edits; the owner pulled that fix into this feature (decision C),
so a copied or duplicated text resource also gets an initial canonical
revision, written by the same code that writes a new resource's.

## Goals

- A resource created from a template is a normal resource: after creation the
  project loads, lists it with its content, and (for text) it has a canonical
  revision v-1, exactly as after the app's own create. Template creation
  supports text templates only; an image, audio or unknown template type is
  rejected with an error naming the type.
- A resource created from a template whose recorded subtype is "X" has
  subtype "X"; a template with none yields none. A resource created blank has
  no subtype, and no existing template or project needs a migration.
- The shipped CLI can save a template from an existing resource, recording
  its type, text body, own metadata and subtype and nothing else from its
  sidecar.
- A copy (UI, HTTP and native) and a duplicate (CLI) of a resource keep the
  source's subtype, covered by automated tests.
- A copy or duplicate of a text resource is editable like any other resource:
  it has an initial canonical revision v-1, so an edit to it is autosaved and
  survives a reload.

## Non-goals

- No template UI and no template API route (Verified: none exists; see
  "Verified code findings" 2).
- No registration of the other helper subcommands that exist only in
  `cli/src/templates.ts` (`inspect`, `parametrize`, `export`, `import`,
  `validate`, `scaffold`, `apply-multiple`, `preview`, `version`, `history`,
  `rollback`, `changeset`).
- Templates do not carry `entityKind`, `aliases`, `wordCountGoal` or
  `dismissedNoiseTerms` (Default accepted, RQ-5).
- Project-type `defaultResources` are a different concept and are not changed
  (Default accepted, RQ-6).
- No change to the importers: that none assigns a subtype is Feature 72's
  FR-27 (shipped and tested there).
- No lookup of a label against `config.subtypes`, no write to `project.json`
  by this feature's own code (every sidecar write still bumps
  `config.metadataRevision`; see FR-10), no rename, no Project Settings work, no general fix to the stale whole-resource
  sidebar save path (all settled by Feature 72).
- The source's revision history is not copied by copy or duplicate. Only the
  single initial canonical revision is created (FR-30). The earlier draft of
  this list excluded any change to what copy writes "unless the owner pulls
  it in"; the owner pulled the revision fix in (RQ-C, Owner decision, Gate 3,
  2026-10-08), and nothing else about what copy writes changes.
- No fresh name or `createdAt` for a duplicate (`duplicateResource` keeps the
  source's; see "Out of scope (deferred)").
- No `--folder`, `--vars` or `--dry-run` option on the shipped `templates
  create` (RQ-9).
- No image or audio templates (RQ-7).

## User stories

- US-1: As a writer on deadline, I want to have a resource created from a template, and a duplicate or copy of a resource, to carry the source's subtype, with a resource created blank having none, so that the fields I scoped to a subtype appear immediately without my relabelling each new resource. (Product US-25.)
- US-2: As a writer on deadline, I want to have a resource I create from a template open and behave like any other resource in my project so that using a template never leaves my project unable to load. (Product US-13.)
- US-3: As a writer on deadline, I want to save a template from a resource I have already written, through the shipped CLI, so that its body, its own metadata and its subtype become a reusable scaffold without hand-editing JSON. (Product US-13, US-25.)
- US-4: As a writer on deadline, I want to edit a copy or duplicate of a text resource and have my edits saved, so that copying a scene to rework it never silently discards my work. (Product US-6, US-9.)

## Functional requirements

FR-1: `createResourceFromTemplate` (`resource-templates.ts`) MUST persist a created text resource through the app's own persistence functions, not through a writer of its own: `createResourceOfType` (`resource-factory.ts`) to build and schema-validate the resource, `writeResourceToFile` (`resource-persistence.ts`) to write `resources/<id>/content.tiptap.json`, `resources/<id>/content.txt` and the full sidecar, and `writeRevision(projectRoot, id, 1, <JSON.stringify of a TipTap document>, { isCanonical: true, metadata: { name } })` (`revision.ts`) for the initial revision. The write-plus-initial-revision tail of `createResourceCore` (`resource-crud-core.ts`) MUST be extracted into one function that takes a project root (the "shared initial-revision writer"; its name is the implementer's choice) and is called by `createResourceCore`, by `createResourceFromTemplate`, by `copyResourceCore` (FR-28) and by `duplicateResource` (FR-29), so that app-created, template-created, copied and duplicated text resources cannot drift (Owner decision C, Gate 3, 2026-10-08, for the copy and duplicate callers). `createResourceCore` itself takes a `projectId` and resolves the root, so the template path cannot call it. The shared writer serializes the document as `createResourceCore` does today (`text.tiptap ?? plainTextToTipTapDocument(text.plainText ?? "")`, then `JSON.stringify`, because the editor only recognises a JSON payload when it loads a revision) and names the revision with `resolveInitialRevisionName(config)` over `loadProjectConfig(projectRoot)`. Today `createResourceCore` reads the config with `.catch(() => null)` (Verified, `resource-crud-core.ts`), which swallows every failure; the shared writer MUST instead catch narrowly: a locked-access error (`isLockedAccessError`) propagates, and any other config-read failure (no `project.json`, unparseable JSON, a schema failure) falls back to the name "Initial Draft". This is a deliberate change. It is behaviour-preserving for an unlocked project, which is every case in which the config read does not fail with a locked-access error; for a locked or keyless encrypted project it turns a silent fallback into a propagated error (Inference: that case would already have failed at the earlier `writeResourceToFile`, so the change is unlikely to be observable; not run). `createResourceFromTemplate` continues to own: loading the template, `{{VAR}}` substitution (`opts.vars`), the `opts.name` override, dry run, and resolving the template's `folderId`, `orderIndex`, `userMetadata` and `resourceSubtype` (FR-4 to FR-7). It MUST reject every template type other than `text` with an explicit error (FR-11). A locked-access error from any other read or write MUST propagate. [US-2]

FR-2: Acceptance test, the measurement inverted. In a project made by `createAndAssertProject`, after `saveResourceTemplate` of a text template and `createResourceFromTemplate`: `loadProjectFromDisk` MUST succeed and return the new resource with its content; `getLocalResources` MUST succeed and include it; `resources/<id>/content.txt` and `content.tiptap.json` MUST exist; a canonical revision v-1 MUST exist (`listRevisions`); and the sidecar MUST contain every key `writeResourceToFile` writes for a text resource (`id`, `name`, `type`, `createdAt`, `orderIndex`, `folderId`, `slug`, `userMetadata`, `wordCount`). [US-2]

FR-3: No flat `resources/<slug>-<id>.txt|.img|.aud` file MAY be written by template creation, and the minimal four-key sidecar MAY NOT be written. The old layout is being replaced, not preserved; no compatibility writer is kept. [US-2]

FR-4: Placement. A created resource's `folderId` MUST be `null` (project root) when the template has no `folderId` or it is `null`. When the template has a `folderId` that names an existing folder, the resource MUST be created in that folder. When it names no existing folder, creation MUST be rejected with an error naming the template id and the folder id, and nothing MAY be written (Default confirmed by the owner, Gate 3, 2026-10-08, RQ-8). This is stricter than the app's own create, which does not check that the target folder exists; it was chosen so that template creation cannot produce an orphan in `doctor`'s sense. A folder "exists" when a descriptor with that id is returned by `readFolderTree(<projectRoot>/folders)`. `orderIndex` MUST be one more than the largest `orderIndex` among the resources and folders that share the destination parent, or 0 when there are none. Resources and folders share one ordering space per parent; the effective parent is `parentId ?? folderId ?? null` for a folder and `folderId ?? null` for a resource (Verified, mirroring the client's computation in `app/(app)/page.tsx` and `doctor`'s `folderParentId`). It MUST be computed from persisted state at creation time, from `getLocalResources` plus `readFolderTree`, so that consecutive creations (`scaffoldResourcesFromTemplate`, `applyMultipleFromTemplate`) receive distinct values. It MUST NOT be computed through `loadProjectFromDisk`, which runs `migrateProjectOnLoad`; that function reads `project.json` (and so needs it) and writes it back when a migration applies (Verified, `project-loader.ts` and `metadata-schema.ts`). Both reads MUST complete before the first write (FR-33). When `getLocalResources` throws because the project already contains an old flat-layout resource (a sidecar missing required fields such as `slug`, written by an older `templates create`), the error template creation surfaces MUST name that situation (a resource sidecar in this project is missing required fields, which an older `templates create` produced; see FR-12) rather than propagate a bare `ZodError`. [US-2]

FR-5: The created resource's `userMetadata` MUST equal the template's `userMetadata` after `{{VAR}}` substitution, and be absent when the template has none, validated by the same schema parse the app's create path applies (`createResourceOfType` runs `TextResourceSchema.parse`); the app's create path does not check keys against the project's metadata schema and neither does this. `{{VAR}}` substitution applies to `userMetadata` string values as well as to `name` and `plainText`, through the existing recursive `applyVars`, which already descends into objects and arrays (Default confirmed by the owner, Gate 3, 2026-10-08, RQ-10). The shipped `templates create` passes no `vars`, so for the shipped binary the behaviour is the same with or without substitution; the difference is reachable only through the model function. A test MUST cover substitution into a `userMetadata` string value through `createResourceFromTemplate`. `inspectResourceTemplate` is unchanged and continues to report placeholders from `name` and `plainText` only. [US-2]

FR-6: `createResourceFromTemplate` MUST write the template's `resourceSubtype` (trimmed) into the created resource's persisted sidecar and onto the returned resource, in the same sidecar write as the rest (no second write), when the template has a valid one, and MUST write no key when it has none. The label MUST be written as recorded, without consulting `config.subtypes` and without editing the project's subtype list. The least invasive mechanism is required: `writeResourceToFile` MUST write `resourceSubtype` into the sidecar when the resource object it is given carries a non-empty one, and the template path MUST set it on the object after `createResourceOfType` returns. `createResourceOfType` MUST continue never to copy a request's `resourceSubtype`, so the app's blank create (`createResourceCore`) still cannot pick up a stray key (FR-23). Today neither function names the key (Verified, `resource-factory.ts` and `resource-persistence.ts`). The other callers of `writeResourceToFile` (Verified by grep: `project-creator.ts`, `trash.ts` for folders, the Scrivener, DOCX and plain-text importers, and `uploadMediaResourceCore`) build their resources through the factory, which never sets the key, and so are unaffected; one of them MUST be covered by a test that its sidecar still has no `resourceSubtype` (the existing `frontend/tests/unit/resource-persistence.test.ts` is the natural file), or the guarantee MUST be a type-level one. [US-1]

FR-7: A template whose recorded label is not in the destination project's subtype list MUST still create a resource carrying that label unchanged (the Feature 72 sidebar shows it as "(not in the current list)"). A test MUST create from such a template and assert the sidecar carries the label and `config.subtypes` in `project.json` is unchanged. It MUST NOT assert that `project.json` is byte-identical: every `writeSidecar` call runs `bumpMetadataRevision`, which rewrites `project.json` with `config.metadataRevision + 1` whenever the file exists (Verified, `sidecar.ts`). [US-1]

FR-8: A template whose `resourceSubtype` is present but not a trimmed non-empty string MUST be rejected by `createResourceFromTemplate` with an error naming the `resourceSubtype` field and the template id, and nothing MAY be written (Default accepted, RQ-3; `docs/standards/failure-visibility.md`; precedent `InvalidResourceSubtypeCoreError`). All validation (template, type, subtype, folder, schema parse) and all pre-write reads MUST complete before the first write (FR-33). A failure part-way through the write sequence is the same exposure `createResourceCore` has and is not widened or narrowed by this feature. [US-1]

FR-9: Dry run. `createResourceFromTemplate` with `dryRun: true` MUST write no file (as today, it still creates the empty `resources/` directory, which `resource-templates.test.ts` relies on; that is unchanged), MUST perform the same validation and pre-write reads as a real run (so a dry run that succeeds predicts a real run that succeeds), and MUST return `plannedWrites` whose paths are exactly the files a real text creation writes: `resources/<id>/content.tiptap.json`, `resources/<id>/content.txt`, `meta/resource-<id>.meta.json`, `revisions/<id>/v-1/content.bin` and `revisions/<id>/v-1/metadata.json` (five entries, replacing today's two). The sidecar entry's content MUST be the exact JSON a real creation writes for that resource, including `resourceSubtype`; to keep the dry-run sidecar identical to the real one, the sidecar-object construction currently inline in `writeResourceToFile` MUST be extracted into a pure function that both the real write and the dry run call. `metadata.json` MAY carry `null` content because it contains a generated id and timestamp. A test MUST assert that the set of planned paths equals the set of files a real creation produces, compared with the id normalised and covering only `resources/<id>/…`, `meta/resource-<id>.meta.json` and `revisions/<id>/…`; it MUST exclude `meta/index/*`, `meta/templates/*` and `project.json`, which a real creation also touches (indexing, template change records, the metadata-revision bump). `resourcePreview` MUST carry the subtype. The existing assertion that `plannedWrites` has length 2 (`resource-templates.test.ts`) MUST be changed deliberately to the new plan. [US-1]

FR-10: Side effects. Template creation MUST perform the same sidecar write as the app's create path (`writeResourceToFile` through `writeSidecar`, `sidecar.ts`), which enqueues background indexing in a `setImmediate` (Verified). This requirement makes no claim that background indexing completes under the shipped CLI. Read, not run: the CLI entry point calls `process.exit` when the command's promise resolves (`cli/src/getwrite-cli.ts`: `main(process.argv).then((code) => process.exit(code ?? 0))`), no CLI command calls `flushIndexer`, and `writeSidecar` enqueues indexing in a `setImmediate`; so a CLI-created resource is likely absent from search and mention results until its next save or a `reindex`, which is how `templates create` already behaves. The implementation MUST confirm or refute this by running the built CLI against a project and recording the result in the task list; the CLI documentation (`docs/features/cli.md`) MUST state that a resource created by `templates create` or `templates duplicate` may need `getwrite-cli reindex` to appear in search and mentions, with the pointer. Flushing the indexer in the command is NOT part of this feature (see "Out of scope (deferred)", adjacent findings). Template creation MUST NOT append a writing-log entry (Verified: `appendWritingLogEntry` is called only from `revision-core.ts` and the three importers, and `createResourceCore` logs nothing). It makes no change to `project.json` other than the `config.metadataRevision` bump that every sidecar write performs (Verified, `sidecar.ts`). Encrypted projects: the shipped `templates create` and `templates save-from-resource` keep refusing an encrypted project through `guardAgainstEncryptedProject`, and the model functions run inside the caller's storage context (`runForTenant`) and fail closed on locked access (FR-1). [US-2]

FR-11: Template creation supports text templates only (Default confirmed by the owner, Gate 3, 2026-10-08, RQ-7). `createResourceFromTemplate` MUST reject a template whose `type` is `image` or `audio` with an error naming the type and the template id, and MUST reject any `type` other than `text` that it does not recognise (an unknown or hand-edited value) explicitly, with an error naming the value. Today a type that is neither `text` nor `image` falls through to the audio branch (Verified by reading `resource-templates.ts`), which this requirement removes. Nothing MAY be written, and template creation MUST NOT keep writing an empty `.img` or `.aud` file beside a four-key sidecar (FR-3). Tests MUST cover an image template, an audio template and an unknown type. Basis (read, not run, except where stated): the shipped CLI cannot create a media template, because `templates save` hard-codes `type: "text"` (Verified), so this narrows only the model function; a media resource with no file shows the viewer's error state ("Unable to load image.") because the file route returns 404, and no path in the app attaches media to an existing resource (the audio player was not read). Image and audio remain supported for copy and duplicate (FR-20 to FR-22). [US-2]

FR-12: This feature fixes creation going forward only. It MUST NOT delete, rewrite or move any existing flat-layout file or minimal sidecar, and MUST NOT claim that a project already containing a resource made by the old path is repaired. Resources already created by the old template path are out of scope (Default confirmed by the owner, Gate 3, 2026-10-08, RQ-12). The documented workaround (FR-27) is to delete the stray `meta/resource-<id>.meta.json` and the flat `resources/<slug>-<id>.*` file. `doctor` cannot report such a resource, because it calls `getLocalResources` before it builds any report, and that call throws (Verified by reading `cli/src/commands/doctor.ts`). Likewise, text resources that already lack an initial canonical revision (copies and duplicates made before FR-28 and FR-29, and any other revision-less text resource) are NOT repaired by this feature: it fixes copy and duplicate going forward only, and neither heals, detects nor repairs an existing revision-less resource (RQ-15, Owner decision, Gate 3, 2026-10-08). The workaround, to be documented (FR-27): duplicate the resource again after the fix and work in the new copy, which gets its own initial canonical revision (FR-29 reads the source's content files, not its revisions, so a revision-less source can be duplicated). For a revision-less resource that is not a copy, there is no workaround in this feature. A repair command is deferred to a follow-up feature. [US-2][US-4]

FR-13: The `ResourceTemplate` interface (`resource-templates.ts`) and `ResourceTemplateSchema` (`schemas.ts`) MUST gain an optional top-level `resourceSubtype`: a trimmed non-empty string, the same rule as `ResourceBaseSchema`. A template with no subtype MUST NOT contain the key (absent, not `null` or `""`). A template saved before this feature MUST create a resource with no subtype, exactly as before, with no rewrite or migration of template files, and no fallback read of a label from `userMetadata.resourceSubtype` (Default accepted, RQ-4). The key name mirrors the sidecar key (Inference: a design choice). [US-1]

FR-14: `validateResourceTemplate` MUST report a template whose `resourceSubtype` is present but blank or not a string as invalid, naming the `resourceSubtype` path. [US-1]

FR-15: The shipped CLI MUST register `templates save-from-resource <projectRoot> <resourceId> <templateId> [--name <name>]` on the commander `templates` group in `cli/src/commands/templates.ts`, following `templates save`: `guardAgainstEncryptedProject` first (exit with its code), the work inside `runForTenant`, output `Saved template <templateId>` on success, and on any error `Error: <message>` to stderr with exit code 2 (Owner decision B). Like `templates save`, it overwrites an existing `<templateId>.json` without prompting (Verified: `saveResourceTemplate` overwrites and records a change entry). `templates create` MUST gain no new options and `templates` MUST gain no `--folder` option (Default confirmed by the owner, Gate 3, 2026-10-08, RQ-9). [US-3]

FR-16: `saveResourceTemplateFromResource` MUST record exactly these template keys: `id` (the argument), `name` (`--name`, else the source's name), `type` (the source's type, which must be `text`; FR-18), `plainText` (FR-17), `userMetadata` (the source sidecar's `userMetadata` object when it has at least one key, otherwise absent; an app-created text sidecar always has `userMetadata: {}`, so "absent when empty" means "has no keys"), and `resourceSubtype` (trimmed, when the source has a valid one). It MUST NOT record `folderId`, `orderIndex`, `slug`, `createdAt`, `wordCount`, `entityKind`, `aliases`, `wordCountGoal`, `dismissedNoiseTerms` or any other sidecar key, either at top level or inside `userMetadata`; and MUST NOT write the subtype inside `userMetadata` (Owner decision B). Today it spreads every sidecar key except `id` and `createdAt` into `userMetadata` (Verified, `resource-templates.ts`). The composed template MUST pass `ResourceTemplateSchema` before it is written. Known limitation, documented and not filtered: a source's `userMetadata` may contain `resource-ref` or `multi-resource-ref` values, which are ids of other resources in the source project. They are copied as recorded, and every resource created from the template carries them; no filter is added. [US-3]

FR-17: For a text source the body MUST be captured from the app's layout (`resources/<id>/content.txt`, read through `loadResourceContent`, defined in `frontend/src/lib/tiptap-utils.ts`). Today it looks only for a flat `resources/*<id>*` file and, for a directory, `readFile` throws and the `catch` leaves `plainText` undefined, so a template saved from an app-created text resource silently has no body (Verified by reading; not executed). `loadResourceContent` returns an empty object when both content files are missing and swallows non-locked read errors (Verified), so the caller MUST check explicitly: when the loaded body (`plainText`) is `undefined`, `save-from-resource` MUST fail with an error naming the resource, and MUST NOT write a template with an empty body (`docs/standards/failure-visibility.md`); a locked-access error MUST propagate. The body is captured as plain text only (`plainText`, the template shape's existing field; Default confirmed by the owner, Gate 3, 2026-10-08, RQ-11). The loss is, as read in `tiptapToPlainText` (`frontend/src/lib/tiptap-text.ts`; read, not run): paragraph breaks survive; marks (bold, italic), headings, lists and other structure are flattened; `hardBreak` (soft line break) nodes contribute no text, so the text on either side of one is joined; trailing blank paragraphs are dropped. This MUST be documented in `docs/features/cli.md`. [US-3]

FR-18: `save-from-resource` MUST fail, writing nothing, when: the resource has no sidecar (message names the resource id; Verified existing behaviour); the sidecar's `type` is not `text` (no silent default to text, which today's `(meta.type) ?? "text"` does); the source's `resourceSubtype` is present but not a trimmed non-empty string (error names the field and the resource id; Default accepted, RQ-3); the body cannot be read (FR-17); or the composed template is schema-invalid. An `image` or `audio` source MUST be rejected with an error naming the type and the resource id, and any other non-`text` type, including an unknown or hand-edited one, MUST be rejected explicitly with an error naming the value (RQ-7; consistent with FR-11). Tests MUST cover an image source, an audio source and an unknown type. [US-3]

FR-19: Round trip. A test MUST save a template from an app-created text resource that has a body, `userMetadata` and a subtype, create a resource from that template, and assert the new resource has the same `plainText` (as plain text; formatting is not preserved, FR-17), the same `userMetadata`, the same `resourceSubtype`, a new id and `createdAt`, and none of the source's name (unless `--name` kept it), `entityKind`, `aliases`, `wordCountGoal` or `dismissedNoiseTerms`. The consequence that a template now carries a resource's `userMetadata` onto every resource created from it is intended and follows from FR-5 and FR-16. [US-1][US-3]

FR-20: `copyResourceCore` MUST return and persist a sidecar whose `resourceSubtype` equals the source's, for text, image and audio sources, and a copy of a source with none MUST have none. Expected to need no code change for the subtype key (Verified by reading: it spreads `sourceSidecar` and overrides `id`, `name`, `createdAt`); satisfied by tests, and a code change is made only if a test fails. [US-1]

FR-21: The copy MUST keep the key end to end: tests MUST assert it in the HTTP response of `POST /api/resource/[resource-id]` with `action: "copy"` (no copy case exists in `tests/unit/resource-detail-route.test.ts`), in `native-resource-backend`'s `copy`, and after a parse through `ResourceResponseSchema` (`lib/api/schemas.ts`), which is expected to keep the key because `ResourceBaseSchema` declares it (Verified by reading; not executed). These three assertions MAY live in one test file. [US-1]

FR-22: `duplicateResource` MUST produce a sidecar whose `resourceSubtype` equals the source's (expected with no code change: `{ ...meta, id: newId }`), and the shipped `templates duplicate` MUST be covered by a test that asserts it, using an app-created source. This requirement guarantees the subtype only; the duplicate's revision is FR-29. [US-1]

FR-23: A resource created through the app's blank create path (`createResourceCore`) MUST have no `resourceSubtype`, including when the request carries a stray `resourceSubtype` key, which MUST NOT be honoured. This is a regression test only and is NOT a behaviour change: the path already ignores the key (Verified: `createResourceOfType` picks fields explicitly and persists no subtype). A second test MUST cover project-type `defaultResources` seeding (`project-creator.ts`). [US-1]

FR-24: `templates list` output MUST remain `<id>\t<name>\t<type>` and `templates` commands MUST add no output field for the subtype (Default accepted, RQ-2). [US-1]

FR-25: Model-level tests that already exist for the unbundled helpers (`parametrize`, export/import, version and rollback in `cli/src/templates.ts`) MAY stay, and where they touch templates they MAY assert that a top-level `resourceSubtype` survives (`parametrize` spreads `...tpl`; export and import write parsed JSON back whole).
