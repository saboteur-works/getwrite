## Overview

The query builder offers conditions whose saved form the evaluator does not evaluate as the label says. "Includes all of" returns the same resources as "includes any of". "In the last" and "is on" on a date return nothing for a resource created minutes earlier. The Tags value box offers resources instead of tags. The Status value list is empty in a project with no configured statuses, although the sidebar offers a built-in list. Each makes a smart folder or a one-off query return something other than what its label promises, with no error. This feature makes each condition return what its label says, reads existing saved "includes all of" folders correctly with no migration, reopens a saved "in the last" as "in the last", gives the sidebar, the query builder and the Organizer status filter one shared notion of the project's statuses, and adds a check that takes every condition the builder can produce and evaluates it, so a shape the evaluator does not handle fails a test. It adds no capability and no new control.

## Goals

- Every condition the query builder offers returns the resources its label says, shown by a test that evaluates each condition the builder can produce against fixtures.
- "Includes all of" returns only resources holding every listed value, including for smart folders already saved, with no migration, and a saved one reopens as "includes all of".
- "In the last" and "is on" on a date return the resources whose date falls in the span or on the day, with the span computed at each evaluation, and a saved "in the last" reopens as "in the last".
- The Tags value box offers the project's tags, and the Status value list, the sidebar Status control and the Organizer status filter read one shared list of the project's statuses.
- Every cause that is a HYPOTHESIS or a READ is tested before its fix, and the fix is shown to turn that test green.

## Non-goals

- The other handbook defects, including D-28 (the Organizer status filter with hand-set statuses and cards never given a status; owner decision OQ-93: out of scope) and the stale-save family described in `CLAUDE.md`'s "Resource subtype" entry.
- Any new query operator, field, control or feature flag, and any new route. The evaluate request gains no field: the client's time zone is not sent (OQ-2, resolved to option (d); sending it is a later follow-up).
- Sending the client's time zone with the evaluate request. Known limit: "is on" and any day boundary use the evaluating process's local zone, so on a hosted deployment, or on a paired device in another zone, the day is the server's. The model for the follow-up is the writing log's client-defined day (`frontend/src/lib/api/writing-log.ts`, `localDayWindow`, computed on the client and read, not run, by the author).
- Migrating or rewriting any saved smart folder (OQ-94). A saved query file is never written by this feature except when a writer saves one.
- Reconciling the query intrinsic `statuses` (`resource.statuses`) with the sidebar's `userMetadata.status`; they are disjoint today and this feature does not join them. The intrinsic "Statuses" field keeps its configured-only value list, unchanged (OQ-7, resolved).
- The Organizer's display of a card with no status in a project with no configured statuses: it stays `""`, unchanged; it goes with the D-28 follow-up (OQ-8, resolved).
- Changing how a resource with no status is stored or evaluated. The sidebar shows the first option for such a resource; nothing is written. A query `Status is Draft` does not match a resource with no stored status; that is the D-28 family and is left alone.
- Reopening "includes any of" or "includes none of" as those operators. Reading `astToGroups` shows `or[in]` reopens as a group with an "includes" chip (READ); the evaluated result is the same, FR-10 of the product spec is not violated by it, and it is not in the defect list.
- Editing the handbook pages (`docs/user/`); warnings these fixes make stale go to the scribe as a follow-up.
- Running the fixes on a physical Android device; native parity here is by shared code (FR-29).

## User stories

- US-1: As a writer on deadline, I want to have "includes all of" in a metadata query return only resources that hold every value I listed so that a smart folder for "scenes with both Alice and Bob" contains only those scenes. (Product spec US-7.)
- US-2: As a writer on deadline, I want to have "in the last 7 days" and "is on" a date return the resources changed in that span or on that day so that a smart folder of recent work is not empty. (Product spec US-7.)
- US-3: As a writer on deadline, I want to see my project's tags in the Tags value box so that I can build a tag condition without knowing a resource's name. (Product spec US-7.)
- US-4: As a writer on deadline, I want to see the same statuses for my project in the query builder, the sidebar and the Organizer filter so that a status I can set is a status I can query and filter. (Product spec US-7.)
- US-5: As a writer on deadline, I want to reopen a smart folder I saved earlier and see the condition I chose, and have it return the corrected result without my editing it so that I do not have to rebuild it. (Product spec US-7.)

## Functional requirements

For every field type in `OPERATORS_BY_TYPE` (`components/QueryBuilder/operator-utils.ts`: text, number, date, boolean, select, multiselect, resource-ref, multi-resource-ref) and every operator that type offers, the test builds a chip as the builder does, runs it through `groupsToAst`/`chipToAst` (`components/QueryBuilder/ast-chip-bridge.ts`), checks that the result parses against the `QueryAST` schema (`query-ast.ts`), evaluates it with `evaluate` (`query-evaluator.ts`) against fixture resources and sidecars, and compares the returned ids with an expected set written by hand from the operator's label. A shape the evaluator throws on or answers differently from the label MUST fail the test. The intrinsic date fields the picker offers (`createdAt`, `updatedAt`) are covered with a fixed evaluation time and a fixed time zone (FR-13, FR-14). [US-1]

FR-12: The evaluator MUST evaluate a `gte` whose value is a relative-date object as "the field's date falls in the span from (evaluation time minus the span) to the evaluation time". The upper bound is the evaluation time, so a date after it (for example a hand-set 2099 date) does not match (product spec FR-10: "within that span ending at the time of evaluation"). A resource whose field is absent, null or not a parseable date MUST NOT match, and MUST NOT throw. A relative-date object with a unit outside the three, or an amount that is not an integer of at least 1, MUST throw an error naming the problem and MUST NOT silently match nothing (`docs/standards/failure-visibility.md`); the builder does not offer such a value, so this is unreachable from the UI. The ordinary `gte` on numbers and strings MUST be unchanged. [US-2]

FR-13: The span is computed each time the query or smart folder is evaluated, from the evaluating process's clock. "Is on" and any day boundary use the evaluating process's local time zone (OQ-2, resolved to option (d)); the client's zone is not sent. Known limit: on a hosted deployment, or a paired device in another zone, the day is the server's. Tests MUST fix the zone (for example a `TZ` environment variable in the test run, or an injectable zone) so they do not depend on the machine running them. Evaluation runs in `executeEvaluate` (`query-evaluate-core.ts`), called by `app/api/project/query/evaluate/route.ts` and by the native backend in-process (READ: `store/query-transport-service.ts`, `store/transport/native-query-backend.ts`), so one change in `query-evaluator.ts` covers both paths; there is no client-side evaluation. `EvaluationInput` MUST gain an optional evaluation time (default: the current time) so tests fix it; no other caller changes. [US-2]

FR-14: The span is rolling (OQ-3, resolved to option (a)): a day is 24 hours, a week is 7 days, and a month is a calendar month counted back from the evaluation time with the day clamped to the month's end (1 month before 31 March is 28 or 29 February); the span ends at the evaluation time. "1 day" means the last 24 hours, not "since local midnight" (owner confirmed). Tests MUST cover, with a fixed evaluation time and zone, at least the handbook's cases (1 day, 7 days, 1 week, 1 month) with a resource just inside and just outside each boundary, and a month span started on the 29th, 30th or 31st. [US-2]

## Open questions

- OQ-1: What shape should a new save of "includes all of" use, and how does reopening map it back? - OQ-2: In which time zone is "is on" a calendar day, and where do day-based span boundaries fall? Cons: on a hosted deployment, or a paired device whose zone differs from the desktop's, "today" is the server's today. Option (b): UTC always. - OQ-3: How is "in the last <amount> <unit>" measured?
