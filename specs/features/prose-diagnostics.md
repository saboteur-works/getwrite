# Feature: Prose diagnostics

**Scope note:** This document runs well over the 500-word guidance in `saboteur-write-feature-spec`. The overrun is carried by the required Transport investigation note (evidence trail for a "verified, not an open question" claim, per this repo's measurement-before-cause rule) and, as of this amendment, by the propagation of all seven open questions — resolved at Gate 3 by the user ("take your recs"), 2026-09-27 — into the FR text they affect, none of which could be shortened without dropping required detail.

## Overview

A writer on deadline has no way to see cheap, automatic observations about a resource's prose — how much of it is dialogue, how long its sentences run, which words repeat too often — without leaving the app or reaching for an external tool. This feature adds three per-resource scalar metrics (dialogue ratio, average sentence length, top repeated words), computed with no AI or network dependency, persisted alongside the existing indexer output, plus an on-demand, unpersisted "located detail" view (exact repeated phrases and their character positions) for a writer who wants to act on a flag rather than just see it.

Parent: `specs/product/getwrite.md` FR-49, FR-50, US-22; `specs/product/getwrite.features.md` Feature 62. Evidence for the sync-vs-async design decision below comes from Feature 63's closed benchmark, carried in FR-49's text.

## Goals

- A writer can see, per resource, dialogue ratio, average sentence length, and top repeated words with no AI or network call.
- A writer can request located detail (exact repeated phrases and positions) for a resource on demand, without that detail ever being persisted.
- Diagnostic output reads as neutral observation, never as an error or a red warning.
- Persisted metrics survive a heuristic change without going stale, via a versioned rebuild.
- The feature behaves identically on web/desktop and native (Capacitor).

## Non-goals

- No AI or network dependency of any kind (FR-49 constraint).
- Finalizing user-facing copy for the diagnostics sidebar section and its detail dialog is out of scope for this spec; the strings referenced in FR-1 are working copy, not yet user-confirmed, mirroring how Features 60/61 handled unconfirmed copy strings.
- No change to the existing mention index, backlinks, or entity layer.
- No change to Feature 60's status roll-up or Feature 59's writing log.
- No aggregation of diagnostics across resources (e.g. a project-wide diagnostics roll-up).
- No backfill of diagnostics for resources saved before this feature ships; metrics compute lazily (on first read after a version mismatch, or at next save).

## User stories

- US-1: As a writer on deadline, I want to see cheap prose diagnostics for each resource so that I can spot dialogue-heavy passages, run-on sentences, and overused words without leaving the app. [US-22]

## Functional requirements

- FR-1: The product MUST compute three per-resource scalar metrics — dialogue ratio, average sentence length, and top repeated words — with no AI or network dependency, and MUST surface them read-only, for text resources only, in a new collapsible section in `MetadataSidebar.tsx`, styled like the existing read-only computed-data sections (`ImageMetadataSection.tsx`/`AudioMetadataSection.tsx`), not like the goal-setting `WordCountGoalSection.tsx`. That section MUST include a "show detail" action opening a dialog (mirroring `WritingLogDetailsDialog.tsx`'s loading/error/ready pattern, per FR-7/FR-8) for the on-demand located-detail view (FR-5), analogous to how `EntityMentionsSection.tsx` sits beside `CompilePreviewModal.tsx`'s trigger in the same file. Exact copy for the section and dialog is working copy, not yet user-confirmed, mirroring how Features 60/61 handled unconfirmed copy strings. The real (non-throwaway) sentence-splitting and dialogue-detection algorithms MUST adopt the benchmark's stand-in regex approach as-is (`text.split(/[.!?]+\s+/)` for sentences; quoted-span matching for dialogue) rather than a more sophisticated detector — a more careful detector (handling abbreviations, em-dashes, nested quotes) is deferred as a future improvement requiring its own benchmark pass before FR-2's synchronous-safety claim could extend to it (see Out of scope). Known blind spots of this approach (e.g. "Mr." falsely ending a sentence, em-dash dialogue tags going undetected) MUST be documented as a stated limitation in the feature's UI copy, not silently accepted. [US-1]
- FR-2: The three scalar metrics MUST be computed together, in one indexer task, synchronously at save time inside the existing indexer path (`indexer-queue.ts`'s `runTask`), not moved to an async/background queue. This is a settled design decision, not an open question: Feature 63's benchmark measured the combined cost of all three metrics together (not summed from individual costs) at 0.128 ms / 1.256 ms / 12.892 ms for 1k / 10k / 100k words (median of 7 runs), and since the worst-measured combined cost is small relative to typical background-queue work and human-imperceptible even if it did block, computing synchronously is judged safe at the measured sizes. Per FR-1's resolution of the sentence/dialogue-detection question, the real implementation adopts the benchmark's own stand-in algorithms rather than a different one, so this finding now extends to the feature's real algorithms and is no longer scoped only to throwaway stand-ins (FR-49). [US-1]
- FR-3: The three scalar metrics MUST be persisted through the existing indexer's storage path, in a diagnostics index validated in `schemas.ts`, stored as one project-wide file keyed by `resourceId` (analogous to `meta/index/mentions.json`, e.g. `meta/index/diagnostics.json`), not as a per-resource sidecar field. Each persisted metric set MUST carry a `heuristicVersion` field and MUST be recomputed and re-persisted unconditionally at every save, inside the same indexer task that rebuilds the mention index (`indexer-queue.ts`'s per-save mention-detection block is the direct precedent), and MUST additionally be rebuilt lazily on read when the stored `heuristicVersion` does not match the current one. Top repeated words MUST use a fixed top-N of 10 with a minimum-occurrence floor of at least 3 occurrences to qualify (both working-copy values, not yet user-confirmed) to avoid noise on short/stub resources, and MUST reuse the existing `STOP_WORDS` set and `tokenize()` function from `inverted-index.ts` rather than inventing new filtering. [US-1]
- FR-4: The diagnostics index MUST be persisted and read through the storage adapter (`io.ts`) and MUST fail closed when the project is locked or keyless, via `isLockedAccessError`, per the mention index's existing precedent (`mention-index.ts`'s `loadMentionIndex`: a locked-access error is rethrown, never degraded to an empty/default result), inheriting that same lock-handling pattern in one place consistent with FR-3's project-wide, keyed-by-`resourceId` file shape. No silent skip. [US-1]
- FR-5: Located detail (exact repeated phrases and their character positions within a resource) MUST be computed on demand and MUST NOT be persisted anywhere. That computation MUST read the resource's persisted plain text from disk — the same source the scalar-metrics index reads — rather than the client's live/unsaved editing buffer, so that located-detail character offsets never drift from what the persisted scalar-metrics index was computed against. On web/desktop this runs through FR-8's HTTP route; on native it runs in-process via the same core, per the `createTransport` pattern. [US-1]
- FR-6: Every diagnostic flag presented in the UI MUST read as a neutral observation, not an error, and MUST NOT use the red color token, matching FR-49's constraint and the codebase-wide rule that red is reserved for position/canonical-state indicators. [US-1]
- FR-7: This feature MUST add a new per-resource read transport for the persisted scalar metrics (`GET`-shaped, analogous to `resource/[resource-id]/mentions`), resolved through `createTransport` with an HTTP implementation, a native in-process backend, a web-stub, and HTTP response-body validation via a new Zod schema in `lib/api/schemas.ts`, per FR-50. The UI consuming this transport (FR-1's sidebar section) MUST use a discriminated `loading | error | ready` state, mirroring `WritingLogDetailsDialog.tsx` exactly, since this data is fetched via a genuinely new async transport and is not synchronously available at mount the way Feature 60's status roll-up is — Feature 60's "structurally unreachable, no loading/error branches" shortcut MUST NOT be applied here. See the Transport investigation note below for why a new transport, rather than an existing one, is required. [US-1]
- FR-8: This feature MUST add a second new transport, of the same shape as FR-7, for the on-demand located-detail computation, since FR-5 requires that computation to run somewhere the persisted index does not reach it: on web/desktop through this transport's own HTTP route reading the resource's persisted plain text from disk (per FR-5); on native, in-process via the same core. The dialog consuming this transport (FR-1's "show detail" action) MUST use the same discriminated `loading | error | ready` state as FR-7, mirroring `WritingLogDetailsDialog.tsx`. [US-1]

### Transport investigation (verified, not an open question)

Verified by reading `frontend/src/lib/models/mention-index.ts`, `frontend/app/api/resource/[resource-id]/mentions/route.ts`, `frontend/src/lib/api/mentions.ts`, and `frontend/src/store/transport/native-mentions-backend.ts`: the closest existing precedent — the mention index — is *not* read by riding some other, already-existing bulk transport. Despite `mentions-core.ts` being usable in bulk internally, the client only ever reaches a resource's mentions through a dedicated new route (`GET /api/resource/:resourceId/mentions`), a dedicated `MentionsTransport` interface, and a dedicated native backend (`native-mentions-backend.ts`) resolving the same `mentions-core.ts` functions in-process. No existing per-resource metadata read (sidecar fetch, resource content fetch, or the bulk project-resources load) carries mention data piggybacked onto it. A per-resource persisted index that the client needs to read on demand has, in this codebase, always meant a new route/transport pair, never a free ride on an existing one — Feature 61's own transport check (word-count goals) found the same thing for its resource-goal write path. This feature's persisted diagnostics index is the same shape (a new per-resource derived index, `meta/index/diagnostics.json`-analogous), so it needs its own new transport (FR-7), which FR-50 already requires to follow `createTransport`. This is stated as verified fact, not an open question.

- OQ-3: What counts as a "sentence" and as "dialogue" for the real (non-throwaway) implementations of average sentence length and dialogue ratio. **Resolved at Gate 3 by the user ("take your recs"), 2026-09-27:** the real algorithm adopts the benchmark's stand-in regex approach as-is (`text.split(/[.!?]+\s+/)` for sentences, quoted-span matching for dialogue) rather than a more sophisticated detector, because Feature 63's benchmark evidence (and FR-2's "safe to compute synchronously" finding) covers only that algorithm's cost — a more careful detector (abbreviations, em-dashes, nested quotes) is deferred as a future improvement requiring its own benchmark pass before FR-2's synchronous-safety claim could extend to it (see Out of scope). - OQ-7: Loading, error, and empty states for the diagnostics display. **Resolved at Gate 3 by the user ("take your recs"), 2026-09-27:** the diagnostics section/dialog uses a discriminated `loading | error | ready` state, mirroring `WritingLogDetailsDialog.tsx` exactly, since this feature's data is fetched via a genuinely new async transport (FR-7/FR-8) and is not synchronously available at mount the way Feature 60's status roll-up is — Feature 60's "structurally unreachable, no loading/error branches" shortcut is not applied here. — Impact: FR-1, FR-4, FR-7, FR-8.

## Out of scope (deferred)

- Any AI-assisted or network-dependent prose analysis.
- A project-wide diagnostics roll-up or aggregation view.
- Backfilling diagnostics for resources that predate this feature.
- Changes to the mention index, backlinks, entity layer, writing log (Feature 59), or status roll-up (Feature 60).
- A more sophisticated sentence/dialogue detector (handling abbreviations, em-dashes, nested quotes) beyond the benchmark's stand-in regex approach adopted by FR-1/OQ-3 — deferred pending its own benchmark pass to establish whether FR-2's synchronous-safety finding still holds at that cost.
- Finalizing the working-copy UI strings and the working-copy top-N/minimum-occurrence numbers (FR-1, FR-3) — left for user confirmation outside this spec.
