## Lock order

Today (READ): `writeSidecar` holds the meta lock and, inside it, bumps `project.json` (`sidecar.ts:174-181`). Family C and D hold `acquireLock(projectRoot)` across the read, mutate and write; family C releases it before any sidecar is rewritten (`metadata-schema.ts:975-979`, `:1008-1014`, `:1122-1126`, `clearField` `:603-604`). No path found takes `acquireLock(projectRoot)` and `withMetaLock(projectRoot)` together. The two locks are unrelated, which is why family A/B and family C/D lost updates against each other.

The problem with the obvious fix. If `updateProjectJson` keeps `withMetaLock(projectRoot)`, `bumpMetadataRevision` (already inside `withMetaLock`, `sidecar.ts:174-180`) cannot call it: a nested call for the same key waits on itself. If family C takes `withMetaLock` while holding `acquireLock`, that creates the edge `acquireLock -> withMetaLock`; any path that takes `withMetaLock` and then `acquireLock(projectRoot)` would deadlock against it. None exists today (READ), but nothing prevents one being added.

The rule this spec requires: a dedicated `project.json` lock (call it L3, keyed by the project root) that is always the innermost lock. It is held only for the read, mutate and write of `project.json`; nothing inside it acquires L3 again or any other lock (`withMetaLock`, `acquireLock`, or any future one). Every other lock may be held when L3 is taken: the permitted edges are `withMetaLock -> L3` and `acquireLock(*) -> L3`, and no edge leaves L3. With one sink and no edges out, no cycle can contain L3, and the existing locks keep the relationships they have today. How the rule is enforced (a test, a runtime guard, or both) is OQ-1 and OQ-5.

## Overview

A writer who changes several project settings in quick succession, or whose editor settings save at the same moment as a metadata-field change, can lose one of the changes without any message, because project settings live in one file and the several kinds of save that rewrite it do not wait for one another. On 2026-10-23 an editor-settings save run against a new metadata field lost the field in 20 of 20 repetitions in each of 9 runs. This feature makes every save that rewrites `project.json` wait its turn, reading the file only once it has its turn, so that none of the overlapping changes is dropped and the project still opens. It does not change what any single save does, how fast one runs when nothing else is saving, or what it reports when it fails.

## Goals

- Two saves to the same project's `project.json` that overlap, from any two of the writer families, both end up in the file, and the file parses.
- Every writer's read of `project.json` that a write is based on happens while it holds the lock it writes under.
- No combination of concurrent operations from the families A to E waits forever; the lock order is stated, and a violation of it is caught by a test rather than by a hung save.
- A single save behaves exactly as before: same stored result, same return value, same errors reaching the caller, no new timeout.
- It is recorded, with a measurement, whether sidecars need the same treatment, and whether any writer reads `project.json` in one request and writes it in a later one.

## Non-goals

- Sidecars, `meta/index/*`, `backlinks.json`, `relationships.json`, writing-log files and any other file under `meta/`. They are unknown, not promised (OQ-110). They change only if Task 1's experiment reproduces a lost update.
- More than one server process. Hosted multi-instance coordination (ADR-017, ADR-019).
- A time limit on waiting for the lock, a retry, or a "could not save" message for a waiting write (OQ-112).
- Changing the other `withMetaLock` users that do not write `project.json`.
- Moving the sidecar migrations in family C (which run after the schema write, outside the schema lock) under any lock.

## User stories

- US-1: As a writer on deadline who changes more than one project setting in quick succession, or whose editor settings save at the moment another setting is saved, I want to have every one of those changes kept and my project still open afterwards, so that I do not find a setting I changed has silently reverted or that the project no longer loads. (Product US-31.)

## Open questions

Local numbers start from 1 (the checker requires a sequence from 1); the product spec's OQ-110 to OQ-114 are resolved and are not repeated. All eight were resolved by the owner at Gate 3 on 2026-10-23; the resolution is appended to each.

- OQ-1: Which mechanism provides the `project.json` lock? READ: `withMetaLock` is a promise chain keyed by the raw string (`meta-locks.ts:16-28`) and `acquireLock` is a FIFO queue mutex (`locks.ts:62-73`); both are not reentrant, and neither knows about the other. Options: (a) `acquireLock` on a key such as `project-json:<root>` in a new helper that `updateProjectJson` and the other writers call (simple, a queue, fair; shares the `queues` map with other `acquireLock` keys); (b) `withMetaLock` on the same kind of prefixed key (reuses the code `updateProjectJson` already runs on, but `withMetaLock` is documented as the metadata serializer and a prefixed key makes it easy to confuse with the real one); (c) a new small primitive with its own map and, optionally, the guard of OQ-5. The code does not settle it; (a) and (c) both satisfy FR-8. — Impact: FR-1, FR-8, FR-9. **Resolved (Owner decision, Gate 3, 2026-10-23; option c):** A small new primitive in its own module owns the `project.json` lock: callback form only, never exposes a release, its own key map, keyed by `path.resolve(root)`. It is the single sink for `project.json` read-mutate-write, and `updateProjectJson` is built on it. Applied in FR-1, FR-8.
- OQ-2: Must the lock key be normalised? READ: `withMetaLock` keys by the string it is given; `revision-core.ts:445-447` keys its lock with `path.resolve(projectRoot)`. `revision-settings.ts:30` passes a variable named `projectPath` as the first argument of `updateProjectJson`; whether it is always the project root was not read to its caller. Two spellings of one root (trailing slash, relative path, symlink) would get two locks and bring the lost update back. Options: (a) key by `path.resolve(root)`; (b) key by `fs.realpath` (resolves symlinks, costs a call per save); (c) key as given and add a test that every caller passes the same string. — Impact: FR-1, FR-7, FR-11. **Resolved (Owner decision, Gate 3, 2026-10-23; resolved from evidence, confirmed):** keys already match for the same project within a process; the helper normalises with `path.resolve(root)` as insurance; no `realpath`. Applied in FR-1.
- OQ-3: Do family C and D keep their outer `acquireLock(projectRoot)`? READ: no other module uses `acquireLock(projectRoot)` with the bare root as the key (`grep`: `revision-core.ts:445` and `revision-manager.ts:39` use other keys), so for the `project.json` sections it excludes only other family C and D operations, which the new lock would now exclude too. Options: (a) remove it and take only the new lock (fewer locks, the order rule is trivially met); (b) keep it as the outer lock and take the new lock inside around the read-mutate-write (changes nothing about when schema operations wait for one another, adds the edge `acquireLock -> project.json lock`). — Impact: FR-4, FR-5, FR-8, FR-12. **Resolved (Owner decision, Gate 3, 2026-10-23; option b):** `metadata-schema.ts` and `project-features.ts` keep their outer `acquireLock(projectRoot)`. The allowed lock edges become `acquireLock(projectRoot) -> project.json lock` and `withMetaLock -> project.json lock`; the `project.json` lock stays innermost. Applied in FR-4, FR-5, FR-8.
- OQ-4: Is `crypto/convert-project.ts` an overlapping writer of `project.json`? Found by `grep` only: it rewrites every file of a project in place (`:223`, `:266`) and no lock appears in the module.
