## Lock order

Today (READ): `writeSidecar` holds the meta lock and, inside it, bumps `project.json` (`sidecar.ts:174-181`). Family C and D hold `acquireLock(projectRoot)` across the read, mutate and write; family C releases it before any sidecar is rewritten (`metadata-schema.ts:975-979`, `:1008-1014`, `:1122-1126`, `clearField` `:603-604`). No path found takes `acquireLock(projectRoot)` and `withMetaLock(projectRoot)` together. The two locks are unrelated, which is why family A/B and family C/D lost updates against each other.

Revised (Owner decision, Gate 5, 2026-10-23): the lock becomes a per-file lock (OQ-1 revised), one key per file path, used for `project.json` and for each sidecar. Today (READ) `writeSidecar` holds `withMetaLock(projectRoot)` and does the sidecar write and the `project.json` bump inside it (`sidecar.ts:174-181`); `updateRevisionInPlace` holds `acquireLock("revision-content:...")` across its whole body, which includes `writeSidecar`, so the edge `acquireLock(revision-content) -> withMetaLock` already exists (READ, `revision-core.ts:445-447`, `:519`). Whether any path takes `withMetaLock` and then a `revision-content:` `acquireLock` (the reverse edge) was not searched; the deadlock test (FR-12) exercises it. The sidecar writers' two files, `project.json` and the sidecar, are different keys; the design that keeps them from nesting is in FR-20.

The problem with the obvious fix. If `updateProjectJson` keeps `withMetaLock(projectRoot)`, `bumpMetadataRevision` (already inside `withMetaLock`, `sidecar.ts:174-180`) cannot call it: a nested call for the same key waits on itself. If family C takes `withMetaLock` while holding `acquireLock`, that creates the edge `acquireLock -> withMetaLock`; any path that takes `withMetaLock` and then `acquireLock(projectRoot)` would deadlock against it. None exists today (READ), but nothing prevents one being added.

The rule this spec requires: a dedicated per-file lock (call it L3, keyed by the resolved path of the file: `project.json` for the project file, `meta/resource-<id>.meta.json` for a sidecar) that is always the innermost lock. It is held only for the read, mutate and write of that one file; nothing inside it acquires L3 again, for the same file or another, or any other lock (`withMetaLock`, `acquireLock`, or any future one). Every other lock may be held when L3 is taken: the permitted edges are `withMetaLock -> L3`, `acquireLock(*) -> L3` (including the `revision-content:` keys and `acquireLock(projectRoot)`), and the existing edge `acquireLock(revision-content) -> withMetaLock` is unchanged; no edge leaves L3, so there is no L3-to-L3 edge between two different files either. With one sink and no edges out, no cycle can contain L3, and the existing locks keep the relationships they have today. Revised at Gate 5 from "keyed by the project root". How the rule is enforced (a test, a runtime guard, or both) is OQ-1 and OQ-5.

## Overview

A writer who changes several project settings in quick succession, or whose editor settings save at the same moment as a metadata-field change, can lose one of the changes without any message, because project settings live in one file and the several kinds of save that rewrite it do not wait for one another. On 2026-10-23 an editor-settings save run against a new metadata field lost the field in 20 of 20 repetitions in each of 9 runs. This feature makes every save that rewrites `project.json` wait its turn, reading the file only once it has its turn, so that none of the overlapping changes is dropped and the project still opens. Revised (Owner decision, Gate 5, 2026-10-23): the same holds for each resource's metadata file (its sidecar): on 2026-10-23 a metadata save run against an autosave of the same resource lost a change in 41 of 100 repetitions, and against the removal of a metadata field in 10 of 100. It does not change what any single save does, how fast one runs when nothing else is saving, or what it reports when it fails.

## Goals

- Two saves to the same file, `project.json` or one resource's sidecar, that overlap, from any two of the writer families, both end up in the file, and the file parses.
- Every writer's read of `project.json` or of a sidecar that a write is based on happens while it holds the lock it writes under.
- No combination of concurrent operations from the families A to E and S1 to S4 waits forever; the lock order is stated, and a violation of it is caught by a test rather than by a hung save.
- A single save behaves exactly as before: same stored result, same return value, same errors reaching the caller, no new timeout.
- It is recorded, with a measurement, that sidecars needed the same treatment (done: Task 2), and whether any writer reads `project.json` or a sidecar in one request and writes it in a later one.

## Non-goals

- `meta/index/*`, `backlinks.json`, `relationships.json`, writing-log files and any other file under `meta/` other than resource sidecars. They are unknown, not promised (OQ-110). (Revised at Gate 5: sidecars were in this list; Task 2's experiment reproduced a lost update and they are now in scope.)
- Moving or renaming a sidecar (trash, restore) under the sidecar lock (OQ-10, option a: left unlocked; recorded as a follow-up).
- Fixing a stale whole-object client write over a correct lock (OQ-9, option a: recorded as a follow-up; values a client sends are stored as sent).
- More than one server process. Hosted multi-instance coordination (ADR-017, ADR-019).
- A time limit on waiting for the lock, a retry, or a "could not save" message for a waiting write (OQ-112).
- Changing the other `withMetaLock` users that do not write `project.json`.
- Moving the sidecar migrations in family C (which run after the schema write, outside the schema lock) under any project-wide lock. (Revised at Gate 5: each sidecar they rewrite takes that sidecar's own lock for its read-modify-write, one sidecar at a time; no lock spans the sweep.)

## User stories

- US-1: As a writer on deadline who changes more than one project setting in quick succession, or whose editor settings save at the moment another setting is saved, I want to have every one of those changes kept and my project still open afterwards, so that I do not find a setting I changed has silently reverted or that the project no longer loads. (Product US-31.) Revised (Owner decision, Gate 5, 2026-10-23): "setting" includes a resource's metadata, so a metadata edit made while that resource autosaves, or while a metadata field is removed, is kept together with the other change. Narrowed (Owner decision, Gate 5 re-gate, 2026-10-23; OQ-9 option a): for metadata, two metadata saves read and write the file in order; values a client sends are stored as sent. A save that carries an older copy of a value, for example an older `updatedAt`, stores that value; that case is a recorded follow-up, not a promise of this feature.

FR-1: Every read-modify-write of a project's `project.json` in families A to E MUST run through one `project.json` lock per project root, shaped like `updateProjectJson` (read, mutate, atomic write, all inside the lock), and two such operations on the same root MUST NOT overlap. The lock is a small new primitive in its own module: callback form only (it never exposes a release), its own key map (shared with neither `withMetaLock` nor `acquireLock`), keyed by `path.resolve(root)`, with no `realpath`. That primitive is the single sink for `project.json` read-mutate-write, and `updateProjectJson` is built on it. Revised (Owner decision, Gate 5, 2026-10-23): the primitive is a per-file lock, not a per-project one: one key per file, `path.resolve(filePath)`, still no `realpath`, still callback-only, with its own key map. The `project.json` key is the resolved path of that project's `project.json` (equivalent to the earlier per-root key), and each resource sidecar uses the resolved path of its own `meta/resource-<id>.meta.json` (FR-19). A key entry MUST be removed from the map when no call is waiting on it, so the map does not grow with the number of files touched. The module name is decided from `frontend/src/lib/` conventions (it is no longer `project-json-lock`). [US-1] (Applied from OQ-1, OQ-2; revised from OQ-1 at Gate 5.)

- OQ-1: Which mechanism provides the `project.json` lock? READ: `withMetaLock` is a promise chain keyed by the raw string (`meta-locks.ts:16-28`) and `acquireLock` is a FIFO queue mutex (`locks.ts:62-73`); both are not reentrant, and neither knows about the other. Options: (a) `acquireLock` on a key such as `project-json:<root>` in a new helper that `updateProjectJson` and the other writers call (simple, a queue, fair; shares the `queues` map with other `acquireLock` keys); (b) `withMetaLock` on the same kind of prefixed key (reuses the code `updateProjectJson` already runs on, but `withMetaLock` is documented as the metadata serializer and a prefixed key makes it easy to confuse with the real one); (c) a new small primitive with its own map and, optionally, the guard of OQ-5. The code does not settle it; (a) and (c) both satisfy FR-8. — Impact: FR-1, FR-8, FR-9. **Resolved (Owner decision, Gate 3, 2026-10-23; option c):** A small new primitive in its own module owns the `project.json` lock: callback form only, never exposes a release, its own key map, keyed by `path.resolve(root)`. It is the single sink for `project.json` read-mutate-write, and `updateProjectJson` is built on it. Applied in FR-1, FR-8. **Revised (Owner decision, Gate 5, 2026-10-23; option 2, scope expanded to sidecars):** option (c) stands, with the primitive made per-file: one key per file path (`path.resolve(filePath)`), used for `project.json` and for each sidecar, callback-only, innermost, nothing acquired while it is held. Applied in FR-1, FR-8, FR-19, FR-20.
- OQ-2: Must the lock key be normalised? READ: `withMetaLock` keys by the string it is given; `revision-core.ts:445-447` keys its lock with `path.resolve(projectRoot)`. `revision-settings.ts:30` passes a variable named `projectPath` as the first argument of `updateProjectJson`; whether it is always the project root was not read to its caller. Two spellings of one root (trailing slash, relative path, symlink) would get two locks and bring the lost update back. Options: (a) key by `path.resolve(root)`; (b) key by `fs.realpath` (resolves symlinks, costs a call per save); (c) key as given and add a test that every caller passes the same string. — Impact: FR-1, FR-7, FR-11. **Resolved (Owner decision, Gate 3, 2026-10-23; resolved from evidence, confirmed):** keys already match for the same project within a process; the helper normalises with `path.resolve(root)` as insurance; no `realpath`. Applied in FR-1. **Revised (Owner decision, Gate 5, 2026-10-23):** the same rule, `path.resolve` and no `realpath`, now applies to the key of each file (the sidecar's own path), not to the project root. Two spellings of one project root still resolve to one `project.json` path; a symlinked project root remains unhandled by design. Applied in FR-1.
