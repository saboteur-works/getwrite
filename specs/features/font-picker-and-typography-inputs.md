## Overview

A writer choosing a font for headings, body text or the toolbar gets a text field whose suggestion list shows only the value already set, fonts that load from Google Fonts over the network (so they fail offline and on a locked-down network), a project font that does not render in the editor unless the same font is also picked in the toolbar, IBM Plex families that render only where installed, and, in the Project Type Manager, free-text typography fields the writer must type correctly. The Colour box and Font Weight select in Project Settings are reported to differ in height from their neighbours. This feature ships the named fonts with the app, replaces every font-family input with one dropdown that always lists every font GetWrite can render, plus an "Other..." entry in the settings forms (the editor toolbar omits it, FR-10), moves the typography inputs into one component used by Project Settings and the Project Type Manager, and makes controls in one row the same height.

## Goals

- Every font in the fixed list renders with no network access and with no request to Google Fonts or any font host.
- Every font-family input (Project Settings headings and body, Project Type Manager headings and body, the editor toolbar) offers the same full list at all times, and "Other..." in the settings forms accepts any allowed name with a fixed hint.
- A font chosen in Project Settings or a project type shows in the editor without also being chosen in the toolbar.
- Project Settings' Editor tab and the Project Type Manager use one typography component, with the 1.8 line-height floor.
- Inputs in one Editor-tab row have equal rendered heights, and the added size of the bundled fonts is recorded for web, Electron and native.

## Non-goals

- Enumerating installed fonts, detecting whether a font is installed, or per-platform font lists.
- An in-app Licences view (a later follow-up); the licence ships as a file only.
- Fonts beyond the list above, other scripts (Cyrillic, Greek, Vietnamese, CJK), weights not already in use, and font upload by the writer.
- Rewriting stored font values (an unlisted value stays as stored).
- A size budget for the bundled fonts.
- Changing heading line heights, adding a heading line-height field, or changing the stored editor config shape (OQ-4, resolved).
- Changing UI-chrome fonts: IBM Plex Serif stays editor-only (STYLING.md).

## User stories

- US-1: As a novelist who tunes project types, I want to get from the Project Type Manager the same font, size, weight, colour, spacing and line-height inputs as Project Settings, so that I pick values instead of typing them correctly. (Product spec US-1.)
- US-2: As a writer, I want to see every font I can use whenever I open a font control, so that I choose by looking instead of by remembering a name. (Product spec US-9.)
- US-3: As a writer who works offline, I want to have the fonts be part of the app, so that my headings and body look the same with no network and on every device. (Product spec US-9.)
- US-4: As a writer who types a font that is not in the list, I want to be told what shows if it is not installed, so that I am not surprised by the fallback. (Product spec US-9.)

FR-9: In the settings forms, choosing "Other..." MUST reveal a text field for the font name. A name typed there MUST be stored as typed (trimmed) and applied with the quoted stack ("<Name>", "IBM Plex Serif", serif) wherever it is rendered (editor text and the Project Settings previews; the Project Type Manager has no preview, FR-12), and accompanied by the fixed hint "If this font isn't installed on this device, text shows in IBM Plex Serif." linked to the field with `aria-describedby` and shown whenever the field is shown. Every font-family declaration (the editor body variable, the heading style attribute, and the previews) MUST be built through one pure, validated helper that returns the quoted fallback stack ("<Name>", "IBM Plex Serif", serif) for a name, a generic family as its bare keyword, and a stored comma value as stored; no call site concatenates a family string itself (a test over the source tree asserts the call sites use the helper, and a unit test covers the helper, including "Source Serif 4", per the READ finding that today's unquoted application is not valid for a name beginning with a digit; OQ-6). ## Open questions

Resolved at Gate 3 (2026-10-21); each resolved question below carries its resolution. OQ-10 was added at Gate 3 (a conflict found in the weights) and resolved the same day; OQ-11 was raised by the OQ-5 answer and resolved the same day.

- OQ-1: Does the toolbar's Google-font loader (`frontend/src/lib/fonts/loadGoogleFont.ts`) go entirely, or does it stay for fonts outside the bundled set? FR-73 forbids requests only for the bundled fonts. READ: its only caller is `toolbar-command-schema.ts:248`, and the toolbar list becomes the fixed list (FR-8, FR-10), whose entries are all bundled, system or generic, so after this feature nothing in the app would call it, and an "Other..." name is never loaded from a host (the hint says it shows only if installed). Impact: FR-4, FR-10, FR-21 (the knip run would flag it as unused if kept uncalled). **Resolved (Owner decision, Gate 3, 2026-10-21):** delete `src/lib/fonts/loadGoogleFont.ts`, its test, and the Google-style `value` and `weights` fields of `FONT_OPTIONS` that only it consumed; keep `label` plus a new per-family shipped-weights structure as the single source of the list. Applied in FR-2, FR-4, FR-21.
- OQ-2: Do the Project Type Manager's typography fields (`ProjectTypeEditorForm.tsx`) match Project Settings' (`HeadingSettingsModal.tsx`, `BodySettingsModal.tsx`) exactly, so that one shared component fits both? READ, differences found: (a) weight values: Project Settings offers "Use default"/Normal 400/Bold 700 and reads any other stored value as empty; the Type Manager offers "—"/normal/bold/lighter/bolder (keywords, not numbers); (b) letter spacing: Project Settings a numeric input in em (step 0.01, min 0), the Type Manager free text (placeholder "0.05em"); (c) colour: Project Settings a button plus hidden colour input, the Type Manager `LabeledColorInput` with a visible value text; (d) body font size: Project Settings free text (placeholder "e.g. 18px"), the Type Manager numeric px; (e) the Type Manager has no "Use default" label ("—"), no live preview, and its own CSS classes (`project-type-editor-field-control`) rather than `Input`/`Select`; (f) neither body form has weight, colour or letter spacing, and the stored body shape has none. Impact: FR-11, FR-12, FR-14, FR-15. Which weight vocabulary the shared component stores (and whether the existing keyword values in project type files are mapped or left), and which inputs the body shows, are decisions not made by the settled list. **Resolved (Owner decision, Gate 3, 2026-10-21):** the shared component stores weights as numeric strings ("400", "700", ...). Type Manager keywords display as numbers (normal as 400, bold as 700). "lighter" and "bolder" are dropped as choices; a stored "lighter" or "bolder" is shown as an extra labelled entry and never rewritten. For the other differences the shared component uses the Project Settings forms: numeric em letter spacing, px size for body, a colour picker with visible value text. The Type Manager does not gain a preview. Applied in FR-11, FR-12, FR-14, FR-15.
- OQ-3: Does the fixed "Other..." hint also appear in the editor toolbar's font control (`components/Editor/MenuBar/...`), or only in the settings forms? The toolbar control is a compact select-style control in a bar (READ: `kind: "input"`, `inputType: "select"`); an "Other..." field and hint there is a layout and focus change the settled decisions do not state. Impact: FR-9, FR-10, FR-13. **Resolved (Owner decision, Gate 3, 2026-10-21; option b):** the editor toolbar's font control lists only the fixed names (bundled, system, generic), with no "Other..." choice and no hint; a selection whose font is unlisted shows its stored name as a read-only extra entry; arbitrary names are set in Project Settings or a project type. This is documented in the docs. FR-72's "Other..." applies to the settings forms only. Applied in FR-8, FR-9, FR-10, FR-18, FR-20, FR-21.
- OQ-4: The product spec names letter spacing and line height as fields "both already have", but headings have no line height and bodies have no letter spacing, weight or colour in the stored shape. Does the shared component show each input only where the stored shape has it (headings: family, size, weight, colour, letter spacing; body: family, size, line height, paragraph spacing), or does this feature add body weight, colour and letter spacing and heading line height to the model? This spec assumes the former (no stored shape change, non-goal above). Impact: FR-12, FR-14, FR-15. **Resolved (Owner decision, Gate 3, 2026-10-21):** each form shows only the inputs its stored shape has (headings: family, size, weight, colour, letter spacing; body: family, size, line height, paragraph spacing). No model change. The shared component takes a prop for which inputs to show. Applied in FR-12, FR-14, FR-15.
- OQ-5: Which characters does "Other..." refuse (FR-9)? The settled decisions say a typed name is stored and rendered with the stack; they do not say how a name containing quotes, commas or semicolons is handled. Options for the owner: refuse any of `"`, `'`, `;`, `{`, `}`, `\`, `(`, `)`, `<`, `>`; or escape and quote; or accept a comma list as a stack. Impact: FR-9, FR-21. **Resolved (Owner decision, Gate 3, 2026-10-21; option b):** newly typed "Other..." names refuse `"`, `'`, `;`, `{`, `}`, `\`, `(`, `)`, `<`, `>` and control characters (refusal shown beside the field, `role="alert"`) and are quoted. A stored value that contains a comma is treated as an existing font stack: applied as stored, shown as "Other..." with the text unchanged, never rewritten. Every font-family declaration is built through one validated helper, with no raw concatenation. Applied in FR-9, FR-21. Raised by this answer: OQ-11.
- OQ-6: Does the preview text in Project Settings and the Type Manager use the same fallback stack for "Other..." as the editor? READ: the Project Settings previews apply `fontFamily: heading.fontFamily` raw (`HeadingSettingsModal.tsx`), so a name with a space but no quotes is parsed by CSS as an unquoted identifier sequence. This spec assumes the stack is applied there too (FR-9). Impact: FR-9. **Resolved (Owner decision, Gate 3, 2026-10-21):** one pure function builds the quoted fallback stack ("<Name>", "IBM Plex Serif", serif) used by the editor body variable, the heading style attribute and both previews. Finding recorded (READ, not measured): today the value is applied unquoted (`editor-heading-settings.ts:158-162`, `TipTapEditor.tsx:720`), so a listed name beginning with a digit such as "Source Serif 4" is not a valid unquoted CSS family; FR-1 (e) observes it. Applied in FR-1, FR-9, FR-21 and the evidence table.
- OQ-7: Where is the stored family value's canonical form for bundled fonts: the label ("Playfair Display"), as `setFontFamily(selected.label)` stores today, or the Google-style value with plus signs? READ: the toolbar stores the label. This spec assumes the label. Impact: FR-8, FR-9, FR-14. **Resolved (Owner decision, Gate 3, 2026-10-21):** the canonical stored form for bundled fonts is the label (for example "Playfair Display"). Applied in FR-8.
- OQ-8: Do the variable-font packages (`@fontsource-variable`) satisfy "exactly the weights shipped" for Playwrite IE, which `FONT_OPTIONS` lists as `100..400`? A variable axis offers a continuous range, not discrete weights. The settled list of weights does not say which discrete weights the select shows for it. Impact: FR-2, FR-11. **Resolved (Owner decision, Gate 3, 2026-10-21):** Playwrite IE offers 100, 200, 300 and 400 (Thin, ExtraLight, Light, Regular) in the weight select; the implementation task confirms which `@fontsource` package supplies them and records it in the package justification. Applied in FR-2, FR-11.
- OQ-9: Source Serif 4 is listed at 400/600 in `FONT_OPTIONS`; the weight select offers 400 and 600 for it by FR-11, which is not the 400/700 pair the other fonts give. Confirm that 600 is shown as "Semibold 600" and 700 is not offered. Impact: FR-11. **Resolved (Owner decision, Gate 3, 2026-10-21):** Source Serif 4 offers Regular 400 and Semibold 600 only; a stored 700 shows as an extra entry, unchanged. Applied in FR-11.
- OQ-10: Which weights does IBM Plex Serif ship? The settled list says 400/700/400 italic, but every built-in project type and the default H3 use weight "500" with IBM Plex Serif (READ: `editor-heading-settings.ts:29`, `getwrite-config/templates/project-types/*.json`), which would otherwise be a weight the select does not offer. Impact: FR-2, FR-11, FR-15. **Resolved (Owner decision, Gate 3, 2026-10-21; option a):** ship IBM Plex Serif 500 as well; Plex Serif shipped weights become 400, 500, 700 and 400 italic. Applied in FR-2, FR-11, FR-15. The product spec was amended accordingly on 2026-10-21 (FR-73 decision (b) and OQ-107 now list Serif 400/500/700 and 400 italic and Playwrite IE 100/200/300/400).
- OQ-11: How is a newly typed "Other..." name that contains a comma handled? OQ-5 refuses a list of characters that does not include the comma, and treats a stored value containing a comma as an existing font stack, applied as stored. A comma name typed in the field is therefore stored as typed and, on the next render or reopen, is indistinguishable from a stack and applied unquoted as stored. Options for the owner: (a) accept it as a deliberate way to type a stack; (b) refuse a comma in newly typed names, so that only existing stored stacks keep working. Impact: FR-9, FR-21. **Resolved (Owner decision, Gate 3, 2026-10-21; option b):** a comma is refused in newly typed "Other..." names (refusal shown beside the field, `role="alert"`, like the other refused characters), so a writer cannot create a new font stack. Font stacks already stored in files (values containing a comma) keep working as existing stacks: applied as stored, shown as "Other..." unchanged, and never rewritten. Applied in FR-9, FR-21.
