## What was built

- `POST /api/project/split/undo`: body `{ projectId }` and nothing else (`parseSplitUndoBody`); `undoLatestSplit(projectId)` runs in `withStorageContext`; the core result is the typed 200 body (`applied`, `index-failed`, `nothing-to-undo`, `unsupported-operation`, `refused` with reason and the core's text field, `could-not-be-checked`, `failed` with step, cause and remaining state). Malformed JSON, non-object, unknown key (a `path` or `projectRoot` included) or a bad id: 400 with the one fixed text `SPLIT_INVALID_REQUEST_MESSAGE`; tests assert the body is exactly that and contains none of the marker strings sent. `InvalidProjectIdCoreError` maps to the same 400. Locked-access errors and any other error propagate (401/409 through `withStorageContext`; a test asserts an unexpected error rejects and is not a body).
- `GET /api/project/split/latest?projectId=`: method choice. Read: the repo's read routes that carry a project id (`/api/claims`, `/api/project/writing-log`, `/api/project/goal-filtered-total`, `/api/project/folder-metadata`) are GET with the id in the query, and the read writes nothing, so GET. The only accepted parameter is one `projectId` (an extra or repeated parameter is the fixed 400). It reads `readLatestOperation(resolveResourceProjectRootOrThrow(projectId))` and returns `{ outcome: "found", record }`, `{ outcome: "none" }` or `{ outcome: "failed", cause }`; a failed read is a separate outcome from `none`.
- Cause texts are stable codes, not stored error messages. Read: `readRecordFile` in `split-records-core.ts` sets a failed read's `cause` to the fs error's `message`, which for an `fs` error names the file path. The latest route therefore returns the fixed `record-unreadable` for any failed read, and the undo route passes a `could-not-be-checked` cause through only if it is `record-malformed`, `project-root-not-absolute` or `record-unreadable`, otherwise `record-unreadable`. A test feeds a path-bearing cause to each and asserts it does not appear. Not run: a real unreadable file (the cores are faked here).
- `SplitLockKeyError` (a relative operator-set projects dir, see task-23.md): `undoLatestSplit` raises it from `revisionContentLockKey` before any lock or write (read from code: it is called at the two `acquireLock` calls, after the record read and before `undoUnderLocks`), so the undo route returns `could-not-be-checked` with cause `project-root-not-absolute`, asserted by a test. The latest route does not use lock keys.
- Client (`src/lib/api/split.ts`): `requestUndoSplit(projectId)` and `requestLatestSplitOperation(projectId)`, plus `parseSplitUndoBody`, `parseSplitLatestQuery`. Both validate before sending, so only `projectId` is sent (the undo body is `{ projectId }`; the latest call is `GET ...?projectId=`). Results by `kind`: undo `applied`, `index-failed` (with failures), `nothing-to-undo`, `unsupported-operation` (`operationKind`), `refused` (reason plus the text from `SPLIT_UNDO_REFUSAL_MESSAGES`, not the server's text), `could-not-be-checked` (cause), `failed` (`failedStep`, `remainingState`, `cause`); latest `record`, `none`, `failed` (cause). A thrown fetch, a non-ok status, a malformed 200 body (including an unknown enum value) is `failed`: for undo `remainingState: "state-unknown"`, `failedStep: null`, `cause: "transport-failed"`; for latest `cause: "transport-failed"`. A body that fails local validation is not sent (`invalid-request`; for undo `remainingState: "split-restored"` since nothing was sent). 401/409 (a 401 with `x-getwrite-gate: not-paired` excepted) is rethrown as the locked-access error. A malformed body goes to `reportTransportValidationFailure`, which does not receive it.
- Undo's client types import only types from `split-undo-core.ts` (server code); the step and remaining-state lists are local tables typed `Record<SplitUndoStep, true>` and `Record<SplitUndoRemainingState, true>`, so a core change that adds a value fails typecheck here.
