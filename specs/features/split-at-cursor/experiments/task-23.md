## What was built

- `split-content-hash.ts`: `hashSplitContent` moved here unchanged (no imports at all); `split-preview-core.ts` imports it and re-exports it, so existing imports and tests are unchanged. A test asserts the client export, the `split-preview-core` export and the leaf export are the same function object (`toBe`), that it equals SHA-256 from `node:crypto` for three inputs (empty, ASCII, multi-byte with an astral character, 40-fold repeated), and that the leaf file has no import statement and no `node:`/`require`/dynamic import outside comments. `split-core-import-graph.test.ts` stays green (it walks every `split-*.ts`, so the new file is covered).
- `src/lib/api/split.ts`: `requestSplitPreview`, `requestSplit`, `hashSplitContent` (re-export), `parseSplitPreviewBody`, `parseSplitBody`, `SPLIT_REQUEST_LIMITS`, three fixed texts. The two parsers are the single definition of a valid body: the client sends only what they accept and the routes accept exactly the same (the routes import them from this file; they are pure and import no server code). Unknown keys at the top level or in `carryOver` are refused; the client copies only the known fields before validating, so an extra key on a caller's object is dropped, not sent.
- Routes: both are `export const POST = withStorageContext(handlePost)`, `dynamic = "force-dynamic"`, no `checkLimit`/`limits-check`/`refusalFor`/`lib/sharing` (asserted by a source scan in both test files).
- Outcome mapping. Routes return the core result as a typed 200 body. The client maps: preview -> `preview`; `refused` with `stale-cursor` -> `stale`; any other `refused` -> `refused` with `reason` and the text from `SPLIT_REFUSAL_MESSAGES`; `failed` -> `failed`. Split: `applied` -> `applied`; `index-failed` -> `index-failed` (a success kind, with the notice text built by `describeSplitIndexFailure` from the failure steps); `refused`/stale as above; `failed` -> `failed` with `failedStep`, `remainingState` and `describeSplitFailure` text. A thrown fetch, a non-ok status or a malformed 200 body is `failed`: for the preview with a fixed "nothing was changed" text; for the split with `remainingState: "state-unknown"` and the state-unknown text, because the request may have reached the server. A body that fails local validation is not sent and returns `failed` (`original-restored` for a split, since nothing was sent). A 401 or 409 (a 401 with the `x-getwrite-gate: not-paired` header excepted) is rethrown as the locked-access error. The server's error text is never shown; a malformed body is reported through `reportTransportValidationFailure`, which does not receive it.
- Boundary: 400 with one fixed text (`SPLIT_INVALID_REQUEST_MESSAGE`) for invalid JSON, a non-object body, an unknown key (a `path` or `projectRoot` key included), a project, resource or revision id that does not match, a hash that is not 64 lower-case hex, an offset that is not a non-negative safe integer, and a bad carry-over; tests assert the body is exactly that text and does not contain the marker strings sent. `InvalidProjectIdCoreError` from a core maps to the same text.
- Bounds chosen here (an assumption: the cores set none): `newName` at most 1000 characters, annotation ids and field names at most 200 characters each, at most 5000 annotation ids and 500 fields. Resource names have no limit elsewhere in the code read; a longer name than 1000 characters is refused at this boundary.
- Locked project: the fake core rejecting `ProjectLockedError` / `MissingProjectKeyError` gives 401 / 409 through `withStorageContext` on both routes, and an unexpected core error is rethrown (not a result body).

## Facts about `SplitLockKeyError` and the project root (handoff item 2)

- Read: `resolveResourceProjectRootOrThrow` returns `path.join(resolveProjectsDir(), projectId)`; `resolveProjectsDir()` is the request's storage-context `tenantRoot`, else `defaultProjectsDir()` = `process.env.GETWRITE_PROJECTS_DIR ?? path.join(process.cwd(), "..", "projects")`. `path.join` does not make a path absolute, so a relative `GETWRITE_PROJECTS_DIR` gives a relative project root and `revisionContentLockKey` throws `SplitLockKeyError`. The hosted tenant root is `path.join(GETWRITE_DATA_ROOT, userId)`, relative the same way if the variable is relative. Nothing in the frontend checks either variable for absoluteness (a search for `isAbsolute` / `path.resolve` in `projects-dir.ts`, `tenant-path.ts` and `app/api/_tenant` found none).
- Read: every in-repo producer of the variable sets an absolute value: the Electron main process passes `dirs.projectsDir` (the user override is refused when not absolute, `validateWorkspaceDir`, `electron/src/projects-dir.ts`; the defaults are `~/Documents/GetWrite` and the repository's `projects/`); the CLI QA harness passes an `mkdtemp` path; the hosted smoke README uses `mktemp -d`; with the variable unset the default is built from `process.cwd()` and is absolute. Android has no route.
- So: the routes can reach `SplitLockKeyError` only if an operator sets `GETWRITE_PROJECTS_DIR` or `GETWRITE_DATA_ROOT` to a relative path by hand. No configuration shipped or documented in the repository produces that. Not run: such a server. `revision-core.ts` (which uses `path.resolve(projectRoot)` for the same key) was not edited.
- Handling: the preview route returns `{ outcome: "failed", cause: "project-root-not-absolute" }` and the split route returns `{ outcome: "failed", failedStep: "lock-original", remainingState: "original-restored", cause: "SplitLockKeyError" }` (the error is raised before the first write; a test asserts both bodies). Neither maps to an empty result. The lead may decide whether a relative operator setting warrants a change in `revision-core.ts` or a startup check; that is outside this task's Files.
