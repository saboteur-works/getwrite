## Overview

A writer using GetWrite on Android cannot see their own images or hear their own audio: on a Pixel 7 Pro, opening an image resource shows "Unable to load image." and opening an audio resource shows "Unable to load audio.", while the same media on desktop and hosted web works. This feature makes image and audio resources display and play on Android up to a size a device run verified, makes images embedded in a document render, be inserted by drop and be picked from the image picker with their thumbnails, tells the writer plainly when a file is too large to show on the device or cannot be read, and releases the memory held for a file when it is no longer shown. Desktop, hosted web and paired devices are not changed.

## Goals

- On Android, opening an image resource shows the image and opening an audio resource plays it, for a file up to 31,457,280 bytes, each verified on a Pixel 7 Pro.
- On Android, an image embedded in a document renders, an image dropped into the editor is inserted and shown, and the image picker shows its images and thumbnails, each path verified on a Pixel 7 Pro.
- On Android, a resource above 31,457,280 bytes is refused before it is read with a plain message and its size, and a read failure at or under that size shows a readable message, with no crash, blank area or endless loading state.
- Memory held for a file is released when it is no longer shown, pinned by a test.
- Desktop, hosted web and paired devices keep loading media through `/api/resource/<id>/file` with the same success and refusal results, pinned by a test.

## Non-goals

- Video or any other media type (OQ-178).
- Compile and export of images on Android (listed as not verified, not claimed).
- A Capacitor file URL (`convertFileSrc`) route, or any other route that avoids holding the whole file in WebView memory.
- Raising the Android cap above 31,457,280 bytes, or any size claim not verified on a device.
- Source attachments (Feature 103 already shows them) and writing or replacing media (Feature 104).
- A second device, a device-class matrix, or a safety margin below the verified size.
- Any new control; the existing viewers, drop and picker are the interface.

## User stories

- US-1: As a writer using GetWrite on Android, I want to open an image resource and see it, open an audio resource and play it, and see, drop and pick images in my documents, so that the media I keep in my project is usable on my phone and not only on the desktop, and to be told plainly when a file cannot be shown. (Product US-47.)

### The resource-level read and its refusal

2. FR-2: A resource-level variant of the in-process byte read MUST exist that, given a project id and an image or audio resource id, returns the resource's own stored file's bytes, a MIME type and the kind (`image` or `audio`), following the shape and the error contract of `readAttachmentBytesCore` (`source-attachment-bytes-core.ts`): ids are validated before any read and no client-supplied path is used; the file is found through the resource's own sidecar `file` entry, which MUST be a bare file name (checked with `isPlainFileName`); all file access goes through the storage adapter; the client module is `frontend/src/lib/api/resource-bytes.ts`, resolved through `createTransport` like `source-attachment-bytes.ts`, with a native backend (literal dynamic import) and a `.web-stub.ts` alias in `next.config.mjs`; the file's size is obtained by `stat` through the adapter before any read, a non-number size is a failure and never 0, ENOENT maps to the missing-file error, the MIME type comes from the extension as the file route does, and there is no leading-byte check; a missing file MUST be reported as a missing file and never as an empty one; a locked-access error MUST NOT be caught. A resource of any type other than `image` or `audio` MUST be refused. Reading a resource MUST write nothing, take no lock and delete nothing. (Product FR-146, OQ-175, OQ-178; `docs/standards/security.md`, `docs/standards/failure-visibility.md`.) [US-1]
3. FR-3: On Android, an image or audio resource whose stored file is larger than 31,457,280 bytes MUST be refused before its bytes are read, and no read of its bytes MUST be attempted, in the viewers and in every embedded-image path of FR-8 to FR-10. This MUST include a resource created before Feature 104, whose file can be up to 104,857,600 bytes on disk. The refusal MUST read "This file is N MB. It is too large to show on this device (limit 30 MB)." with MB computed by the MiB arithmetic of `media-validation.ts:179-186` and N shown to one decimal place. The threshold MUST be a separate exported constant `ANDROID_VERIFIED_MAX_MEDIA_READ_BYTES = 31_457_280` in `media-validation.ts`, and a unit test MUST fail if `maxMediaFileBytes()` on native exceeds it. A file of exactly 31,457,280 bytes MUST NOT be refused and a file of 31,457,281 bytes MUST be refused; both MUST be tested at the unit level and run once each on the device (FR-7). (Product FR-148, OQ-176.) [US-1]
4. FR-4: On Android, a read that fails for a resource at or under 31,457,280 bytes (a missing file, a locked project, an allocation failure, or an object URL that cannot be created; a locked project MUST show Feature 103's "This project is locked. Unlock it, then try again." through `isLockedAccessError`, the branch being unreachable on native today and tested with a fake) MUST NOT crash the app, MUST NOT leave a blank area, and MUST NOT leave an indefinite loading state in the viewer or in any embedded-image path; it MUST show a message the writer can read that says the file cannot be shown. While the read is in progress each path MUST show a loading state that ends in either the media or a message. A failed read MUST NOT be reported as a successful read of an empty file. Each of the viewer's two failure states ("Unable to load image.", "Unable to load audio.") MUST remain what a failure of the file itself shows (an `<img>` or `<audio>` error), distinct from the refusal of FR-3 and from a read failure of this requirement; the refusal, read-failure and locked messages MUST be rendered by a wrapper in `MediaView` before the viewer mounts, with `role="alert"`. (Product FR-148; `docs/standards/failure-visibility.md`.) [US-1]

By reading, the stored `src` round-trips on save, so a value that only works on Android would end up in the document on desktop. — Resolution (owner, Gate 3, 2026-11-08): the stored `src` stays the web serving URL plus `resourceId`; the blob URL exists only on the rendered DOM `img.src`; the node view MUST NOT write it back through `updateAttributes`; the FR-14 test pins the stored content and the Markdown (`renderMarkdown`, `GetWriteImage.ts:135-154`). — Impact: FR-9, FR-10, FR-14.
- OQ-5: How many embedded images may be loaded at once, and what is the memory cost? Each read holds one whole file in WebView memory, up to 31,457,280 bytes; a document can embed many resources, and the picker renders one `<img>` of the full file per image resource. Feature 104 measured the read of a single file, not several held at once, and no experiment has loaded several. An experiment would settle it: a document with several images near the threshold, recorded for crash, out-of-memory warnings and time. A limit, a queue, or lazy loading (only what is on screen) is not chosen. — Resolution (owner, Gate 3, 2026-11-08): (a) lazy loading: documents and the picker read only images near the viewport, with a per-resource ref-counted shared cache so one loaded file exists per distinct image; a picker entry over the threshold shows a "too large" placeholder and stays listed and insertable; a device run with several near-threshold images in one document and in the picker is recorded in `experiments.md`; no "safe number" is claimed. — Impact: FR-4, FR-8, FR-10, FR-11, FR-13.
- OQ-6: What is the exact wording of the refusal message and its size unit? The feature breakdown says "a plain message that it is too large to show on this device and its size"; Feature 104's upload refusal reads "File exceeds the N MB limit." and prints MiB arithmetic with an "MB" label (`media-validation.ts`); whether the size shown here is in MB or MiB, to what precision, and whether the message names the limit, is not decided. — Resolution (owner, Gate 3, 2026-11-08): (a) the wording is "This file is N MB. It is too large to show on this device (limit 30 MB)." with MB computed by MiB arithmetic as Feature 104 does (`media-validation.ts:179-186`), the file size shown to one decimal place. — Impact: FR-3, FR-19.
- OQ-7: How does the core know the file's name and size before reading it? By reading, a resource's stored file name is its sidecar `file` entry (`ImageResource.file` and `AudioResource.file`, `types.ts:466`, `:479`) found under `resources/<id>/`, and the sidecar has an optional derived `sizeBytes` field (`types.ts:295`), but it was not read whether that figure is always present or reliable. Whether the size comes from the sidecar or from a stat of the file, and whether the adapter exposes a stat that does not read the bytes (neither was read), is not decided; FR-3 requires the size to be known without reading the bytes. Also open: whether the core checks the leading bytes of the file as `readAttachmentBytesCore` does (`validateAttachmentFile`) and what it does when the stored file does not match its type. — Resolution (owner, Gate 3, 2026-11-08): the file name comes from the sidecar `file` entry checked with `isPlainFileName`; the size comes from `stat` through the storage adapter (`io.ts:100`; the `capacitorFsAdapter.ts` stat returns `size`) before any read; a non-number size is a failure, not 0; ENOENT maps to the missing-file error; the MIME is derived from the extension as the file route does; there is no leading-byte check (the upload path validates; a bad file surfaces as an `<img>` or `<audio>` error). The sidecar's derived size field is `sizeBytes` (`types.ts:295`); it is rarely written and is not used for the gate. — Impact: FR-2, FR-3.
- OQ-8: Does the picker's thumbnail load the full file? By reading, yes: the `<img>` uses the same URL as the full image, and no thumbnail file exists. Whether the picker should read each file (subject to OQ-5), show a placeholder for files above some size, or load an entry only when it is scrolled into view, and what the picker shows for a resource refused under FR-3, is not decided. — Resolution (owner, Gate 3, 2026-11-08): settled together with OQ-5: lazy loading in the picker and documents, the shared per-resource cache, and a "too large" placeholder for a picker entry over the threshold that stays listed and insertable. — Impact: FR-3, FR-10, FR-11.
- OQ-9: Where is a blob URL revoked in the editor's non-React rendering, and what happens on re-render? A TipTap node can be re-rendered on any document change, and revocation on removal depends on a node-view destroy hook or an equivalent, which was not read. Whether a URL is cached per resource across nodes (two nodes embedding the same image) or created per node is not decided, and it changes how many whole files are held at once. — Resolution (owner, Gate 3, 2026-11-08): the blob URL is revoked in the node view's `destroy()`; a per-resource ref-counted cache is shared by nodes; the node view's `update()` keeps the DOM for the same `resourceId` (no re-read); a test shows that editor teardown destroys the node views and revokes. — Impact: FR-8, FR-11.
- OQ-10: What does the refusal, loading and read-failure state look like inside a document: an inline message in place of the picture, an alt-text placeholder, or a toast? The viewers have a place for a message; an image node and a picker entry do not. — Resolution (owner, Gate 3, 2026-11-08): (a) an inline placeholder box where the picture goes, with an icon and the same short message as the viewers, reusing the picker's placeholder style (`editor-image-picker-thumb-placeholder`); no red (repository red rule). — Impact: FR-3, FR-4, FR-8, FR-10.
- OQ-11: If the Android cap changes (the cap is temporary, POS task_bdf70699), does the viewers' threshold follow `maxMediaFileBytes()` automatically, or is it a separate value that only changes after the viewers' read has been verified at the new size? FR-148 of the product spec says the threshold equals `maxMediaFileBytes()` on native today, but a cap raised for writes (Feature 104) is not verified for reads here. — Resolution (owner, Gate 3, 2026-11-08): a separate exported constant `ANDROID_VERIFIED_MAX_MEDIA_READ_BYTES = 31_457_280` in `media-validation.ts` is the read threshold; a unit test fails if `maxMediaFileBytes()` on native exceeds it. — Impact: FR-3, FR-13.
- OQ-12: What does a viewer or embedded image show for a locked project on Android? The read core raises a locked-access error that Feature 103's hook turns into "This project is locked. Unlock it, then try again."; whether this feature reuses that sentence, and whether a locked project on native is reachable at all (Feature 104 read that no encrypting adapter is bound on native, `native-bootstrap.ts:60-83`), is not decided. — Resolution (owner, Gate 3, 2026-11-08): reuse Feature 103's "This project is locked. Unlock it, then try again." through `isLockedAccessError`; the core does not catch locked errors; the case is not reachable on native today (`native-bootstrap.ts:60-77`), so the branch is kept and tested with a fake. — Impact: FR-4.
- OQ-13: Does the existing viewer need to distinguish "the file itself is not a valid image or audio" (an `<img>` or `<audio>` error on a blob URL) from a failed read? FR-4 requires the failure states not to be confused; whether the `ImageViewer` and `AudioPlayer` error messages stay as they are, and whether a message is added for the read failure, is not decided. — Resolution (owner, Gate 3, 2026-11-08): the viewers' existing `<img>` and `<audio>` error messages stay for a bad file; read failure, refusal and locked get their own messages, rendered by the `MediaView` wrapper before the viewer mounts, with `role="alert"`. — Impact: FR-4, FR-5.
