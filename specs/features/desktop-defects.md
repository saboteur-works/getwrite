## Overview

Three things go wrong, or are unknown, in the desktop app. Word import answers "That project type isn't recognized." in the development app when it is launched from a directory other than the one the project-type lookup expects, and a packaged build may do the same. Adding a global noise word fails in the development app because it has no user-data directory to write to, and the desktop settings file that holds that list, the sharing setting and the workspace-folder override is written in place, so an interrupted write can leave it partly written. And it is not known whether desktop compile produces no file because of the app or because of the script that checked it. This feature makes the Word import independent of how the app was launched, makes the noise-word list work in the development app, makes the settings file write safe against interruption, and answers the compile question by a manual run, fixing it only if the answer is a one-line product change.

## Goals

- A Word import started from the desktop app recognises the same project types as the command line and project creation, whatever directory the app was launched from, in the development app and in a packaged build.
- Adding a global noise word in the development desktop app succeeds, and the word is read back after a restart of that app.
- `workspace.json` is never left partly written by an interrupted write, in either build; a damaged file still reads as empty.
- It is recorded, with a measurement from a manual run, whether desktop compile produces a file, and whether a failure is a product defect or a fault in the verification script.
- Every cause that is a HYPOTHESIS or a READ is reproduced before its fix, and the fix is shown to turn that reproduction green.

## Non-goals

- The other handbook defects, including D-1, D-6, D-28 and the "stale until reload" and display groups.
- Unifying `GETWRITE_PROJECT_TYPES_DIR` and `GETWRITE_TEMPLATES_DIR` (OQ-95 decision 1), changing the Scrivener worker (it does not read project types, READ), and changing `frontend/src/lib/projectTypes.ts`'s fallback order.
- A main-process download handler, a save dialog, or any decision about where compiled files go on the desktop (OQ-95 decision 2). If the compile check shows that is needed, it is recorded for a separate feature.
- Changing how a damaged `workspace.json` is read (it reads as empty and the next write keeps only the field being set), adding a backup or repair of it, or locking it between processes.
- Changing the workspace-folder chooser's use of the empty user-data directory in the development app (`main.ts:298`), or any other development-app behaviour not listed in the requirements.
- Any new IPC channel, route, transport module, feature flag or user-visible copy.
- Running anything on the owner's real app folders (see FR-21).

## User stories

- US-1: As a novelist migrating from Word, I want to import my Word document from the desktop app without being told its project type is not recognised, however the app was launched, so that I do not have to recreate its structure by hand. (Product spec US-18.)
- US-2: As a novelist who works across multiple projects, I want to add a word to my global noise-word list in the development desktop app so that the same setting works there as in the packaged app. (Product spec US-3, US-24.)
- US-3: As a plain-file writer, I want to have the desktop settings file written in a way an interrupted write cannot leave partly written so that my workspace-folder choice, sharing setting and noise-word list survive a crash or power loss. (Product spec US-5.)
- US-4: As a novelist, I want to compile a selected subtree of my project into a single manuscript file from the desktop app so that I can produce a deliverable draft. (Product spec US-2.)

## Open questions

- OQ-1: How is a packaged (unpacked) build run safely with a throwaway user-data directory, workspace folder and logs folder? Evidence: READ — for a packaged build `resolveProjectsDir` reads `userData/workspace.json`'s `projectsDir` and otherwise defaults to `~/Documents/GetWrite` (`projects-dir.ts:411-419`), so a throwaway `workspace.json` seeded in the throwaway user-data directory would name a throwaway workspace; the legacy-directory migration reads only `<resourcesPath>/projects` and `<userData>/projects`, both inside throwaway locations in that case; a packaged build's `app.getPath("logs")` is derived from the app name (`GetWrite` from `productName`, expected `~/Library/Logs/GetWrite`, HYPOTHESIS, not measured), and the log file is written there (`main.ts:79`); `--user-data-dir` was measured to work for the development app (`desktop-dev.mjs` asserts the reported path equals the throwaway one) but not for a packaged build. Options: (a) pass `--user-data-dir=<throwaway>`, seed `workspace.json` there, and redirect logs by a call to `app.setAppLogsPath` or `app.setPath("logs", ...)` in main driven by an environment variable read only when set (a product code change, test-only in effect); (b) build the unpacked app with a throwaway `productName` through electron-builder's config override (`-c.productName=...`), so its default logs and user-data names are throwaway, with `--user-data-dir` as well, and no product code change; (c) do not run the packaged import; it becomes the owner's manual check. Impact: FR-7, FR-22, FR-23, FR-27; if (a), a small product change outside the listed fixes. **Resolved (resolved from evidence, owner confirmed, Gate 3, 2026-10-18):** (b) the unpacked build is made with a throwaway `productName` via electron-builder override (`-c.productName=...`), launched with `--user-data-dir=<throwaway>` and a `workspace.json` seeded there whose `projectsDir` is a throwaway folder; no product code change. FR-22's first action reads `app.getPath("userData")` and `app.getPath("logs")` and stops if either is under a protected folder; that assertion, not the name-to-logs mapping (general Electron behaviour, medium confidence), decides safety. If safety cannot be shown, the packaged import is the owner's manual check. See FR-7, FR-22.
- OQ-2: Does an electron-builder unpacked directory build count as "packaged" for FR-33's purpose? Evidence: `app.isPackaged` is true for it (READ, not measured here), so the code path is the packaged one (`process.resourcesPath` for templates and workers); the Finder-launch working directory of an installed `.app` may differ from the one an unpacked build has when started from a terminal; the hypothesis that a Finder-launched build fails the same way concerns that difference. Options: (a) yes, with the working directory of the launch recorded, and the claim limited to "the unpacked build, launched from a terminal at directory X"; (b) yes, and the unpacked app is also opened from a different working directory (including `/`) to approximate Finder; (c) no, only an installed `.dmg` build counts and the check is the owner's. Impact: FR-7, FR-23; what the report may say about a Finder launch. **Resolved (Owner decision, Gate 3, 2026-10-18):** (b) an unpacked `--dir` build counts as packaged; it is launched from a terminal directory and also from `/`; the report says "unpacked build launched from `/`" (and the other directory), never "Finder-launched". See FR-7, FR-23.
- OQ-3: Which directory is the explicit `cwd` for the DOCX worker fork? Evidence: READ — `getwrite-config/` is directly under `getRepoRoot()` in both builds, so that cwd makes the cwd-relative fallback resolve too, as a second layer behind the environment variable; the worker itself writes only to the `projectRoot` it is given and the source path it is given, both absolute (`handle-import-request` request, `main.ts:672-680`); no other cwd-relative read in the DOCX pipeline was looked for. Options: (a) `getRepoRoot()`; (b) `path.dirname(path.dirname(path.dirname(templatesDir)))`-style derivation from the templates directory, same value, derived; (c) the worker bundle's own directory (`dirname(resolveDocxWorkerBundlePath())`). Impact: FR-3, FR-4; low, since the environment variable decides the lookup when set. **Resolved (resolved from evidence, owner confirmed, Gate 3, 2026-10-18):** (a) the worker `cwd` is `getRepoRoot()`, passed into the pure function by main; `GETWRITE_PROJECT_TYPES_DIR` is the primary mechanism. See FR-3, FR-4.
- OQ-4: Should the atomic write of `workspace.json` reuse `writeAtomically` from `device-store-writer.ts`?
