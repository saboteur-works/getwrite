## Overview

A writer on an Android phone who sees a link, a passage of text or a photo in another app has no way to send it to GetWrite: the app is offered by no share sheet, and the Capture box from Feature 106 has no entry on a touch device. This feature adds an Android Capture entry and a share target. A writer shares text, a link or one or more images from another app, chooses a project (defaulting as the Capture box does), and each item is saved as its own resource in that project's Inbox without opening the project. Text and links go through the Feature 106 capture function; images need a new capture path through the media write. An image over the 30 MiB Android cap is refused on its own and the other items in the same share are still captured. On Android a project that carries the encrypted marker is refused and nothing is written, because native storage has no encryption layer. The whole path runs in-process through the data layer, and it is claimed to work only after a recorded run on a physical Pixel 7 Pro.

## Goals

- A writer can share text, a link or an image from another Android app to GetWrite and find each item as its own resource in the Inbox of the project they chose, without that project being open.
- A writer can open the Capture box from an Android capture entry in the top bar or menu without a keyboard.
- An image over 31,457,280 bytes is refused with a plain message, individually, without stopping, losing or crashing the other items of the same share.
- A share or typed capture into a project that carries the encrypted marker is refused on Android with nothing written, and the writer is told what was and was not captured.
- The share and capture paths are verified on a physical Pixel 7 Pro, once for text and once for an image, with build, device and file size recorded, and every unmeasured path is listed.

## Non-goals

- Audio, video, PDFs, documents and any type other than text, links and images; the share sheet offers nothing else.
- A web share target on hosted web (OQ-186) and the web clipper.
- Fetching a page title or any content from the network for a shared link.
- Compile and export of captured images on Android (listed as not verified in Feature 105) and a Capacitor file URL route (`convertFileSrc`).
- Raising the 30 MiB Android cap.
- Converting an Inbox item to a Source and combining several items into one.
- Touch drag-and-drop and Android signing and packaging (separate, later work).
- A new paired-device limit switch (Android runs in-process; no `/api` route is called).

## User stories

- US-1: As a writer on Android, I want to send a link, a passage of text or a photo from another app to a project's Inbox in a few seconds, so that I do not lose it while I am doing something else and can file it later. (Product US-48; this feature covers the Android entry and images; the Capture box on other platforms is Feature 106.)
- US-2: As a writer on Android, I want to open the Capture box from a button in the app, so that I can type a thought without a keyboard shortcut. (Product US-48, FR-154.)

### Locked, no project, duplicates

11. FR-11: On Android, the share path (text and images) and the Capture entry MUST refuse a project that carries the encrypted marker: they MUST say plainly that nothing was captured and why, MUST write nothing, and MUST NOT report success. The refusal is on the project's encrypted marker (`.encrypted.json`, `PROJECT_MARKER_FILENAME` at `frontend/src/lib/models/crypto/project-marker.ts:34`), tested with `isProjectEncrypted(projectRoot)` (`project-marker.ts:130`, exported at `frontend/src/lib/core.ts:44`; the list entry's `isEncrypted` at `project-crud-core.ts:292,301` is the same fact), read in-process before any write and before any image bytes are read; a marker read that fails for a reason other than the marker being absent MUST refuse as well, never be treated as not encrypted. This is required because writes on native are not encrypted: FR-1(c) found `native-bootstrap.ts:73-77` binds a bare `capacitorFsAdapter` with no encrypting wrapper, and a probe through the raw adapter in a project carrying the marker stored the plain bytes; that holds for every native write, including Feature 106's text capture, and predates this feature. Making native storage encrypting is a separate feature and is NOT done here; it MUST be recorded under "Not verified" and in `docs/features/inbox.md` (FR-18). Because an encrypted-marked project is refused, no unlock prompt can follow from a share on native (amended 2026-11-10: the Capture box did open one until 8c7141e4, which now refuses an encrypted-marked project on native like the share sheet; the device run disproved the reading for the Capture entry), and the queue of OQ-6 (a share arriving while an unlock prompt is open is queued in memory with a visible count, and is discarded with the first if the unlock is declined) applies only where an unlock prompt exists; on native it is not reachable and MUST be recorded as such, though the same count of shares queued behind a pending project choice MUST still be shown. A declined or failed capture MUST be told plainly, with everything held discarded. No part of a shared item MUST be written anywhere, including a cache or files directory, before a project is chosen (OQ-3); the bytes of an image MUST be read only after that. (Product FR-160, OQ-180, OQ-6; spec amendment after Task 1.) [US-1]

- OQ-1 (F107-1): Which share-in mechanism: a community plugin or a custom plugin? Options with the spike's evidence (READ and FOUND as the spike labels them; device behaviour of every option unmeasured). (a) `@capgo/capacitor-share-target` 8.0.65: peer `@capacitor/core >=8.0.0`, released weekly (latest 2026-11-02), MPL-2.0 (the repo is FSL-1.1-ALv2; obligations not assessed), 3 manifest filters on `MainActivity`, `handleOnNewIntent` with a retained event for cold and warm starts; reads one `EXTRA_TEXT` string only, ignores `ClipData`, reads no size, applies no cap, copies every image in full to `getCacheDir()/shared_files` unencrypted before JS sees it, in a call the spike infers runs on the main thread (ANR risk not measured); needs a new dependency and `cap sync`. (b) `@mindlib-capacitor/send-intent` 8.0.6 (the renamed `send-intent`): MIT, last release 2026-01-22, 21 open issues including titles on app reload and on multiple files in the background; pull model reading `getIntent()`, which under `singleTask` the spike infers returns the old launch intent on a warm share, so the README uses a second `BridgeActivity`; `SEND_MULTIPLE` reads `ClipData` with no null check; copies each image whole to `getFilesDir()` named by the sender's display name (collisions overwrite); no size or cap; adds `commons-io`; needs a dependency and `cap sync`. (c) Capawesome Share Target: paid Insiders registry, source not read, behaviour on warm start not stated; the spike excluded it from inspection. (d) A custom plugin in `android/`: roughly 130 to 200 lines of Java (spike estimate), no new dependency, no `cap sync` change, three filters on `MainActivity`, one `handleOnNewIntent` that Capacitor 8.4.2 calls for the cold-start and warm intent, retained events, can send a size with each item and apply the cap before any copy, can avoid a staging copy (JS reads the `content://` URI with the already-installed `@capacitor/filesystem`, unrun in this app) or copy after the project is chosen; cost: native code owned here with no unit-test harness in `android/` and the bytes path (`readFile` returns base64 over the bridge) unmeasured for a share. The spike did not choose. — Impact: FR-2, FR-3, FR-7, FR-11, FR-16, FR-1(f), FR-15.
  Resolved (owner), Gate 3, 2026-11-09, option (d): a custom Capacitor plugin in Java in `android/`, no new dependency, no new Gradle plugin, registered before `super.onCreate`, with a web stub; it reports each item's MIME type and size before any copy, and delivers shares on cold start and through `handleOnNewIntent`, held with `notifyListeners(..., true)` until a listener exists. Any new dependency remains owner-installed. — Impact: FR-2, FR-3, FR-7, FR-16.
- OQ-2: Which message does a refused oversized shared image show? The spike found two existing texts: `validateMediaFile`'s "File exceeds the 30 MB limit."   Resolved (triage, confirmed by the owner), Gate 3, 2026-11-09, option (a): `mediaTooLargeToShowMessage(size)` (the FR-148 text), falling back to the write-refusal text only when no size is known; settled at Gate 1 through FR-154. — Impact: FR-7.
- OQ-3: Is an unencrypted copy of a shared item made before the project is chosen acceptable under FR-160 ("MUST NOT write the captured content, or any part of it, unencrypted anywhere")? The two public plugins always copy shared images into app cache or files storage before JS runs (READ); a custom plugin can avoid or defer the copy (INFERRED). Options: (a) no: any design that writes shared content outside the data layer before a project is chosen is refused, which excludes (a) and (b) of OQ-1 unless their copy is deleted at once and the owner accepts the window; (b) yes for a staging copy that is deleted when the share finishes or is cancelled, with the deletion measured; (c) yes only for images and only for unencrypted projects, with the encrypted-project case reading the URI directly; (d) leave it to the OQ-1 choice and record every staging location under FR-1(f). Also open: the URI read grant may not hold when JS reads later, after the picker or unlock (spike R9, not checked). — Impact: FR-7, FR-11, FR-15, FR-1(f).
  Resolved (owner), Gate 3, 2026-11-09, option (a): no write of shared content anywhere before a project is chosen (and unlocked, if locked); bytes are read only after the choice. Whether the `content://` read grant survives until after the picker or unlock is measured in the device run; if it does not, the work returns to the owner and no task adds a staging copy. — Impact: FR-3, FR-11, FR-15.
- OQ-4: What is the capture button, and where does it live in the Android UI? Options: (a) a floating action button on the Start screen and in the project view that opens the Capture box; (b) an entry in the existing top bar or menu of `AppShell`; (c) a persistent button on the Start screen only, with the project's resource view relying on the share target; (d) an Android app shortcut (long-press launcher icon) in addition to one of the above. The spike found it needs no native code for (a) to (c) (INFERRED). The touch layout is not read in this spec. — Impact: FR-12.
  Resolved (owner), Gate 3, 2026-11-09, option (b): a "Capture" entry in the `AppShell` top bar or menu on Android, on the Start screen and inside a project, opening the Feature 106 Capture box; no floating action button, no app shortcut, no native code for it. — Impact: FR-12.
- OQ-5: How is one share holding several items presented? Options: (a) one project picker for the whole share, then every item is captured and one result is shown; (b) one picker with a preview list in which the writer can remove an item before saving; (c) each item asks for its own project, one after another; (d) a single item is captured after one confirmation and a multi-item share uses (a). Also open: whether a single text share is saved on the picker's confirmation or can be edited first (see OQ-9). — Impact: FR-4, FR-8, FR-10.
  Resolved (owner), Gate 3, 2026-11-09, option (a): one project picker for the whole share; every item is captured, then one result names each refused or failed item; text is not edited before saving. — Impact: FR-4, FR-8.
- OQ-6: What happens when no project exists or the app is locked? Options for no project: (a) say a project is needed and discard the share, as the Capture box does; (b) hold the share in memory and offer to create a project, then capture into it; (c) open the Start screen's create flow. For a locked project the spec requires the unlock prompt (FR-11); the open point is what a share offers when the writer declines it (discard, or keep it in memory until the app is closed) and whether a share arriving while the unlock prompt of another capture is open queues or replaces it. No app-level lock other than a locked project was found in the inputs read; if one exists the question covers it. — Impact: FR-11, FR-13.
  Resolved (triage for no project; owner for the residual), Gate 3, 2026-11-09: with no project, say a project is needed and write nothing (FR-152, OQ-187); if unlock is declined, discard and tell the writer (FR-160). Residual, option (a): a share that arrives while an unlock prompt is open is queued in memory behind the first, with a visible count; if the unlock is declined, everything is discarded and the writer is told. Amended 2026-11-09 after Task 1 (owner): refuse encrypted-marked projects on native; document the absence of native encryption. An encrypted-marked project is refused before any prompt, so on native no unlock prompt can occur and the queue-behind-unlock applies only where an unlock prompt exists (not reachable on native); the count of shares queued behind a pending project choice still applies. Amended 2026-11-10 after the device run (owner): the statement that no unlock prompt can occur on native was disproved; the Capture box opened the passphrase prompt for a "Locked project" on native until 8c7141e4, which now refuses it like the share sheet. — Impact: FR-11, FR-13.
- OQ-7: How is duplicate delivery on relaunch prevented? Android can redeliver the original share intent when the app is relaunched from Recents (INFERRED, spike R12, not checked). Options: (a) clear the pending intent in the native layer once the web layer has taken the share; (b) record a share id (intent timestamp or hash) in memory and ignore a repeat; (c) record it in `localStorage` per origin so it survives a process restart, accepting a missed second identical share; (d) measure first on the device and add a guard only if a duplicate is observed. — Impact: FR-3, FR-14, FR-15.
  Resolved (owner), Gate 3, 2026-11-09: the plugin marks the intent consumed once taken (it clears the extras or action natively); the device run checks whether a relaunch redelivers; no persisted share id. — Impact: FR-14, FR-15.
- OQ-8: What is the image entry point, and what does a shared image do? Options for the core path: (a) a new function `captureImageToInboxCore` beside `captureToInboxCore` that shares the Inbox resolution and calls `uploadMediaResourceCore`; (b) extend `captureToInboxCore` with an optional image payload; (c) call the existing media create and the Inbox resolver from the native backend without a new core function. Whether a shared image is left out of compile by default like a typed capture (the exclusion is seeded through `config.compileDefaults`): (a) yes, same as text; (b) no, because Android compile and export of captured images is not verified (Feature 105) and an exclusion hides the item from a dialog the writer cannot yet check; (c) yes, and the Android Compile dialog is not used for it until verified. — Impact: FR-7, FR-9, FR-17.
  Resolved (owner for the entry point, triage for the compile half), Gate 3, 2026-11-09, option (a): a new `captureImageToInboxCore` beside `captureToInboxCore`, reusing `resolveInboxFolder` and the compile seeding and leaving the text core's validation unchanged; a shared image starts unticked in compile like every Inbox item (FR-157). — Impact: FR-7, FR-9.
- OQ-9: How is shared text handled in the goals and the writing log? FR-156 says shared text is an import entry and the Capture box's typed text is additions. Open: (a) text shared in and saved as is: import, as FR-156 says; (b) text shared in and then edited by the writer in the box: still one import of the shared words, or additions for the edit; (c) a share the writer edits is logged as typed. Also open: the import entry has no document id today (READ), so whether it should record the item's id for the filed-out case of Feature 106's FR-7. — Impact: FR-10.
  Resolved (triage, confirmed by the owner), Gate 3, 2026-11-09: shared text is logged as an import (`source: "plaintext"`, no document id), as already implemented in `inbox-capture-core.ts:130-134`; the import entry carries no item id; the edited-text case does not arise because OQ-5 (a) allows no editing; images write no writing-log entry. — Impact: FR-10.
- OQ-10: How is a link recognised and what do the sender's subject and title do? Options: (a) a link-only item is one whose trimmed text is a single `http` or `https` URL; any other text, with or without a link inside, is text and `capturedLink` is not set; (b) as (a), and when the text holds one URL with other words the URL is also stored in `capturedLink` and the text stays the body; (c) as (b), and the sender's `EXTRA_SUBJECT` is used as the title when the body is a link only. Which apps send a subject with a link is not measured. — Impact: FR-5, FR-6.
  Resolved (owner), Gate 3, 2026-11-09, option (a): link-only means the trimmed text is exactly one `http` or `https` URL, which goes into `capturedLink` and becomes the body; any other text is plain text with `capturedLink` unset; `EXTRA_SUBJECT` is ignored. — Impact: FR-5, FR-6.
