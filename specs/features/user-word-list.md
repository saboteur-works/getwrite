# Feature 96: A user word list that follows the writer across projects

Source: `specs/product/getwrite.features.md` "### Feature 96" and F94-3, F94-4 (option d); `specs/product/getwrite.md` FR-78, US-33, OQ-125, OQ-128 (resolved, Gate 1, 2026-10-25). Depends on: Feature 95 (`specs/features/spell-checker.md`, merged to `main`, not released). Branch suggestion: `feat/spell-checker-user-list`.

Scope note. This spec is longer than the skill's 500-word guide: it carries three platform stores, a paired-device rule and a settings section that cannot be used apart. Fact labels: READ means read in the code on 2026-10-26, not run; MEASURED means run; nothing below is MEASURED. No cause is stated beyond the evidence cited.

Settled decisions, not reopened (owner, Gate 1 and Gate 2, 2026-10-25):

- The user list is stored per platform and not synced: desktop `userData` through IPC (`getDesktopBridge`), hosted web in a tenant-root file behind an `/api` route, Android in a device file (OQ-125). The pattern is the global noise-word list: `frontend/src/lib/api/global-noise-words.ts:133-169` (READ: `getDesktopBridge()` checked at call time, else `fetch`; native via `createTransport`), `frontend/src/lib/models/global-noise-words.ts`, `electron/CLAUDE.md:23`.
- A word in either list (project or user) is correct (FR-78).
- On a paired device, adding a word defaults to the project list; adding to the user list happens from the desktop window (OQ-128).
- The user list's view and remove section is in App Settings, following the global noise-word list (`AppSettingsDialog.tsx`, `NoiseWordsSettingsTab.tsx`; F94-4 option d).

Facts this feature builds on (all READ):

- The known-word set takes only `projectWords`, `ignoredWords` and `aliasTable` (`frontend/src/lib/spelling/known-words.ts:23-30`), built in `frontend/src/hooks/useSpellCheck.ts` from `selectSpellingLists` and the alias table; it has no user-list input.
- The checker is `active` only when the project lists and the alias table are loaded, the engine has not failed and the browser is supported; any failure pauses it with a reason (`frontend/src/store/spellingAvailabilitySlice.ts`, `selectSpellCheckerState`).
- The flagged-word menu has "Replace with", "Ignore", "Add to project dictionary" (`frontend/components/Editor/EditorContextMenu.tsx:657-725`); both list writes are thunks with no optimistic update and a toast on failure (`:365-395`).
- Project lists are bounded at 100 UTF-16 units per word and 5,000 words per list (`frontend/src/lib/models/project-spelling-core.ts:33,36`).
- The window is classified apart from a paired device by the `x-getwrite-classification` header, `off` and `window` being exempt from limits (`frontend/src/lib/sharing/limits-check.ts:21-35`; `classify-request.ts`). The route `frontend/app/api/global-noise-words/route.ts` shows no `checkLimit` call (grep for `checkLimit`, 2026-10-26, no match). The desktop IPC channels `getwrite:global-noise-words-get`/`-set` DO check the sender (`assertTrusted` / `isTrustedSender`, `electron/src/noise-words-ipc.ts:44-63`, wired at `electron/src/main.ts:454-468`); the only payload check is "array of strings". The statement in `electron/CLAUDE.md:30` that they do no sender check is stale (docs fix in Stage 6, not in this feature's spec). The global noise-word transport replaces the whole list on every write (`global-noise-words.ts:61,188-190`).
- Release note `specs/features/spell-checker/release-note.md` ("Known gaps") names the missing user list. This feature removes that gap.

## Overview

A writer who adds a word to the spell checker adds it to one project. A term used in every project (a place name, a coined word, a surname) is flagged again in each new project until it is added there too. This feature gives the writer a user word list, kept on the device and shared by every project opened on it, so a word added once is treated as correct everywhere on that device. It completes the two-list requirement of FR-78 and removes the known gap stated in Feature 95's release note.

## Goals

- A word in the user list is not underlined in any project opened on the same device and platform.
- A writer can add a flagged word to the user list from the flagged-word menu in the desktop window, on hosted web, and on Android.
- A writer can see every word in the user list and remove any of them from App Settings.
- On a paired device, adding a word never writes the user list by default and never fails silently.
- A user-list problem is never shown as "no words": it is visible, and never hides misspellings or flags correct words without saying so.

## Non-goals

- Syncing the user list between desktop, hosted web and Android (decided: not synced).
- An Ignore list at user level (FR-78 names two lists, project and user; a user-level Ignore is not in scope; see OQ-3).
- Changing the project word list, the project ignore list, the entity rule or the app-wide switch.
- Exporting, compiling or backing up the user list (see OQ-8).

## User stories

- US-1: As a writer who uses the same names and terms in every project, I want to add a flagged word to my own dictionary so that it is not flagged again in any other project on this device.
- US-2: As a writer, I want to see and remove the words in my own dictionary from App Settings so that a mistaken add does not stay until I edit a file by hand.
- US-3: As a writer using a paired device on the home network, I want to have adding a word default to the project list so that I never write to a list that lives on another device by mistake.

## Functional requirements

1. FR-1: The user list MUST be stored per platform with no sync between platforms: desktop `userData` reached through `getDesktopBridge` IPC, hosted web in a tenant-root file behind an `/api` route, Android in a device file; a client transport MUST resolve to the correct store at call time following `global-noise-words.ts`. [US-1]
2. FR-2: A word MUST be validated at the store boundary on every platform by the same rule as a project-list word (string, trimmed, NFC, no whitespace or control character); the length and size limits are per FR-13. An invalid word MUST be refused with an error and the list left unchanged. [US-1]
3. FR-3: The checker's known-word set MUST include the user list, so a word in the user list, the project list, or both is not underlined, matched as project-list words are (ignoring case, apostrophes normalised). [US-1]
4. FR-4: The user list MUST be loaded once per app session (lazily, per FR-23) and shared by every open project and editor; an add or remove MUST change the underlines of every open editor without reopening a project, and MUST NOT be applied optimistically. [US-1] [US-2]
5. FR-5: A failure to read the user list MUST NOT be rendered as an empty list. What the checker does in that case is per FR-15 and FR-16; in every case the failure MUST be visible as a toast and in the status line under the spelling switch in App Settings, with the reason. [US-1]
6. FR-6: The flagged-word menu MUST show "Add to my dictionary" beside "Add to project dictionary" in the desktop window, on hosted web and on Android. A successful add MUST stop the word being underlined in every open editor; a failure MUST show a toast and leave the word underlined. [US-1]
7. FR-7: On a paired device, "Add to project dictionary" MUST remain the default add and "Add to my dictionary" MUST be absent or refused (see FR-11 and FR-12). A refusal MUST show a visible message and write nothing. [US-3]
8. FR-8: App Settings MUST gain a "My dictionary" section, following `AppSettingsDialog.tsx` and `NoiseWordsSettingsTab.tsx`, showing the count and the words sorted ignoring case, an empty-state sentence, and per word a remove button whose accessible name includes the word. Removal MUST move keyboard focus to the next word's remove button, else the previous, else the section heading. [US-2]
9. FR-9: Storybook stories (empty, populated, load failed, remove failed) and an a11y test with `runAxe` for the section and for the menu entry MUST exist and pass. [US-2]
10. FR-10: `docs/features/spell-checker.md` MUST be updated: the user list, where it is stored on each platform, the paired-device rule, that it is not synced, and that it is not part of any export, compile or backup (FR-20); the "no user-level list" known gap MUST be removed there and in the feature list entry. [US-1]

11. FR-11: The client MUST use the sharing-limits role already provided by `SharingLimitsContext` (`GET /api/sharing/limits`) to decide whether the user list is offered. Role `paired` MUST hide "Add to my dictionary" and the add path in the "My dictionary" section; role `exempt` (desktop window, sharing off, hosted web) MUST show them; on Android (no `/api`, no proxy) the user list MUST always be allowed. A paired device MUST NOT load the user list, and the user list MUST NOT be an input to the checker's gate there. [US-3]
12. FR-12: The user-list route MUST refuse a paired caller's write and read regardless of the UI, following the always-refused passphrase-creation precedent: its own message, HTTP 403 with the `{ error, limit }` shape built by `refusalFor`, and no new `LimitKey` owner switch (`limits-check.ts:20-28,44-49,66-85`, `limits-copy.ts:34`, `app/api/encryption/route.ts:204`). The exact wording MUST be checked against the encryption route during implementation. [US-3]
13. FR-13: The user list MUST reuse the project-list bounds, 100 UTF-16 units per word and 5,000 words, enforced at the store boundary on all three platforms (`project-spelling-core.ts:33,36`); a word or add over a bound MUST be refused with an error and the list left unchanged. [US-1]
14. FR-14: The user list MUST be add-only in scope: there MUST be no user-level Ignore list (FR-78); the flagged-word menu's "Ignore" stays project-level. [US-1]
15. FR-15: The user list MUST be a third input to `selectSpellCheckerState` on the desktop window, hosted web and Android (`spellingAvailabilitySlice.ts:139-153,161-214,226-249`). A failed read MUST pause the checker with a new reason kind (for example `user-list-failed`, message "Your dictionary could not be loaded (reason).") and raise a toast through `startUnavailableToasts`; a not-yet-loaded list MUST give `loading` (paused, no toast). [US-1]
16. FR-16: When the user-list read has failed, the writer MUST be offered "Retry" and "Continue without my dictionary". "Continue without my dictionary" MUST be a session-only override that un-pauses the checker with the project lists only, and MUST keep a persistent visible notice that the writer's own words are not applied (the status line under the spelling switch and/or a persistent banner, not a dismissible-only toast). The override MUST last until reload or a successful re-read, and MUST write nothing to the file. [US-1]
17. FR-17: A word MAY be in both the project list and the user list; there MUST be no move between lists, and removing a word from one list MUST leave the other unchanged. [US-1] [US-2]
18. FR-18: Within one window the shared Redux store MUST update every open editor (FR-4). Other tabs and windows MUST re-read the user list when they regain focus (`visibilitychange`). The desktop has a single `BrowserWindow` (`electron/src/main.ts:730`); the window and a paired device read different stores, which is not bridged. [US-1] [US-2]
19. FR-19: Storage and transport. Android MUST use a new device file separate from `/global-noise-words.json` (`native-global-noise-words.ts:56`). Hosted web MUST use a per-tenant file at `<tenantRoot>/<name>.json` resolved from `StorageContext` via `withStorageContext` and never from the client (`models/global-noise-words.ts:46,72-76`; route `:4-17`). The transport MUST expose idempotent `addUserWord` and `removeUserWord`, not set-whole-list; the store MUST do read-modify-write (the server under `withFileLock`, Electron main synchronously in the handler, Android in the native backend) and MUST return the persisted list, which the client stores as the stored value with no optimistic update. Responses MUST be validated through `lib/api/schemas.ts` with `reportTransportValidationFailure`. [US-1] [US-2]
20. FR-20: The user list MUST NOT be part of any export, compile or backup; it is a per-device store outside every project, and the documentation MUST say so (FR-10). [US-1]
21. FR-21: A word in the user list MUST be removable only from App Settings; no flagged-word menu or underline offers removal. [US-2]
22. FR-22: The user-list IPC channels MUST check the sender first (`assertTrusted` / `isTrustedSender`) and then validate each word per FR-2. [US-1]
23. FR-23: The "My dictionary" section MUST be available with the spelling switch off. The list MUST be loaded lazily on first need (the switch turning on, or the section opening), not at startup when the switch is off. A read failure on the section path MUST be shown in the section (FR-5); the gate and toasts MUST apply only while the checker is wanted. [US-2]
24. FR-24: While the spelling switch is on, the editor footer MUST show a compact `role="status"` cue about the spell checker. When the checker is paused for a failure (any unavailable kind in `selectSpellCheckerState`: `lists-failed`, `alias-table-failed`, `user-list-failed`, `engine-failed`, `browser-unsupported`) it MUST show "Spell check paused", expose the reason message the slice already produces as text available to assistive technology (and as a tooltip), and offer a "Spell check settings" button that opens the existing App Settings dialog. When the checker is active but the writer's own words are not applied ("Continue without my dictionary", `selectUserWordsNotApplied`) it MUST show the quieter "Your words aren't applied". It MUST show nothing when the checker is active, when it is only loading, or when the switch is off, and MUST NOT use red. [US-1]

## Amendment (2026-10-26): editor cue for a paused or partly applied checker

Added after Task 23 (`specs/features/user-word-list/experiments.md`, "Defects found" item 4). Measured in the real app: when the checker is paused for a failure the editor shows no underlines and nothing in the editor says why; the only cues were the App Settings status line and a load-time toast. After "Continue without my dictionary" the editor likewise says nothing. FR-24 adds the cue; it changes no gate, no reason and no toast. The "Spell check settings" action reuses the single `AppSettingsDialog` instance in the app shell through a window event (`src/lib/app-settings-open.ts`), so no second dialog is created. Implemented by Task 25.
