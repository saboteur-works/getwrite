# Feature 93: A save never puts back an older value, and overlapping server writers keep each other's change

Source: `specs/product/getwrite.features.md`, "### Feature 93" and the resolved F93-1 to F93-5 group in "Open Questions" (Gate 2, 2026-10-24); `specs/product/getwrite.md` FR-77, US-32 and resolved OQ-115 to OQ-119 (Gate 1, 2026-10-24). Branch suggestion: `fix/stale-saves-and-index-races`. Depends on: none (Feature 92, the per-file lock, is merged; this feature is its recorded follow-up). Measurements for this feature: `specs/features/stale-saves-and-index-races/experiments.md` (created by the first task; not yet written). Scope note. This spec is longer than the skill's usual 500-word limit. The feature has four parts (sidecar allowlist, features-route sends, two carried settings checks, index and backlinks races) that share one idea (no save or writer undoes a change it did not make), the same files and one test approach (measure first, fix only what reproduces). The parts can be built and merged as separate pull requests inside the branch; none depends on another.

Settled decisions, not reopened here (owner, Gate 1 and Gate 2, 2026-10-24; product spec OQ-115 to OQ-119, features F93-1 to F93-5):

- Sidecars (OQ-115, OQ-116): `updateSidecarCore` (`frontend/src/lib/models/resource-crud-core.ts`) accepts only an allowlist of client-writable keys, fail-closed (`docs/standards/security.md`), in place of the denylist `SERVER_DERIVED_SIDECAR_KEYS`. `updatedAt`, `name` and `dismissedNoiseTerms` are server-owned: a client value is ignored. `wordCount` and `file` are already dropped; `orderIndex` and `folderId` are already re-applied from the stored sidecar by `mergeSidecarUpdate`. Writer-owned and stored as sent: `entityKind`, `aliases`, `wordCountGoal`, `resourceSubtype`, `userMetadata`. No key-by-key `userMetadata` merge, no client-sends-changed-keys, no version check. Known gap by decision: a stale `userMetadata` is replaced wholesale.
- The allowlist is needed at one path only, `updateSidecarCore` (F93-1). No caller relies on it to rename or to set `updatedAt` or `dismissedNoiseTerms`; there are two production callers (F93-2), so no caller migration is needed.
- Features route (OQ-117, F93-5): `POST /api/project/features` keeps four whole blocks (`features`, `relationshipTypes`, `subtypes`, `organizerCardBody`) with last-write-wins per block, documented. The fix is preventing overlapping sends from one window. Between two devices the newest write per block wins; that narrowing of OQ-118's "newest write per key" was accepted at Gate 2.
- Editor config (`editor-config-core.ts`) and entity-graph settings (`entity-graph-settings-core.ts`) are carried checks: measured first; a reproduced revert is fixed in this feature only if small (a key-level merge inside the existing `updateProjectJson` mutate), otherwise a follow-up with the measurement recorded (F93-3, option b).
- Class B (OQ-119, F93-4): mention index and backlinks get race tests in the manner of PR #300; only what reproduces is fixed, as one locked load, change and save. An atomic `computeBacklinks` recompute is a recorded follow-up, widened into this feature only if a race test reproduces a loss one locked step cannot close. The inaccurate "inside one `withMetaLock`" comments are corrected either way.
- Two devices (OQ-118): newest write wins, no conflict UI, consistent with Feature 79. A version check is a recorded follow-up.

## Overview

A writer who edits a resource's metadata can find that the resource's name, last-modified time or dismissed noise-term list has gone back to an older value, because the save posts a whole copy of the resource that was loaded earlier and the server stores every key in it. On 2026-10-23 a stale copy sent after a canonical save left the stored last-modified time at the older value in 100 of 100 repetitions. The same kind of loss may exist where a settings screen sends two quick edits from one window, where an editor or entity-graph setting is saved from an older copy, and where the mention index or the backlinks file is loaded, changed and saved by two writers at once. This feature makes the server keep what it owns when a client sends an older copy, stops one window from sending two overlapping settings writes, and measures the remaining cases before changing any of them. It does not add a conflict screen or a version check.

## Goals

- A sidecar save from a client copy never changes `updatedAt`, `name` or `dismissedNoiseTerms`; only the five writer-owned keys (`entityKind`, `aliases`, `wordCountGoal`, `resourceSubtype`, `userMetadata`) are stored from a client.
- One window never has two overlapping writes to the same features-route block in flight, so a quick second edit does not drop the first.
- Each cause-unknown case (features-route loss, editor config, entity-graph settings, mention index, backlinks) is measured first, and a fix is made only for a loss that reproduces.
- A mention-index or backlinks write that reproduces a lost change is one locked load, change and save, and no caller deadlocks on `withMetaLock`.
- The known gaps are written down: stale `userMetadata`, whole-block last-write-wins between two devices, and a non-atomic `computeBacklinks` recompute.

## Non-goals

- A version check, a "changed elsewhere" message or any conflict UI (OQ-115 option c, OQ-118; recorded follow-up).
- A key-by-key `userMetadata` merge, or a client that sends only changed keys (OQ-115).
- Per-item `relationshipTypes` or `subtypes` operations on the features route (F93-5); newest write wins per block.
- `relationships.json`, writing-log files and any index other than the mention index and backlinks: unknown, not promised.
- An atomic `computeBacklinks` recompute, unless a race test reproduces a loss one locked load, change and save cannot close (F93-4).
- Changing how a canonical save, a rename or a noise-term dismissal behaves; these are the dedicated writers of the three server-owned keys.
- More than one server process; a time limit or retry on a waiting write.

## User stories

- US-1: As a writer on deadline who edits a resource's metadata while the resource is saved, renamed or has a noise term dismissed, I want to be sure a metadata save never puts back an older name, last-modified time or dismissed-term list, so that I do not find a value I or the app had already replaced silently reverted. (Product US-32.)
- US-2: As a writer on deadline who changes project settings in quick succession, in one window or from two devices on my network, I want to have each setting I change kept, so that I do not find a relationship type, subtype, feature switch or editor setting silently missing. (Product US-32.)
- US-3: As a writer on deadline whose resource is saved, indexed or deleted while another of those happens, I want to have the mention index and the backlinks keep every change, so that I do not find a mention or backlink silently missing. (Product US-32.)
