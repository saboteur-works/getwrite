## Overview

A writer can open the Project Type Manager, edit a project type, and then cannot save it: the form marks "Unsaved changes" and the edits are gone on reopening. The Start Page and the manager both describe types the writer can create and delete. This feature adds a store of writer-made project types that survives restarts and updates, a Save and a Delete control, and one list of built-in and saved types that the new-project dialog, the desktop Word import and the command line all read. Separately, a writer who sets the body line height in Body Text Styles sees no change in their paragraphs, because every paragraph carries its own fixed leading of 1.5. This feature makes a paragraph the writer has not spaced follow the project's line height, keeps leading the writer did set, and enforces the 1.8 reading floor on the two project-level line height fields. Several causes are readings or hypotheses, so part 2 starts from a measurement on `main`.

## Goals

- A project type a writer creates or edits in the Project Type Manager can be saved, renamed and deleted, survives closing the manager, restarting the app and updating the app, and is never lost without the writer being told.
- The new-project dialog, the desktop Word import and the command line show and accept the same list of built-in and saved types, and a type saved a moment ago is in all three without a restart.
- Saving can never change a built-in type, can never reuse an existing type's id or name, and can never be steered to a file outside the saved-types directory by anything the client sends.
- A paragraph whose leading the writer has not set renders at the project's body line height, a change to that setting changes it, and opening a document changes no paragraph's leading.
- The 1.8 floor is refused with a visible reason in Body Text Styles and in the Project Type Manager's line height field, at the server as well as in the form, and an explicit paragraph leading below 1.8 is still allowed.

## Non-goals

- Android saved types and hosted multi-tenant saved types (both decided out for now). The native build keeps its static registry.
- Changing any project already made from a type: a project copies its type's settings at creation and keeps only the id (READ: `project-creator.ts:226-237` as cited by the product spec; the Start Page shows that id, `StartPage.tsx:1038`).
- Editing a built-in type in place, or deleting one.
- Per-workspace or per-project saved types; import and export of type files; sharing types between machines.
- A toolbar control to return a paragraph to unset (the command exists, `GetWriteParagraphLeading.ts:78-84`; no new control, per the features entry).
- A line height floor on an explicit paragraph leading, and any change to heading line heights.
- Rewriting stored `project.json` line heights that are already below 1.8 (there are no users; see FR-22).

## User stories

- US-1: As a novelist who has tuned a project layout, I want to save it as my own project type, rename it and delete it, so that I can start new projects from it without rebuilding the layout and without risk to the built-in types. (Product spec US-1.)
- US-2: As a writer who imports Word documents or uses the command line, I want to see my saved types offered there as well as in the new-project dialog, so that I choose from one list wherever I choose a type. (Product spec US-1.)
- US-3: As a writer who edits project types, I want to get a refusal with a stated reason, an unsaved-changes warning and a clear line between built-in and saved types, so that I never lose an edit or overwrite a type by accident. (Product spec US-1.)
- US-4: As a writer on deadline, I want to have my body line height setting space every paragraph I have not spaced myself, and to keep the spacing I chose for the paragraphs I did, so that the editor looks the way I configured it and reopening never undoes my choice. (Product spec US-9.)

FR-6: A read failure MUST NOT render as an empty saved list (`docs/standards/failure-visibility.md` §1). The list response MUST carry, besides the entries, a list of saved files that could not be used (`fileName` and a short reason: `unparseable`, `invalid`, `unreadable`) and a saved-directory status (`ok`, `not-configured`, `unreadable`). A saved directory that does not exist yet is `ok` with no entries (ENOENT is the one benign case, narrowed as `project-loader.ts` does); any other `readdir` error is `unreadable` and is shown, not folded to `[]`. The reason MUST NOT contain file contents or parser text. [US-3]

FR-7: There MUST be write routes under `frontend/app/api/project-types/`: `POST /api/project-types` (create a saved type; the body is the spec only), `PUT /api/project-types/[id]` (replace the saved type with that id) and `DELETE /api/project-types/[id]`. No route accepts a path, a file name, a directory or a `source` from the client. The file name is always `${id}.json` inside the configured directory, where `id` is first validated against the same pattern the schema uses (`^[a-z0-9-_]+$`, `schemas.ts:687`, `project-type.schema.json:8-12`) and a bounded length chosen so the file name is legal; a non-matching id is rejected with 400, never normalised (security.md §2). After the join, the route MUST assert the resolved path's parent is the saved directory. In `PUT`, the body's `id` MUST equal the path id or the request is a 400. The body MUST be parsed with `validateProjectType` (the Zod schema, `.strict()`, so unknown keys fail) and a body larger than a documented byte cap (proposed 256 KiB) MUST be refused before parsing. The writer-side gate and the loader's gate are the same function, so a file the route accepts is a file the resolver lists. A test posts `../x`, `a/b`, `%2e%2e`, an empty id, an over-long id, a body with an extra key, and a path id that differs from the body id, and asserts a 400 and no file written. The handlers are not wrapped by `withStorageContext` and say why in a comment, as the existing GET does (`route.ts:40-47`): the store is app-wide, not tenant data. There is no new paired-device limit (OQ-2, resolved (a)): once the pairing gate passes, a paired device may save, update and delete saved project types, as it may write the global noise words (`app/api/global-noise-words/route.ts:58-59`). The three write routes (and the changed GET) MUST be registered in the sharing gate-enumeration test(s) (`frontend/tests/unit/sharing-gate-enumeration.test.ts` and, if it enumerates routes, `sharing-gate-proxy.test.ts`), so a route added without a gate decision fails. [US-1]

FR-17: Leaving the manager with unsaved edits MUST NOT lose them silently. FR-18: A paragraph's leading MUST be representable as unset. The `paragraphLeading` attribute's default is absent (`null`); in a stored document unset MAY be written as `"paragraphLeading": null` or with the key absent, and both read as unset (owner, 2026-10-20; see Stage 6.5 findings). `renderHTML` emits no inline `line-height` for an unset paragraph, and `parseHTML` returns the element's inline `line-height` as a number when it is a finite number greater than 0 and other than the legacy "1.5", and absent otherwise (not "1.5"; `GetWriteParagraphLeading.ts:21,31-38`; see FR-20 for the stored form and the legacy rule). The attribute holds a JSON number when set. An unset paragraph's computed line height is then the stylesheet's `var(--gw-body-line-height, 1.8)` (`editor.css:25`). Acceptance (a browser-level test, since jsdom cannot compute layout): with the project's Body Text Styles line height 2.2, an unset paragraph's computed `line-height` is 2.2 times its font size and its inline style has no `line-height`; after the setting changes to 2.4, the same paragraph, without being touched, computes 2.4; with the setting absent it computes 1.8. A paragraph with explicit leading keeps its inline value in every one of those cases. [US-4]

FR-19: Opening a document MUST NOT change any paragraph's leading. The rule is therefore one pure function, `normalizeParagraphLeadingInDocument` (a module under `frontend/src/lib/`, with a single-value form `readParagraphLeading`), applied at every place a stored document is read, each of which MUST have its own test: (1) `TipTapEditor.tsx` at editor creation (`content:` at `:417`) and at the external content swap (`loadDocumentIntoEditor`, `:622`), which covers a resource opened and a revision opened; (2) `markdown-serializer.ts` `tallyNode` (`:101`), which reads stored JSON without an editor; (3) `menuBarState.tsx:61`, which reads the attribute from the live editor and uses the single-value form; (4) any further reader of `paragraphLeading` that a search of `frontend/`, `electron/` and `cli/` finds at implementation time, and the task list records the search. The normalisation is in memory only and marks nothing changed (FR-19). ## Open questions

Local numbers continue Feature 89's convention (the checker requires a sequence from 1). In the product register they continue from the highest existing question, OQ-102: this spec's OQ-1 to OQ-6 are OQ-103 to OQ-108. Resolved at Gate 3 (2026-10-19); each question below carries its resolution.

- OQ-1: How does the command line learn the saved-types directory when `GETWRITE_SAVED_PROJECT_TYPES_DIR` is not in its environment? The CLI is run from a terminal, not forked by Electron, so it gets no variable from the desktop app (READ: `cli/src/commands/project.ts` reads no environment; the import worker and server get theirs from `main.ts`). Options: (a) the CLI reads only the variable, and says so when it is unset (FR-16's minimum), so the CLI list can differ from the dialog's until the user exports the variable; (b) the CLI derives the desktop app's `userData` path per platform (macOS `~/Library/Application Support/getwrite-electron/project-types` is the path recorded in the project's working notes, not in the repository; Windows and Linux paths are UNMEASURED) when the variable is unset, which makes the lists agree but duplicates Electron's path logic outside Electron and may point at a development app's data; (c) a `--saved-types-dir <path>` option on the CLI in addition to (a), an explicit path typed by the person running the command (the one place a path from the caller is acceptable, since the CLI is the caller's own process). Which? — Impact: FR-4, FR-16; whether "the CLI shows the same list" (OQ-98) holds without user action. **Resolved (Owner decision, Gate 3, 2026-10-19):** (a) the CLI reads only `GETWRITE_SAVED_PROJECT_TYPES_DIR` and prints a notice when it is unset that saved types were not included; no derived userData path, no new flag. The CLI list can differ from the dialog's until the user exports the variable, as with `GETWRITE_PROJECTS_DIR`. Applied in FR-16.
- OQ-2: Should saving and deleting project types from a paired device on the home network be a sixth paired-device limit, or be allowed like other routes? READ: the five existing limits are project deletion, unlocking, locking, encryption changes and permanent deletion (CLAUDE.md glossary, Paired-device limits); the new routes write app-wide state on the host machine, not inside a project, and are not among them. Options: (a) no new limit (the pairing gate alone applies); (b) a sixth switch, on by default, global to paired devices, refusal HTTP 403 `{ error, limit }` as for the others; (c) refuse these writes from any non-window client. Which? — Impact: FR-7; the sharing limits store and its settings screen if (b). **Resolved (Owner decision, Gate 3, 2026-10-19):** (a) no new paired-device limit; saving, updating and deleting saved project types are allowed to paired devices once the pairing gate passes, like the global noise-words route (`app/api/global-noise-words/route.ts:58-59`). The new routes are registered in the sharing gate-enumeration test(s). Applied in FR-7.
- OQ-3: How are names compared for the clash rule? Ids need no rule: the pattern is lowercase (`schemas.ts:687`). A name is free text. Options: (a) exact string match; (b) after trimming surrounding whitespace, case-insensitive; (c) (b) plus collapsing internal runs of whitespace and ignoring accents. The owner decision (OQ-100) says "name" and does not say how near a match must be. — Impact: FR-8, the manager's refusal text. **Resolved (Owner decision, Gate 3, 2026-10-19):** (b) names compare after trim and case-insensitively, matching `normalizeSubtypeLabel`'s convention. Applied in FR-8.
- OQ-4: How are a pre-change stored "1.5" and a post-change explicit 1.5 told apart on reopen? READ: the extension's default is "1.5" and `onCreate` stamps it on every paragraph (`GetWriteParagraphLeading.ts:21`, `TipTapEditor.tsx:483-491`), and `markdown-serializer.ts:101-103` and its tests treat "1.5" as the default in stored JSON, so a stored file written by the current code is expected to hold "1.5" on every paragraph (UNMEASURED; FR-1 reads it). The owner decisions (OQ-102) say "1.5" reads as unset and a new explicit 1.5 is kept; for a string-valued attribute these cannot both hold unless something besides the value distinguishes them, and the stored JSON passes through no per-attribute parse hook. Options: (a) a document-level format marker written on save (for example a field on the document or the resource sidecar); a document without it is legacy, its "1.5" is read as unset once, and the marker is written by the next real save; (b) store an explicit choice in a different form from the legacy one (a number rather than a string, or a distinct value such as "1.50"), so the legacy string is unambiguous; (c) a one-time rewrite of every stored document at first launch of the new version, which the owner's zero-users statement permits; (d) accept that a deliberate 1.5 is read as unset forever (this contradicts "a new explicit 1.5 is kept" and is listed only for completeness). Which? — Impact: FR-20, FR-24, FR-19 (what "unchanged" means for a legacy value), and the choice between a fix and a regression test in FR-1. **Resolved (Owner decision, Gate 3, 2026-10-19):** (b) an explicit paragraph leading is stored as a JSON number, a form the legacy stamp never produced; on load the legacy string "1.5" reads as unset and any other legacy string value is still honoured as explicit; `setParagraphLeading` normalises at set time. Evidence (triage, READ): stored JSON enters the editor as JSON (`EditView.tsx:429`, `TipTapEditor.tsx:417`) and skips `parseHTML` (`GetWriteParagraphLeading.ts:32-35`); revisions also hold the legacy "1.5". Applied in FR-1, FR-18, FR-20, FR-24.
- OQ-5: Which forms of line height does the 1.8 floor accept in the project field, and is there any bound on an explicit paragraph leading beyond "a finite number greater than 0"? The schema's description says "Unitless multipliers recommended" (`project-type.schema.json:94-97`) and the field is a free string; "normal", "150%", "28px" and "1.8em" are all valid CSS and cannot be compared with 1.8 without the font size. Options: (a) unitless numbers only, at least 1.8, and no upper bound; (b) (a) plus an upper bound (a value to be named); (c) also accept `%` and `em` and compare as multipliers, still refusing `px` and `normal`. For the explicit paragraph leading: (d) the minimum of FR-21 only; (e) a documented lower bound above 0 (a value to be named) so a near-zero value cannot hide text. — Impact: FR-21, FR-22, FR-23. **Resolved (Owner decision, Gate 3, 2026-10-19; field rule resolved from evidence (triage), presented to the owner at Gate 3):** explicit paragraph leading: any finite number greater than 0, no other bound. Project line height field (Body Text Styles and Project Type Manager): unitless numbers only, at least 1.8, no upper bound; `normal`, `%`, `em` and `px` refused; empty means 1.8 (evidence `project-type.schema.json:94-97`, all six built-ins "1.8", `editor-body-settings.ts:14,25`). Applied in FR-21, FR-22, FR-23.
- OQ-6: When the project line height is below 1.8, does the form refuse the save with a message, or correct it to 1.8 and say so? Refusal keeps the writer's input and shows why; correction saves a value the writer did not type. Both are visible. FR-22 is written for refusal because a silent change to a typed value is the failure-visibility pattern this repository avoids, but the owner's decision says "enforced" without saying which. Options: (a) refuse; (b) correct to 1.8 and show a message; (c) refuse in the form and clamp at the server for any other caller. — Impact: FR-22, FR-23 (the message text and whether Save is disabled). **Resolved from evidence (triage), presented to the owner at Gate 3 (2026-10-19):** refuse, do not clamp; the form shows an accessible error keeping the typed value, and the core and the route return 400 (evidence `frontend/CLAUDE.md` "reject (not clamp)", `MentionHighlightDurationField.tsx:48-51`, `editor-config-core.ts:106-111`, `docs/standards/failure-visibility.md` §1).
