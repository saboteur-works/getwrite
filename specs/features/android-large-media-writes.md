## Overview

A writer using GetWrite on Android can today lose their place when they add a large audio, image or attachment file: on a Pixel 7 Pro, 50 MiB and 100 MiB adds crash the app with an out-of-memory error, while 25 MiB works, and the product has stated a 100 MB cap that no device run ever measured. This feature makes adding, replacing, creating and restoring large media on Android complete without crashing, up to a size limit that a device run on a Pixel 7 Pro verified, tells the writer plainly when a file cannot be added and leaves nothing behind when a write fails, and makes the product, its documentation and its messages state only that measured limit. Desktop, hosted web and paired devices are not changed.

## Goals

- On Android, attachment add, attachment replace, audio and image resource create and Trash restore complete without crashing the app for any size up to the Android cap, each verified on a Pixel 7 Pro at the cap and at one size above it.
- The Android cap is a size that a device run on a Pixel 7 Pro verified (100 MiB if the chunked write passes there twice, otherwise the highest of 30, 35, 40 and 45 MiB that passes twice), and no document, message or limit states an Android cap or throughput that no device run measured.
- A write that cannot complete on Android fails with a readable message and leaves no attachment file, sidecar entry or resource directory.
- Preview and playback of a stored large file are checked on the device up to the cap, and compile and export at large sizes are listed as not verified.
- Desktop, hosted web and paired devices keep the 100 MB cap, the upload and attachment routes and their results, pinned by a test.

## Non-goals

- Importers (Scrivener, DOCX) on any platform; no Android import path was found.
- Android image-resource display ("Unable to load image.", POS task_fed2906c) and OQ-170 of the product spec.
- A second device, a device-class matrix, or a safety margin below the verified cap (F104-2).
- Verifying compile or export of large media on Android (OQ-173).
- Any new control; the existing add, replace, create and restore actions are the interface.
- Raising the 100 MB cap on desktop, hosted web or a paired device, or changing a throughput claim for them.

## User stories

- US-1: As a writer using GetWrite on Android, I want to add, replace and restore a large attachment or audio or image file without the app crashing, and to be told plainly when a file cannot be added, so that I never lose my place or my project to a file that is too big for the device. (Product US-46.)

### The write funnel and its failure behaviour

2. FR-2: Before the funnel is changed, a run on the device MUST log the payload length of the `Filesystem.writeFile` call for a 25 MiB add (the experiment product FR-141 names), and the chunked-write experiment of FR-1 MUST be run through the existing adapter and `capacitor-filesystem-real.ts` wrappers (`writeFile` of the first piece, then `appendFile` in pieces). The first piece size tried MUST be 4 MiB (4,194,304 bytes), and the piece size MUST be recorded on every run; the piece size the experiment settles on is the one the funnel uses. The whole-file copy `Buffer.from(input.fileBytes)` made in the WebView by the cores (`source-attachments-core.ts:284`, `:469`; `resource-persistence.ts:188-191`) happens before the funnel and is part of what the 100 MiB run tests; the experiment MUST NOT be read as testing the funnel alone. Each result MUST be recorded as an observed value with the build, device, size, piece size and run number. A cause MUST be written as a cause only where an experiment discriminated it from the alternatives; a passing chunked write alone MUST be recorded as "the chunked write passed at N bytes", not as proof that the single bridge message was the cause. (Product FR-141, FR-143; Resolution, OQ-1 and OQ-2, owner, Gate 3, 2026-11-08: both are settled by this experiment, and no cause is named by it.) [US-1]
3. FR-3: On Android, adding an attachment to a Source, replacing an attachment, creating an audio or image resource, and restoring an attachment or a media resource from Trash MUST NOT crash the app for any size up to the Android cap. The fix MUST be at the single shared write funnel, `capacitorFsAdapter.writeFile`, so every path that writes bytes takes it; no call site in `source-attachments-core.ts` or `resource-crud-core.ts` MUST gain its own chunking. A write of a small file, including every text write that goes through `atomicWriteFile`, MUST produce the same stored bytes as before. The funnel MUST chunk only when the buffer exceeds one piece; at or below one piece it MUST issue exactly one `fs.writeFile`, as today, and the threshold MUST be the piece size the experiment picks, with no second constant. Trash restore (OQ-7, traced) is a plugin rename and does not pass through the funnel; the funnel fix therefore covers add, replace and create, and restore is covered by FR-4's device run. (Product FR-141; Resolution, OQ-10, owner, Gate 3, 2026-11-08.) [US-1]
4. FR-4: Each path of FR-3 MUST be verified once on a Pixel 7 Pro at the largest size the Android cap accepts and at one size above it, with the build, device, size and result recorded as a measurement in the experiments file. At the cap the path MUST complete and the stored file MUST have the exact byte length. At one size above the cap the path MUST end in the refusal or failure of FR-5, and the app MUST NOT crash. Trash restore was traced (OQ-7, reading, Gate 3 triage, confirmed by owner): a plugin rename (`trash.ts:2096-2109` attachments; `:1027`, `:1042` resource content and revisions), with only the sidecar JSON written through `atomicWriteFile` (`:1007-1013`), so no file bytes cross the bridge. The first task MUST record that trace in the experiments file, and the device run for restore MUST still be made once with a large trashed item and recorded as such, because rename of a large file on Android is unmeasured. Importers are not run. (Product FR-141; Resolution, OQ-7, owner, Gate 3, 2026-11-08; a dated note at product FR-141 points here.) [US-1]
5. FR-5: On Android, a write of an attachment or media file that cannot complete MUST fail visibly, with a message the writer can read, and MUST leave no partial state: no attachment file, no sidecar entry, and no resource directory from the failed write. A refusal before the write starts, for a size the device cannot take, is allowed if the message says so. Cleanup design (Resolution, OQ-3, owner, Gate 3, 2026-11-08): the adapter's chunked `writeFile` MUST best-effort delete the target when any piece fails, swallowing only the cleanup error, narrowly, and rethrowing the original error (`docs/standards/failure-visibility.md`); `uploadMediaResourceCore` (`resource-crud-core.ts:305`) MUST remove the run-created resource directory when `writeResourceToFile` throws (the create path has no cleanup today); the add and replace `catch` blocks are unchanged. Delete-on-failure is chosen, not temporary-name-and-rename. Known limit (Resolution, OQ-4, owner, Gate 3, 2026-11-08, option (a)): a process kill in the middle of a multi-piece write can leave a file no sidecar lists (add already writes the file before the sidecar entry, `source-attachments-core.ts:284-290`); that file stays on disk until the Source is deleted, there is no sweep, and the limit MUST be listed in the experiments file and the PR. A size above the cap MUST be refused before the file's bytes are read: the size check MUST come before `await file.arrayBuffer()` in `native-source-attachments-backend.ts:42` and in the equivalent native resource-upload backend; the first task MUST confirm that the native resource-upload backend and the file pickers check size before reading (Resolution, OQ-11, owner, Gate 3, 2026-11-08). The refusal wording is FR-6's. This MUST be tested at the adapter level with a fake plugin that fails at the first, a middle and the last piece, for add, replace and create, asserting that no file, sidecar entry or resource directory remains, that a failed Replace restores the previous attachment, and that the original error is the one raised, not a cleanup error. It MUST be observed once on the device (for example by writing above the cap through a path that reaches the funnel, or by the refusal) and recorded. (Product FR-142.) [US-1]

## Open questions

All product questions OQ-171 to OQ-174 and the feature-breakdown questions F104-1 and F104-2 are resolved and are not reopened. OQ-1 to OQ-12 below were raised by this spec and are all resolved at Gate 3 (2026-11-08); each resolution is folded into the requirement named in Impact. Evidence-resolved items are readings, confirmed by the owner, not runs. No question remains open.

- OQ-1: What piece size does the chunked write use? The only sizes in the evidence are the 25 MiB file that worked and the example "4 MiB pieces" in the experiments file; no measurement chose one. — Resolution (owner, Gate 3, 2026-11-08): settled by the FR-1/FR-2 experiment, starting at 4 MiB pieces; the piece size is recorded every run; a pass is recorded as "the chunked write passed at N bytes" with no cause named. The cores' whole-file `Buffer.from(input.fileBytes)` copy in the WebView (`source-attachments-core.ts:284`, `:469`; `resource-persistence.ts:188-191`) happens before the funnel and is part of what the 100 MiB run tests. — Impact: FR-1, FR-2, FR-3.
- OQ-2: Does `appendFile` per piece avoid the large allocation? This is the experiment of FR-1, not a settled fact. It also leaves open where the limit sits (the JS-side base64 string of the whole buffer made by `toString("base64")`, the single bridge message, or the Java-side parse), and whether peak WebView memory outside the bridge (the picked file's bytes, `Buffer.from(input.fileBytes)` in the core, the encoded string) fails before the bridge does. — Resolution (owner, Gate 3, 2026-11-08): settled by the FR-1/FR-2 experiment, recorded as in OQ-1; no cause is named by a pass, and the whole-file copy before the funnel is part of what the run tests. — Impact: FR-1, FR-2, FR-3, FR-6.
- OQ-3: How is a partial file cleaned up if a piece fails? Add and replace set `isFileWritten` only after `writeFile` returns, so a throw midway leaves a file the `catch` does not remove; whether `writeResourceToFile` cleans a failed binary write was not read. Whether the cleanup belongs in the adapter (write to a temporary name and rename, as `atomicWriteFile` does), in each core, or in both is not decided. — Resolution (owner, Gate 3, 2026-11-08): the adapter's chunked `writeFile` best-effort deletes the target when any piece fails, swallowing only the cleanup error narrowly and rethrowing the original (`docs/standards/failure-visibility.md`); `uploadMediaResourceCore` (`resource-crud-core.ts:305`) removes the run-created resource directory when `writeResourceToFile` throws (reading, Gate 3 triage, confirmed by owner: the create path has no cleanup today, the binary is written at `resource-persistence.ts:188-191` before the sidecar at `:195`); add and replace `catch` blocks are unchanged. Delete-on-failure, not temp-and-rename. — Impact: FR-3, FR-5.
- OQ-4: Does a process kill or crash in the middle of a multi-piece write leave a partial file that nothing removes on relaunch? Today's observed "no partial state" after an out-of-memory crash is because the single write had not started; a multi-piece write changes that. Whether relaunch cleanup, a temporary-name convention, or acceptance of an unlisted file is wanted is not decided. — Resolution (owner, Gate 3, 2026-11-08, option (a)): accept that a process kill mid-write can leave an unlisted file (add already writes the file before the sidecar entry, `source-attachments-core.ts:284-290`); listed as a known limit: the orphan stays on disk until the Source is deleted; no sweep. — Impact: FR-5.
- OQ-5: Do reads above 25 MiB need `readFileInChunks` (or another path)? Reads decode a whole base64 string in the WebView and were measured at 25 MiB only. If a read fails at a size the write accepts, whether the cap is lowered to the read-passing size, the read path is changed in this feature, or the file is stored but not previewable is not decided. — Resolution (owner, Gate 3, 2026-11-08): settled by the FR-8 read check at the cap; `readFileInChunks` exists (plugin 8.1.2, native only) but is not added now; if the read fails at a size the write accepts, the cap drops to the read-passing size, and a read-path change returns to the owner as new scope. — Impact: FR-8, FR-6, FR-1.
- OQ-6: Where does the Android-only cap live, and how does the interface learn it? `MAX_MEDIA_FILE_BYTES` is one constant in `media-validation.ts` and the client and the cores share it. How Android is detected inside code that must stay unchanged for desktop and hosted web, and how the message and the file picker read the value, is not decided. — Resolution (owner, Gate 3, 2026-11-08): a pure resolver beside `MAX_MEDIA_FILE_BYTES` in `media-validation.ts` (for example `maxMediaFileBytes()`) returns the Android cap when `resolveRuntime() === "native"` (`store/transport/runtime.ts:24`) and 104,857,600 otherwise; `validateMediaFile`, `validateAttachmentFile` and the message read it; `MAX_MEDIA_FILE_BYTES` stays for FR-9's pin test and `next.config.mjs`; the first task confirms the native build inlines `NEXT_PUBLIC_GETWRITE_RUNTIME` in that shared module. — Impact: FR-6, FR-9.
- OQ-7: What is Trash restore's byte path? The reading found `rename` for attachments and resources and no `writeFile` of the bytes; if confirmed, restore does not reach the funnel and the product wording "restore of a large item takes the fix" needs a different device check. Not traced end to end. — Resolution (reading, Gate 3 triage, confirmed by owner): traced: restore is a plugin rename (`trash.ts:2096-2109` attachments; `:1027`, `:1042` resource content and revisions; only the sidecar JSON is written, via `atomicWriteFile`, `:1007-1013`); no file bytes cross the bridge. FR-4's device run is kept, because rename of a large file on Android is unmeasured. A dated note (2026-11-08) at product FR-141 says restore is a rename and does not pass through the write funnel, and points here. — Impact: FR-3, FR-4.
- OQ-8: How is the ladder read when results are not monotonic or none pass? The decision says the highest ladder size that passes both runs is the cap; it does not say whether the ladder is run in full or stops at the first failing size, what happens if 45 MiB passes and 40 MiB fails, or what the cap is if no ladder size passes both runs (25 MiB was added once by the single write, not run twice). — Resolution (owner, Gate 3, 2026-11-08, option (a)): run the ladder ascending; stop at the first size that fails either run; the cap is the last size before it that passed both runs; sizes above a failure are never the cap; if no ladder size passes both runs, stop and return to the owner (no 25 MiB floor). — Impact: FR-1, FR-6.
- OQ-9: How does an encrypted project on Android behave at large sizes? `encryptingAdapter` seals a whole file in one call and has its own `appendFile`; whether a chunked write through it is correct, whether sealing adds memory beyond the file size, and whether an encrypted project has a lower cap was not measured. — Resolution (reading, Gate 3 triage, confirmed by owner): no encrypting adapter is bound on native (`native-bootstrap.ts:60-83` binds the plain `capacitorFsAdapter`); no encrypted-project case; listed under Not verified as a reading. `isEncryptionAvailable`'s doc text claims native Android, which the bootstrap does not match. — Impact: FR-3, FR-4, FR-6, FR-10.
- OQ-10: Do all writes go through the chunked path, or only those above a threshold? Every write, including small text, uses `capacitorFsAdapter.writeFile` today; the size above which chunking starts, and whether small writes stay a single call, is not decided. — Resolution (owner, Gate 3, 2026-11-08): chunk only when the buffer exceeds one piece; at or below one piece, one `fs.writeFile` exactly as today; the threshold is the piece size the experiment picks; no second constant. — Impact: FR-3.
- OQ-11: When is a size above the cap refused, and with what words? FR-5 allows a refusal before the write starts; whether the refusal happens before the file is read into memory, and the exact wording and unit, are not decided. — Resolution (owner, Gate 3, 2026-11-08): wording "File exceeds the N MB limit." as `media-validation.ts:153-155` (MiB arithmetic, "MB" label, kept); the size check moves before `await file.arrayBuffer()` in `native-source-attachments-backend.ts:42` and the equivalent native resource-upload backend; the first task confirms the native resource-upload backend and file pickers check size before reading. — Impact: FR-5, FR-6.
- OQ-12: Is the write duration at the cap recorded or stated as a throughput? The duration of a chunked 100 MiB write is a new measurement; whether documentation states it, and in what words, is not decided. — Resolution (owner, Gate 3, 2026-11-08): always record durations in `experiments.md`; user docs state only the cap (FR-7, FR-13). — Impact: FR-7, FR-10.
