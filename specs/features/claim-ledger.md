## Overview

A writer gathering evidence for nonfiction, true crime or folklore has no way to say, inside a manuscript, "this statement is a claim, here is the Source that backs it, and I have (or have not) checked it". Annotations and Source citations exist, but nothing marks a statement as a claim, records whether it is verified, or shows the claims of a whole project in one place, so an unsupported statement is found only by rereading. This feature adds a claim ledger as a switchable first-party module that is off by default: a writer marks a passage of a text resource as a claim, ties it to at most one Source, sets a status from a fixed list, and opens a project-wide Claims tab that shows each claim with its status, its Source or "unsourced", and whether its passage or Source is gone. A new project can start with the module on because a project type can declare which modules a new project starts with. Claims are annotations, never compiled or exported, and are claimed to work on Android and a paired device only after a recorded run.

## Goals

- A writer can mark a passage of a text resource as a claim with a statement of 1 to 5000 characters, link it to at most one Source, and set its status from Unverified, Verified, Disputed and Needs review, with the date the status last changed recorded.
- A writer can open one Claims tab and see every claim in the project with its statement, passage and resource, status, Source or "unsourced" and any detached or removed-Source state, filter by status and by sourced or unsourced, and open a claim at its passage.
- The claims module is off for every project with no entry for it (including every existing project), Sources stays on by default, and a new project created from a project type that declares the module on starts with it on.
- A claim is never silently dropped, hidden, changed in status or counted as verified: it survives copy, duplicate, paste, cut-paste, revision restore, Trash and restore, and encrypt and unlock, and is shown detached, with a removed Source, or as "could not be checked" instead of disappearing.
- Compile and export output is unchanged by claims, and the ledger is verified on a physical Pixel 7 Pro and a paired device with every unmeasured path listed.

## Non-goals

- Citation formatting, a bibliography or a compile option that renders citations (runway 11), folklore variants, motif or tale-type tagging, place and time (runway 14 to 16), a web clipper or PDF excerpt import (runway 13), and collaboration or assignment of a claim to another person (product FR-175).
- Several Sources per claim and a stance (supports, disputes, mentions); a claim backed by two Sources is two claims.
- Claims on Source attachments, on image or audio resources, or as freestanding ledger entries; a link from a claim to an entity.
- A writer-editable status list, seeding the status list from a project type, and status history (only the date of the last change is kept).
- Status or Source as query fields or smart-folder fields; a compile report of claims.
- A new paired-device limit switch (deleting a claim is already under `permanentDeletion`) and a generic module storage channel.
- Switching module state of an existing project from a project type, and any change to `config.statuses` (Document status).

## User stories

- US-1: As a writer gathering evidence for nonfiction, true crime or folklore, I want to mark a statement in my text as a claim, tie it to the Source that supports it and record whether I have verified it, so that I know which statements are backed by evidence and which are not. (Product US-49.)
- US-2: As a writer gathering evidence, I want to see all my claims and their status in one place and jump to the passage of any of them, so that I can find the unsourced and unverified ones before I publish. (Product US-49, FR-168.)
- US-3: As a writer, I want to leave the claim ledger off until I switch it on, and to start a new project of a research-minded type with it already on, so that writers who do not need it never see it and writers who do are not setting it up by hand each time. (Product US-49, FR-163.)

## Open questions

All product questions OQ-188 to OQ-201 and the feature-breakdown question F108-1 are resolved and are not reopened. The questions below were raised by this spec and resolved by the owner at Gate 3 (2026-11-11, "all recommended"); each answer is folded into the requirement named. None remains open.

- OQ-1: Where do the claim marker, the status and the status date live in the annotation record? Resolved (2026-11-11, Owner decision, Gate 3): (b) one optional nested `claim: { status, statusChangedAt }` on the annotation, presence being the marker; the Source link stays in `target`. — Impact: FR-7, FR-9, FR-10, FR-11, FR-15, FR-18, FR-21.
- OQ-2: How are a claim's status, Source link and statement written after it exists, and is creation one write? Resolved (2026-11-11, Owner decision, Gate 3): (b) one new "update claim" operation (status, Source link, statement) with one validator, one `mutateSidecar` write and one paired-device classification; creation is a single write starting `claim: { status: "unverified", statusChangedAt }`. — Impact: FR-7, FR-9, FR-10, FR-11, FR-15, FR-21.
- OQ-3: How does a writer create a claim in the editor? Resolved (2026-11-11, Owner decision, Gate 3): (a) a new "Mark as claim" control beside Cite selection and Mark as excerpt, owned by the claims module, working with Sources off; the Source is linked afterwards from the panel. — Impact: FR-7, FR-11, FR-14.
- OQ-4: How is the per-module default expressed? Resolved (2026-11-11, Owner decision, Gate 3): (a) `defaultEnabled` on `ModuleManifestEntry`, read through one lookup used by `isModuleEnabled`; the lookup goes in a leaf module if FR-1(b) shows an import cycle. — Impact: FR-2, FR-3.
- OQ-5: What happens to an existing project's absent claims entry? Resolved (2026-11-11, Owner decision, Gate 3): Confirmed from evidence: nothing writes a claims entry automatically; a type declaring nothing creates no `config.modules` entries; the Modules screen shows only on or off. — Impact: FR-2, FR-3, FR-4.
- OQ-6: How does the project-type format declare modules, and how does the Manager show it? Resolved (2026-11-11, Owner decision, Gate 3): (a) a `modules` record (module id to boolean, like `config.modules`) and a three-state control (on, off, not set) per manifest module in the Project Type Manager; no built-in type declares claims on in this feature. — Impact: FR-4, FR-5.
- OQ-7: How do older builds treat the new annotation fields? Resolved (2026-11-11, Owner decision, Gate 3): (c) the `claim` key rides through the server's stored-record spread; `annotation-paste.ts` and the client response schema carry it; FR-1(c) records older-build behaviour, and "older build may drop it on paste or parse" is stated under Not verified unless the test shows otherwise. — Impact: FR-18, FR-21.
- OQ-8: Do the Claims tab and control register through existing slots or need a new slot kind? Resolved (2026-11-11, Owner decision, Gate 3): Confirmed from evidence: claims gets its own `MODULE_MANIFEST` entry and `UiModuleEntry` with `view` and `citationControl` slots; module id and view id `claims`; `"claims"` added to `ViewName`; no new slot kind; the first task confirms `CitationControlSlot` renders the control of every enabled module and extends it if not. — Impact: FR-3, FR-14, FR-16.
- OQ-9: How is the project-wide claim list read? Resolved (2026-11-11, Owner decision, Gate 3): (a) scan every text resource's sidecar when the tab opens, no new store; failed reads named per resource; revisit if FR-1(e) measures it slow. — Impact: FR-3, FR-16, FR-17, FR-21.
- OQ-10: What is the status date's format, and is it set at creation? Resolved (2026-11-11, Owner decision, Gate 3): Confirmed from evidence: a core-written full ISO timestamp, set at creation and on each status change, never client-supplied, displayed as a local calendar date. — Impact: FR-10, FR-15, FR-16.
- OQ-11: What is shown for a stored status not on the fixed list? Resolved (2026-11-11, Owner decision, Gate 3): Confirmed from evidence: shown as stored and marked, never rewritten, matches no filter except "all". — Impact: FR-9, FR-16.
- OQ-12: What does a pasted or copied claim carry? Resolved (2026-11-11, Owner decision, Gate 3): (a) paste, copy and duplicate keep status, status date and Source link. — Impact: FR-10, FR-18.
- OQ-13: With the module off, what does the panel show for a claim? Resolved (2026-11-11, Owner decision, Gate 3): Confirmed from evidence: an ordinary note, statement editable as the body; marker, status and Source line hidden; all claim fields kept untouched (a body edit does not touch claim fields). — Impact: FR-6, FR-15.
- OQ-14: Where do Re-attach and relink live, and does relink need Sources on? Resolved (2026-11-11, Owner decision, Gate 3): Confirmed from evidence: both in the annotations panel; relink offered only while Sources is on; with Sources off the removed-Source line stays visible with the saved name and relink is not offered (a documented limit, not a dependency rule). — Impact: FR-11, FR-13, FR-15, FR-16.
- OQ-15: Is the Claims tab read-only apart from opening a claim? Resolved (2026-11-11, Owner decision, Gate 3): (a) the Claims tab lists, filters and opens only; writes happen in the panel. — Impact: FR-15, FR-16, FR-21.
