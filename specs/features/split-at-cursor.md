## Overview

A novelist whose chapter has grown to hold four scenes, or whose imported file arrived as one block, can reshape it today only by copy and paste, which leaves the passage's revisions, notes, citations and claims behind and records nothing about where the new document came from. This feature lets a writer split an open text document at the cursor into two. The text before the cursor stays in the original, and the text after it becomes a new document placed directly after it. The new document records which document and which revision it came from, nothing is copied from the original's history, and a preserved snapshot of the original's full text is saved first. A dialog asks each time which notes, citations, claims and metadata travel with the text. The latest split can be undone without losing text. It covers desktop and hosted web.

## Goals

- A writer can split an eligible open text document at the cursor and, in one operation, end up with the original holding the text before the cursor and a new document directly after it holding the rest, with every other document unchanged.
- The new document names its source document and source revision, the original keeps every revision it had plus one preserved snapshot of its pre-split text, and each document has exactly one canonical revision.
- The writer chooses, each time and from the same fixed starting choices, what travels with the text, and a note whose passage spans the cut is never duplicated or lost.
- Backlinks, mentions, search, annotation search, word counts and prose diagnostics reflect both documents without a whole-project reindex, moved text adds nothing to the writing log, and a failure at any step leaves no document half-changed and is reported.
- The writer can undo the latest split after a reload without losing any text, including edits made since, and the resolver for a lineage target that is gone is built and tested although nothing displays it yet.

## Non-goals

- Merge, the merged mark, the rule for compile, goals and search of a merged-away document, and Undo merge (Feature 121). This feature adds only what Feature 121 reuses.
- Showing lineage anywhere in the interface, including the stated states of a missing revision or document (Feature 122).
- Split at every heading of a chosen level (Feature 123), split at a selection (v2, Product FR-260), splitting a Source (v2, Product FR-265), and splitting an entity document (refused in the MVP; Product FR-264 applies when lifted).
- Split on Android or on a paired device, and any claim for either (Features 128 and 124).
- Alternates (several live versions of a scene), reconciling edits between devices, any other way of moving text between documents, and any change to how canonical revisions work (Product FR-255).
- Editor-level undo across documents, undo of an operation older than the latest, and a time window on Undo.
- A remembered default in the dialog, and a sixth paired-device limit switch.

## User stories

- US-1: As a novelist or long-form writer whose chapter has grown to hold several scenes, I want to split an open document at my cursor into two, with the new one recording which document and revision it came from, so that I can reshape my manuscript without copying and pasting and without losing the link between the text and its past. (Product US-55.)
- US-2: As a writer splitting a document whose passages carry notes, citations and claims and whose fields carry status and point of view, I want to be asked each time what travels with the text, so that nothing is invented, nothing is deleted, and I decide what the new document takes. (Product US-55; FR-241 to FR-243.)
- US-3: As a writer who split a document and changed my mind, I want to undo the latest split after closing and reopening the project, so that the text is back as it was and nothing I typed since is lost. (Product US-55; FR-246, FR-262.)
- US-4: As a writer who later opens the history of a split-off document, I want to rely on a record that stays true through Trash, restore and pruning and that says plainly when the revision or document it names is gone, so that the lineage is never blank and never mistaken for "none". (Product US-55; FR-251, F120-4.)
- US-5: As a product owner, I want to have the unknowns about revisions, indexing, locking and the project record measured first, and a desktop and a hosted run recorded by the lead, so that no claim outruns what was observed. (Product FR-232 to FR-263 as a whole.)

### The split

2. FR-2: Whether a document can be split MUST be decided by one pure function, used by the client to explain and by the server to enforce, that returns a distinct stable reason for each refusal: an image or audio resource, a folder, a Source, an entity document (a sidecar with `entityKind`), a document marked as merged, a cursor inside a table cell or a code block, a cursor where the first half would be empty, and a cursor where the second half would be empty. A half holding only whitespace or empty paragraphs counts as empty. A cursor inside paragraph, heading, blockquote or list-item text is allowed, by splitting the node. A refusal MUST show a message and MUST change nothing (no revision, sidecar, project or index write). Until Feature 121 defines the merged mark, the merged check MUST read through one named predicate that reads one exported key-name constant, outside the client sidecar allowlist and `SIDECAR_CLEARABLE_KEYS`, and returns false, with a test proving the seam. The message texts live in one message-constants module (as `limits-copy.ts` does), drafted there for the owner to review. [US-1]
3. FR-3: A split MUST leave the original with its id, its name and its text before the cursor in its one canonical revision, and MUST create a new text document in the same folder, directly after the original in tree order (created at the end of the folder, max sibling + 1, then moved into place with `reorderResourcesCore`), named "<name> (part 2)" by default and editable in the dialog, with its own id, fresh `UniqueID`s on moved nodes, holding the text after the cursor in its own single initial canonical revision `v-1` and no copied revisions, written through the same initial-revision path as any new text document. No other document, folder or revision MUST change. [US-1]
4. FR-4: Before the original is truncated, the split MUST save a new non-canonical revision of the original's full text with `metadata.preserve` set, and MUST record that revision's number (and id) in the lineage. After the split the original MUST have every revision it had before, plus this one, and exactly one canonical revision. The snapshot MUST be taken from the stored canonical text read inside the operation, not from the client, while the split holds the `revision-content` lock across it, and MUST be created with `createRevision(..., { metadata: { name, preserve: true, splitSnapshot: true } })`, named "Before split" plus the date. [US-1]
5. FR-5: The new document MUST carry a lineage record naming the source document, the source revision (the snapshot of FR-4), the operation (`split`) and the date. The record MUST be written through the storage adapter (so an encrypted project stores it encrypted and fails closed with no usable key), MUST survive Trash, restore, reopening, copy-independent reads and a prune, MUST NOT be writable or clearable by any client sidecar update, and MUST NOT be rewritten or deleted by Trash, restore, prune or purge of any other document. It MUST be stored in a new file under `meta/` (for example `meta/lineage.json`), outside the `project.json` schema, and the purge sweep MUST leave it alone; FR-1(e) measures the adapter path and tenancy. [US-1] [US-4]
6. FR-6: A split MUST be one operation. If any step fails, the original, the new document, the revisions, the sidecars, the project record and the saved compile exclusions MUST be as they were before it, no half-written new document MUST remain listed, and the writer MUST be told what failed. If a step cannot be undone, the writer MUST be told which state remains, and the failure MUST NOT read as success. The writes MUST be ordered with reverse compensation: lock the original's revision, snapshot, create the new document, move annotations, seed the exclusion, truncate, write the record last; a failure in any step undoes the earlier ones in reverse and is reported. The derived-index update (FR-9) runs after commit and is outside this rollback. At the compile-exclusion cap, or with an unreadable list, the split proceeds and shows the notice (`saved-defaults-core.ts:178-189`), and Undo removes the entry with `removeCompileExclusions`. The operation MUST take its locks in one recorded order with no non-reentrant lock nested (the lock-guard tests of Feature 93 apply). A failure injected after each write step MUST be a test, and two overlapping splits of one document MUST end with one applied and one refused. The claim holds under one writer instance per tenant (ADR-017, ADR-019). [US-1]
7. FR-7: A split MUST NOT run at a place the writer did not choose. The editor MUST send any pending save before the request, a cursor that no longer matches the stored document MUST be refused with a message and no change, and after a successful split no autosave of the pre-split text MUST overwrite the truncated original; the open editor MUST then show the stored state of the document it shows. The original stays open with the cursor at its end. [US-1]
8. FR-8: A split MUST add nothing to the writing log for either document: the original's truncation MUST NOT log deleted words and the new document's initial text MUST NOT log added words, so the day files, the daily word goal and `reindex` results are as before. The truncating write MUST use a new sibling function to `updateRevisionInPlace` that, under the same `revision-content` lock, calls `writeRevisionContent`, then `syncDerivedResourceContent`, then `mutateSidecar` (`wordCount`, `updatedAt`), and skips `snapshotBeforeDestructiveWrite` and `logCanonicalSave`; it MUST NOT go through the path that appends a log entry, and it MUST NOT leave an "Auto-backup" revision in addition to the FR-4 snapshot. A test MUST compare the writing-log directory before and after, and a later ordinary edit MUST log its own words as today. [US-1]
9. FR-9: After a split, the inverted index, the annotation-body index, backlinks, the mention index, word counts (the sidecar `wordCount` of both documents) and prose diagnostics MUST reflect both documents without a whole-project reindex, with mentions recomputed and not copied, and a link to the original MUST still resolve. A failure to update any of them MUST be reported to the writer, MUST NOT show as an empty or up-to-date index, and MUST be repairable by `reindex`; a test MUST inject the failure and compare the result of `reindex` with a rebuild. The update MUST be one new awaited per-document index function that returns failure and also rebuilds prose diagnostics, run after commit; a failure is reported and does not roll the split back (Owner decision, Gate 3, 2026-11-16; Product FR-245 amended). [US-1]
10. FR-10: The new document MUST inherit the original's resource subtype and, when the original is in `config.compileDefaults`, the same saved compile exclusion; its Inbox and Goal-filter membership MUST follow from its folder and carried fields. The new sidecar MUST be built from named keys and MUST NOT be a spread of the original's sidecar, so no `entityKind`, aliases, `wordCountGoal`, annotations or stored `wordCount` arrive unchosen. A metadata value not carried MUST be absent (a status not carried is absent as for "No status"), never invented, and the original's own metadata MUST be unchanged. At the compile-exclusion cap or on an unreadable stored shape the split proceeds and shows the notice (FR-6). [US-1] [US-2]
11. FR-11: Annotations MUST be carried by these rules, for every annotation (a note, a citation with its `target`, a claim with its status and date), whether or not its module is switched on. One whose passage lies wholly before the cursor stays unchanged. One whose passage lies wholly after it and which the writer chose goes with its exact text, keeping its body, `target` and claim status and date, and is no longer in the original's sidecar. One not chosen stays in the original, and if its passage left, is detached there, with its stored quote unchanged and its body not deleted. One whose passage spans the cursor stays with the original, its mark covering only the part that remains there, and is never duplicated or lost. No annotation id MUST be shared between the two documents. A spanning annotation's stored quote MUST stay unchanged while its mark shrinks. In the new document the marks of annotations not carried MUST be stripped; a carried annotation keeps its id and leaves the original's sidecar, so the 500 limit cannot be exceeded. How a mark is cut is measured by FR-1(i). [US-2]
12. FR-12: Before every split a dialog MUST ask what carries over, each time. It MUST open with the same fixed defaults whatever the last choice was, MUST store nothing between operations (no `localStorage`, no config key), and Cancel or Escape MUST change nothing (a test counts writes). ### Undo split (built last)

## Open questions

Product OQ-251 to OQ-265 are resolved at Gate 1 and F120-1 to F120-4 at Gate 2; none is reopened here. The questions below are this spec's own. All were open when drafted; at Gate 3 (2026-11-16) the owner accepted the evidence-based resolutions and made the decisions recorded under each question. OQ-8 is deferred by design, as stated under it. FR-1 records the measurement that settles what a resolution still defers.

- OQ-1: How is the cursor conveyed to the server and tied to the stored canonical revision (a document position, a text offset, a revision id or content hash as a staleness check), and what does the server do when the editor holds unsaved text or a save lands during the request? — Impact: FR-1, FR-3, FR-4, FR-7, FR-12.
  Resolved (2026-11-16, Owner decision, Gate 3): the client flushes pending saves, then sends the canonical revision id, a content hash and a text offset; the server reads the stored text under the revision lock and refuses a hash mismatch as stale.
- OQ-2: How is an `annotation` mark cut at the split point in TipTap JSON: a mark that spans the point, ends at it or starts at it, two marks with one id after the cut, and what the stored `quote` of a spanning annotation becomes (the full passage, or the part that remains, given the 500-character limit)? — Impact: FR-1, FR-11.
  Resolved (2026-11-16, Owner decision, Gate 3): a spanning annotation keeps its stored quote unchanged while its mark shrinks to the part that remains in the original. Whether the cut itself behaves so in TipTap JSON is measured by FR-1(i).
- OQ-3: What is a split inside a list item, table cell, code block, blockquote, heading or next to an image: which block structure each half gets, whether a cut is allowed there at all, and what happens to node `UniqueID` attributes in the half that moves? — Impact: FR-1, FR-2, FR-3.
  Resolved (2026-11-16, Owner decision, Gate 3): a split is allowed inside paragraph, heading, blockquote and list-item text by splitting the node, and refused inside a table cell or code block with a stated reason. Moved nodes must get fresh `UniqueID`s; FR-1(i) measures whether the extension does that.
- OQ-4: What makes a half "empty" for FR-233 when the cursor is at the end followed by empty paragraphs or whitespace, or at the start preceded by them? — Impact: FR-2.
  Resolved (2026-11-16, Owner decision, Gate 3): a half holding only whitespace or empty paragraphs counts as empty.
- OQ-5: Which word count does the dialog show for each half (the sidecar `wordCount`, `countWords` over the plain text, the figure the tree shows), and is it computed from the stored or the editor's text? — Impact: FR-1, FR-12.
  Resolved (2026-11-16, from evidence, confirmed by the owner at Gate 3): the dialog's word counts come from `countWords(tiptapToPlainText(storedText))`, computed server-side in the call that checks staleness (`revision-core.ts:526`).
- OQ-6: Where in "project meta" does the latest-operation record live (`project.json` `config`, `project.json` `metadata`, a file under `meta/`), what is its shape, and does that home survive every `project.json` writer and a schema parse? — Impact: FR-1, FR-16, FR-17.
  Resolved (2026-11-16, Owner decision, Gate 3): the latest-operation record lives in a new file under `meta/` (for example `meta/latest-operation.json`), outside the `project.json` schema, and survives purge; the purge sweep is told to leave it alone. FR-1(e) measures the encrypting-adapter path and tenancy. Supported by evidence that `ProjectConfigSchema` would strip an undeclared key (`schemas.ts:367`), which this placement supersedes.
- OQ-7: Where does the lineage record live (a sidecar key of the new document, project meta, or both), what shape does it take (revision number, revision id, or both; the source document's name at the time), and how is FR-251's rule that purge never deletes a record reconciled with the record being part of a document that purge removes? — Impact: FR-1, FR-5, FR-15.
  Resolved (2026-11-16, Owner decision, Gate 3): the lineage record lives in a new file under `meta/` (for example `meta/lineage.json`), outside the `project.json` schema, and survives purge; the purge sweep is told to leave it alone. FR-1(e) measures the encrypting-adapter path and tenancy.
- OQ-8: Which shortcut is chosen, given Cmd/Ctrl+K and Cmd/Ctrl+Shift+K in `AppShell.tsx`, the TipTap keymaps, the Electron menu and browser-reserved keys on hosted web? — Impact: FR-1, FR-13.
  Deferred by design (Owner, Gate 3, 2026-11-16): chosen by the owner from the FR-1(j) shortlist before the UI task; no task before that may assume a key.
- OQ-9: How is the operation made atomic across the revision directory, two sidecars, the new document's files, the compile exclusion in `project.json` and the latest-operation record, given no cross-file transaction, non-reentrant locks, a non-atomic revision metadata rewrite, a per-process lock, and `enqueueIndex` firing on every sidecar write (stage then rename, compensate in reverse, or suspend indexing and verify)? — Impact: FR-1, FR-6, FR-9, FR-17.
  Resolved (2026-11-16, Owner decision, Gate 3): ordered writes with reverse compensation. Order: lock the original's revision, snapshot, create the new document, move annotations, seed the exclusion, truncate, write the record last; a failure in any step undoes the earlier ones in reverse and is reported. Also from evidence (owner accepted): `withIndexingSuspended` must not be used, being process-wide and forbidden in the server (`indexer-queue.ts:600-608`).
- OQ-10: When a derived-index update fails after the text is written, does the split roll back (FR-245 says any failed step does) or stay applied and reported and repairable by `reindex` (FR-244 says so)? — Impact: FR-6, FR-9, FR-17.
  Resolved (2026-11-16, Owner decision, Gate 3): the derived-index update runs after commit and is awaited; it reports failure but does not roll the split back, and `reindex` repairs it. Product FR-245 is amended to say so.
- OQ-11: What updates the derived data of a chosen set of documents and reports failure, given `rebuildDerivedIndexes` covers the whole project and `enqueueIndex` reports none and resolves after 5 s regardless; and who rebuilds prose diagnostics, which the shared rebuild does not? — Impact: FR-1, FR-9.
  Resolved (2026-11-16, Owner decision, Gate 3): a new awaited per-document index function that returns failure and also rebuilds prose diagnostics.
- OQ-12: What do the refusal messages say, for a document type, a Source, an entity document, a merged document, either cursor end, a stale cursor, a locked project, a full compile exclusion list and a failed step, and where does each appear (dialog, toast, inline)? — Impact: FR-2, FR-6, FR-7, FR-14.
  Resolved (2026-11-16, Owner decision, Gate 3): refusal and notice texts live in one message-constants module (as `limits-copy.ts` does). The wording stays drafted in the constants module, and its review by the owner happens in the UI task.
- OQ-13: What are the fixed defaults of the dialog (which choices start ticked), is the annotation choice per annotation or per kind (notes, citations, claims), and which fields are listed (status, point of view, Synopsis, Notes, every other `userMetadata` key, `wordCountGoal`)? — Impact: FR-10, FR-12.
  Resolved (2026-11-16, Owner decision, Gate 3): annotations anchored in the moving text start ticked, as per-annotation checkboxes grouped by kind; metadata fields start unticked.

  Resolved (2026-11-16, Owner decision, Gate 3): the new document is named "<name> (part 2)" by default, editable in the dialog; afterwards the original stays open with the cursor at its end.
- OQ-15: How is "directly after the original" kept in `orderIndex` order (a gap, a tie rule, or renumbering siblings, which writes to other sidecars), including for a document in the project root and one sharing an index with subfolders? — Impact: FR-1, FR-3, FR-6.

- OQ-16: When the original is in `config.compileDefaults` and the list is at 5000 or its stored shape is unusable, so `seedCompileExclusion` returns a notice and writes nothing, does the split proceed with that notice, refuse before any write, or something else, given FR-253 says the new document inherits the exclusion? — Impact: FR-6, FR-10.
  Resolved (2026-11-16, from evidence, confirmed by the owner at Gate 3): at the compile-exclusion cap, or with an unreadable list, the split proceeds and shows the notice (`saved-defaults-core.ts:178-189`); Undo uses `removeCompileExclusions` (`:225`).

  Resolved (2026-11-16, from evidence, confirmed by the owner at Gate 3): marks of annotations that are not carried are stripped in the new document; a carried annotation keeps its id and leaves the original's sidecar, so the 500 limit cannot be exceeded.
- OQ-18: How is the original truncated without a writing-log entry and without an automatic "Auto-backup" revision, given `updateRevisionInPlace` does both: a new function, a flag on the existing one, or another path? — Impact: FR-1, FR-4, FR-8.
  Resolved (2026-11-16, from evidence, confirmed by the owner at Gate 3): truncation uses a new sibling function to `updateRevisionInPlace` that, under the same `revision-content:<root>:<id>` lock, calls `writeRevisionContent`, then `syncDerivedResourceContent`, then `mutateSidecar` (`wordCount`, `updatedAt`); it skips `snapshotBeforeDestructiveWrite` and `logCanonicalSave` (`revision-core.ts:495`, `:517`).
- OQ-19: How does Undo restore the original's text: `setCanonicalRevision` (which strips marks with no sidecar body, rewrites every revision's metadata in a loop and does not sync derived files or `wordCount`), or a new restore that does, and what happens to marks of annotations that were carried out? — Impact: FR-1, FR-9, FR-17.
  Resolved (2026-11-16, from evidence, confirmed by the owner at Gate 3): Undo does not use `setCanonicalRevision` (`revision-core.ts:627-656`, mark strip at `:639`); it overwrites the original's canonical content from the snapshot using the no-log function of OQ-18.
- OQ-20: What else does Undo reverse: carried annotations (moved back or left in the trashed document), the split-off id in the saved compile exclusion, the order indexes, the metadata chosen; and after Undo is the record cleared, kept as undone, and can Undo be run twice? — Impact: FR-16, FR-17.
  Resolved (2026-11-16, Owner decision, Gate 3): Undo is a full reversal and runs once: it saves both documents' current text as preserved revisions, overwrites the original's canonical content from the snapshot with the no-log function, moves carried annotations back into the original's sidecar, sends the split-off document to Trash (not purge), removes its compile-exclusion entry, and clears the latest-operation record so it cannot run twice.
- OQ-21: What does Undo do when the original or the snapshot is gone, in Trash or purged, when the split-off document is already in Trash, purged, edited, or itself split or merged since (which makes that later operation the latest), and which resolver state is a refusal and which a proceed? — Impact: FR-15, FR-17.
