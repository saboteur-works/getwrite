## Overview

Two gaps in how a writer organises research are closed together. First, a folder has a name and a place in the tree but nothing else: a writer who groups work into a case, an episode, a chapter or a set of variants has nowhere to put what they know about the whole group, and cannot find or filter folders by it. Second, a writer gathering evidence for nonfiction, true crime or folklore has no kind of item for a source (an interview, an archive item, a newspaper piece) that keeps a write-up together with its images and audio, and an attachment removed by mistake is gone. This feature gives each folder its own plain-text notes, custom field values and an optional writer-defined subtype, stored apart from the folder's structure and carried by Trash; lets queries, smart folders, the Organizer and the Data view show and filter folders; and adds a `source` resource type with one rich-text body and an ordered list of image and audio attachments whose removed or replaced files go to Trash and can be restored. Sources in this feature are reached through the generic resource tree, sidecar and the compile and export dialogs; the Sources module and interface are a later run. Several statements above are readings, so each part starts from a test that settles them.

## Goals

- A writer can give any folder notes, field values and an optional subtype, edit them in the metadata sidebar, and find and filter folders by them; a project with no folder metadata behaves exactly as before.
- Folder metadata survives rename, reorder, move, trash and restore intact, and no permanent delete leaves a folder sidecar behind.
- A writer can create, open, rename, move and delete a Source that holds one rich-text body and an ordered list of image and audio attachments, and every place that handles a resource by type handles it without error.
- An attachment the writer removes or replaces can be restored to its Source from Trash, and attachments never create or enter a revision.
- What a Source is left out of stays the writer's choice: new projects start with Sources out of compile only, and the writer can change that per run and as a saved default.

## Non-goals

- Any Sources view, panel or module interface, excerpts, citations, bibliography, claim handling, and the contribution seam for modules (product FR-110; Run C). What minimum interface this feature needs to be exercised is OQ-2.
- Built-in folder subtypes; built-in fields other than notes on folders (OQ-137, OQ-143).
- Rich-text or formatted folder notes; a document inheriting its folder's fields or notes (product FR-99).
- Including folder notes in compile or export (OQ-141); mapping Scrivener folder synopsis, notes or metadata (OQ-142).
- Video or any other attachment kind; attachments as tree items; revisions of attachments (product FR-106, FR-107).
- Linking a Source to an entity (OQ-151); a per-Source or project switch for spell check, diagnostics or mention detection (OQ-146).
- Seeding saved defaults from a project type or a module (Feature 101 non-goal).

## User stories

- US-1: As a writer who organises research or a long work into folders (a case, an episode, a chapter, a collection of variants), I want to give a folder its own notes and my own fields, and to give a folder a kind, so that what I know about a whole group sits on the group and I can find and filter folders by it. (Product spec US-39.)
- US-2: As a writer gathering evidence for nonfiction, true crime or folklore, I want to keep a source (an interview, an archive item, a newspaper piece) as its own kind of item that holds my write-up and the images and audio that belong to it, without losing an attachment I remove by mistake, so that one source stays together and its evidence is recoverable. (Product spec US-40; core part only.)

## Open questions

All twelve implementation questions were resolved at Gate 3 (owner, 2026-11-07, "all recommended, 6b"). None reopens a product OQ. Statements marked reading are code readings, not runs.

- OQ-1 (resolved): How does "Sources excluded from compile by default" work, given saved defaults store only `excludedResourceIds`?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): Source id seeded into `config.compileDefaults.excludedResourceIds` on create, copy and duplicate; no migration of existing projects; clearing the saved default brings Sources back in; 5000-id cap refuses seeding visibly while the Source is still created; export defaults not seeded. Applied in FR-27.
- OQ-2 (resolved): What is the minimum interface to create a Source, edit its body and manage attachments?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): "Source" in the tree's create control, the existing editor for the body, and one new "Attachments" sidebar section (add, remove, replace, reorder) as the only Source-specific component; a11y test, story and e2e required; no preview or playback. Applied in FR-19, FR-24, FR-30.
- OQ-3 (resolved): How do the folder sidecar's allowlist and lock interact with folder rename, reorder, move and delete?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): The sidecar is written only by its own core with `mutateSidecar`-style locking; rename, reorder and move write only `folder.json`; reorder must not call the sidecar core inside `withMetaLock`; soft delete and restore move the sidecar under its file lock; `purgeFolder` adds it to its idempotent sweep. Reading, not run; the owner confirmed it. Applied in FR-1, FR-3, FR-5, FR-6, FR-7.
- OQ-4 (resolved): How do folders enter the query evaluator, and what do folder rows show?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): A second id source used only when the query names `type = folder`; a mixed-type query result is defined and tested; Data view row shows name, subtype and chosen field columns; Organizer card shows name and subtype; no notes preview or child count (deferred); `appliesToFolders` originally meant also offered on folders; superseded for fields with `appliesTo` by the Gate 5 rule in FR-9 (Owner, 2026-11-07). Applied in FR-9, FR-13, FR-14.
- OQ-5 (resolved): What do Electron and Android need beyond the core, route and native backend pattern?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): Desktop needs no Electron change (reading, not run; a review or test step confirms); Android needs the native backend, `.web-stub.ts` and `next.config.mjs` alias; native lock parity is reasoned, not run. Applied in FR-8, FR-32.
- OQ-6 (resolved): How do folder sidecars and attachments behave in an encrypted or locked project?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): Expected, not run: both go through the storage adapter and are sealed; locked access raises `ProjectLockedError` or `MissingProjectKeyError` and new cores rethrow `isLockedAccessError`; attachment code uses `io.ts` and the adapter only; FR-31 tests prove it. Applied in FR-31, FR-34.
- OQ-7 (resolved): Which text features include a Source's body?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): All sites where the text rule exists, with annotations allowed on a Source body and templates staying text-only; the FR-18 survey records each disposition. Applied in FR-28, FR-29, FR-38.
- OQ-8 (resolved): What is a removed attachment's Trash entry and how is it restored?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): Its own new Trash item kind, shown as "Attachment of <Source name>"; restore to the end of the list with the " (restored)" suffix on a name clash; refused with a message when the Source is in Trash or purged; purge and empty-trash handle the kind. Applied in FR-26, FR-31.
- OQ-9 (resolved): What does the sidecar core do with `entityKind` or `aliases` submitted for a Source?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): Refused with a named error mapped to HTTP 400; `clearKeys` for those keys still allowed. Reading, not run. Applied in FR-21. Refusal clause superseded by the Owner decision, 2026-11-07, in FR-21: a writer may set `entityKind` and `aliases` on a Source, the same as a text resource; the question stays resolved.
- OQ-10 (resolved): What limits apply to attachments?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option, option 6b): `validateMediaFile` reused (extensions, MIME, video refused, 100 MB per file, allowlisted extension, `isPlainFileName`) on every transport, plus a new magic-byte check for attachments only; at most 500 attachments per Source (option 6b); no total-size cap. Applied in FR-23, FR-24, FR-31.
- OQ-11 (resolved): What is the scope of the type-branch survey?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): `frontend/`, `cli/` and `electron/`, covering exhaustive switches, type literals, string-keyed maps, `ResourceType` references, `repair-revisions` and import workers; the count is a record, acceptance is typechecks passing and a disposition per site. Applied in FR-18, FR-36.
- OQ-12 (resolved): Where in the folder sidecar is the subtype stored?
  **Resolution:** Resolved (Owner decision, 2026-11-07; recommended option): The same top-level key `resourceSubtype`, reusing its validation and `normalizeSubtypeLabel`; `isFieldVisibleForSubtype` reused unchanged and called explicitly by the folder sidebar section. Reading, not run. Applied in FR-3, FR-10.
