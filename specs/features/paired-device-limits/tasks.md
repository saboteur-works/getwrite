### Task 6: Limits file format, shared fixtures and the main-side writer
**What:** Define the `sharing-limits.json` format as shared JSON fixtures and add the electron module that reads it (fail closed to all-on) and writes it by read-modify-write under the same lock-file protocol as the device store.
**Files:** `electron/src/sharing/limits-store.ts` (NEW), `electron/tests/limits-store.test.ts` (NEW), `frontend/tests/fixtures/sharing/sharing-limits.cases.json` (NEW: a list of named cases, each `{ name, text, expected }` with `expected` one of `ok` with the five booleans, `missing`, `invalid`, `unreadable-other` not representable in a fixture so it is tested directly), and fixture files beside it such as `sharing-limits.valid.json`, `sharing-limits.unknown-keys.json`. Reads, and the implementor MUST open and copy the facts from: `electron/src/sharing/device-store-writer.ts` (the lock protocol: lock file `wx`, mode 0600; retry on `EEXIST` only, 200 attempts at 25 ms; a lock older than 30 s removed; released in a `finally`; replacement through a 0600 temp file, synced, renamed, temp removed on failure), `frontend/src/lib/sharing/file-lock.ts`, `electron/src/sharing/store-status.ts` and `electron/tests/store-status.test.ts` (the contract-test pattern).
**Done when:** tests first, seen failing, then green, in temp directories. The format is `{ "version": 1, "limits": { "projectDeletion", "unlocking", "locking", "encryptionChanges", "permanentDeletion" } }`, each a boolean, true meaning restricted. The reader returns `{ kind: "ok", limits }`, `{ kind: "missing" }` (ENOENT; effective all five true), `{ kind: "invalid" }` (unparseable, `version` other than 1, `limits` missing or not an object, any of the five missing or not a boolean; effective all five true), or `{ kind: "unreadable", reason }` (any read error other than ENOENT, for example permissions; effective all five true); unknown extra keys, top level and inside `limits`, are tolerated. `readEffectiveLimits(dir)` always returns five booleans and treats a limit as off only when the file positively says `false`. The writer `setLimit(dir, key, value)` (or `setLimits`) validates in the module that the key is one of the five and the value a boolean, takes the lock, reads INSIDE the lock, then: `ok` rewrites with the one value changed and every unknown key, top-level and inside `limits`, preserved after `JSON.parse`; `missing` and `invalid` MAY be overwritten with all five true except the changed one (assert the file afterwards reads `ok` with that value); `unreadable` is REFUSED with a distinct `unreadable` outcome and the bytes unchanged (simulate by a directory at the file path or a mode-0 file; skip the permissions case on Windows with the skip in the test name). Outcomes are explicit and never `ok` for a failure: `ok`, `unreadable`, `lock-not-acquired` (inject small retry count/delay; assert defaults 200, 25, stale 30 000 ms), `write-failed`, `invalid-input`. The lock path is exactly `${file}.lock`; the written file has mode 0600; the temp file is removed on failure; the lock is gone after success, after a throwing mutate and after a failed write. A contract test classifies every case in `sharing-limits.cases.json` and asserts the same `expected` (Task 8 asserts it again for the server reader). Neither the module nor an outcome contains a path other than the directory passed in. From `electron/`: `pnpm test` and `pnpm typecheck` pass; from the repo root `pnpm knip` reports nothing new compared by set to Task 4.
