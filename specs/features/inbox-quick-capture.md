## Overview

A writer on desktop, hosted web or a paired device who has a thought, a quote or a link to keep has no quick way to put it into a project without opening that project and creating a resource by hand. This feature adds a per-project Inbox and a Capture box: the writer presses Cmd/Ctrl+Shift+K (or picks "Capture..." in the resource command palette), types, presses Enter and is back where they were, with the text saved as an ordinary text resource in the Inbox of a project they chose, without that project being open. The Inbox is an ordinary folder identified by an id in the project's config and created on first capture. Inbox items are left out of compile and out of the word-count goals by default, show a count in the resource tree, and can be filed out with the existing move or a "File to..." action. Capture into a locked project fails closed, and capture widens nothing a paired device or a hosted tenant may do. The capture function is built so that Feature 107 can call it in-process on Android.

## Goals

- A writer can capture typed text into a chosen project's Inbox from the Capture box in at most one keyboard shortcut, one text entry and one Enter, without opening the project, on desktop, hosted web and a paired device.
- Each project has at most one live Inbox identified by `config.inboxFolderId`, created on first capture, with the three states (live, in Trash, purged or unknown) behaving as the product spec says, and no captured text lost or left unreported.
- Inbox items are out of compile by default, out of the project total goal and the daily goal by default, counted in the tree, findable by search and queries like any resource, and can be filed out by the tree move or "File to...".
- A capture into a locked or encrypted project writes nothing unencrypted and tells the writer so; a capture is refused or allowed on a paired device exactly as creating a resource is, and a hosted capture touches only the signed-in tenant's projects.
- One capture function, callable in-process, serves the Capture box now and Feature 107 later, pinned by a test that it imports nothing the native build cannot bundle.

## Non-goals

- The Android capture button, the share target and any native code (Feature 107, product FR-154 and FR-155).
- A desktop global shortcut, `getwrite-cli capture`, a web share target and the web clipper.
- Capturing images or audio in this feature; the Capture box takes text only (Feature 107 owns image capture, through the same function).
- Fetching a page title or any content from the network.
- Converting an Inbox item to a Source, and combining several fragments into one.
- A new resource type, a meaning for the deprecated `special` folder flag, a new paired-device limit switch, or protection of the Inbox folder from rename, delete or move.

## User stories

- US-1: As a writer, I want to capture a thought, a link or a photo in a few seconds from wherever I am in the app, so that I do not lose it, and later find it in one place and file it where it belongs. (Product US-48; this feature covers desktop, hosted web and paired devices, text and links; photos are Feature 107.)

### The capture function

2. FR-2: A capture core function (new module `frontend/src/lib/models/inbox-capture-core.ts`) MUST exist that, given a project id, the captured text, an optional link, an origin (`typed` or `shared`) and, when the Inbox is in Trash, the writer's choice (`restore` or `new`), resolves the Inbox (FR-4), creates one text resource in it (FR-5), seeds its compile exclusion (FR-6) and writes its writing-log entry (FR-8), and returns the created resource, the Inbox folder id and any visible notices. The module MUST be reached through the route, client and native backend of FR-10 and MUST be unit-tested without HTTP. A failure at any step MUST be reported to the caller as a failure, never as success, and no captured text MUST be dropped (see FR-4, FR-6, FR-8 for each step's failure behaviour). (Product FR-151 to FR-153, FR-156, FR-162; `docs/standards/security.md`, `docs/standards/failure-visibility.md`, `docs/standards/storage-context.md`.) [US-1]
3. FR-3: The Inbox MUST be a folder identified by a new optional field `inboxFolderId` (a UUID) in `ProjectConfig`, declared in `types.ts`, `schemas.ts` and `lib/api/schemas.ts` (the last strips undeclared keys, per `frontend/CLAUDE.md`), and by nothing else: not its name, not the `special` flag. 4. FR-4: The capture function MUST resolve the Inbox in three states, and MUST test each one. Live (the config id names a live folder): the item goes into it. In Trash (the config id names a trashed folder): the function MUST NOT write the item, MUST return a "needs choice" result that carries nothing but the state, and on a second call with `restore` MUST restore the folder with `restoreFolder` (`trash.ts:1157-1215`, which never refuses, keeps the folder id, and may relocate the folder to the root or rename it with a suffix), report `relocated` and `renamed` to the writer, and then capture into it whatever the restore did (OQ-17); on a second call with `new` it MUST create a new Inbox, repoint the config id, and capture into it, leaving the old one in Trash (if the old one is later restored beside the new one, that is a case to test and report, not prevent). Purged, or the id names no folder, or no id is set: a new Inbox is created and the config id repointed, without a prompt. Reading `config.inboxFolderId`, creating the folder and writing the id MUST be one step inside `withMetaLock(projectRoot)` (`meta-locks.ts:17-39`, in-process and not reentrant, so the caller of `updateProjectJson` holds the lock and its callback takes none; the folder is created in the outer callback), so two captures racing on the first capture create one Inbox (test: two concurrent captures into a project with no Inbox leave one Inbox folder and both items inside it). That guarantee is in-process only, as it is for every config writer; it MUST be stated in the docs and not claimed across processes (OQ-2). If the folder was created and the config write then fails, the function MUST remove the just-created empty folder and fail visibly; nothing captured is lost because the typed text stays in the box (FR-17). If the item cannot be created after the Inbox was created or restored, the Inbox MAY remain and the failure MUST be reported. (Product FR-151, FR-162, OQ-179.) [US-1]

## Open questions

All product questions OQ-179 to OQ-187 and the feature-breakdown questions F106-1 and F106-2 are resolved and are not reopened. OQ-1 to OQ-18 below were raised by this spec and resolved at Gate 3 (2026-11-09), each by triage evidence or by an owner decision; each carries its resolution and the requirements above are written to match. None remains open. FR-numbers refer to this document.

- OQ-1: How is the capture route and transport shaped across hosted, desktop, paired and native? — Resolved from evidence (triage), Gate 3, 2026-11-09, option (a): a new route (for example `POST /api/project/capture`), a `lib/api` client on `createTransport`, a native backend with a `.web-stub.ts` alias, and `inbox-capture-core.ts`, the Feature 101/102 pattern. Client composition cannot close the race: `withMetaLock` (`src/lib/models/meta-locks.ts:17-39`) is in-process and not reentrant. — Impact: FR-2, FR-4, FR-10.
- OQ-2: Which lock closes the first-capture race, and is it enough? — Resolved from evidence (triage), Gate 3, 2026-11-09, option (a): `withMetaLock(projectRoot)` around reading `config.inboxFolderId`, creating the folder and writing the id; the id write goes through `updateProjectJson` (`project-json-write.ts:54-76`; its doc lines 11-13 allow a caller-held `withMetaLock`, and its callback must take no lock, so folder creation is in the outer callback). For "folder created, config write failed": remove the just-created empty folder and fail visibly; nothing captured is lost because the typed text stays in the box. The guarantee is in-process, the same as every config writer. The folder-create path was not located by triage; FR-1(b) records it. — Impact: FR-1, FR-4.
- OQ-3: Does a filed-out item lose its saved compile exclusion? — Owner decision, Gate 3, 2026-11-09, option (a): moving an item out of the Inbox (to a folder outside the Inbox subtree) removes its id from `compileDefaults`, through the move route and the native backend, even if the writer had set that exclusion deliberately (the owner accepted that loss). Beyond the owner's answer, lead's derivation, Gate 3, 2026-11-09, confirmed by the owner at Gate 3 approval, 2026-11-09: a folder moved out removes the ids of all resources inside it and its descendants, and the removal runs after the move (the move stands, with a visible message, if the removal fails). — Impact: FR-6, FR-15, FR-23.
- OQ-4: If seeding the exclusion fails after the item is created, what happens? — Owner decision, Gate 3, 2026-11-09, option (b): the item is kept; a cap or shape problem gives a notice, and a read or write throw gives a visible error. — Impact: FR-2, FR-6.
- OQ-5: What does "the capture route is classified" mean when it calls no `checkLimit`? — Resolved from evidence (triage), Gate 3, 2026-11-09, option (a): no `checkLimit`; the sharing gate (`src/lib/sharing/gate.ts:247-274`) refuses not-confirmed requests to any non-exempt route, and tests pin that not-confirmed is refused and confirmed is allowed. No extra route guard (the owner accepted this). — Impact: FR-10.
- OQ-6: Is the Capture box reachable when no project is open? — SUPERSEDED (see amendment below). Owner decision, Gate 3, 2026-11-09, option (a): the Capture box and its key handling are mounted once above both the Start screen and `AppShell` (in `app/(app)/page.tsx` or the `(app)` layout); the existing Cmd/Ctrl+K handler (`AppShell.tsx:916-926`) moves there so there is one key handler, and its missing `shiftKey` check is fixed so that Cmd/Ctrl+K opens the palette and Cmd/Ctrl+Shift+K opens Capture, pinned by a test. `AppShell` is not mounted on the Start screen (`app/(app)/page.tsx:131, 1111`); FR-1(d) still records this as measured. — Impact: FR-1, FR-11.
  Amended 2026-11-09 after Task 2 measured AppShell mounted on the Start screen: owner decision, mount inside AppShell, key handler stays in AppShell with the shiftKey fix.
- OQ-7: Where are the capture time and the link stored? — Owner decision, Gate 3, 2026-11-09, option (b): new sidecar keys `capturedAt` (full ISO timestamp) and `capturedLink`, written server-side by the capture core with validation and not client-writable, shown read-only in a small metadata block in the sidebar. No change to the default metadata schema. — Impact: FR-5, FR-22.
- OQ-8: How is the title derived, and what bounds the text? — Owner decision, Gate 3, 2026-11-09: the title is the first non-empty line, trimmed, cut to 80 characters, with the fallback "Captured note"; the captured text is capped at 50,000 characters with a plain refusal above it (no existing text cap was found). The cut has no word-boundary rule (lead's derivation, Gate 3, 2026-11-09, confirmed by the owner at Gate 3 approval, 2026-11-09). — Impact: FR-2, FR-5, FR-19.
- OQ-9: What is "in the Inbox" for the count and the goal exclusion? — Owner decision, Gate 3, 2026-11-09, option (b): the Inbox folder and all its descendant folders, for the count, the goal exclusion and the compile seeding and clearing. The client walks `parentId` from the store; the server reads the folder tree once per aggregate (`readFolderTree`, `folder-utils.ts:32`). The cost is not measured; FR-1(e) records it. — Impact: FR-1, FR-7, FR-14, FR-23.
- OQ-10: Does moving an item out of the Inbox end the goal exclusion immediately, and for which words? — Owner decision, Gate 3, 2026-11-09, option (a): membership is checked at read time, like Sources; filing an item out makes its words count from then on, including earlier words, so today's figure can jump. The docs state this. — Impact: FR-7, FR-15, FR-21.
- OQ-11: Is pasted text typed? — Owner decision, Gate 3, 2026-11-09, option (a): all text from the box is logged as typed, which matches the editor's word-bag diff. — Impact: FR-8.
- OQ-12: Does Enter submit, and how is a multi-line capture entered? — Resolved from evidence (triage), Gate 3, 2026-11-09, option (c): Enter submits, Shift+Enter inserts a newline, and Enter does not submit while `event.nativeEvent.isComposing`. No existing guard exists (a grep found no `isComposing`), so this is new code with a test. — Impact: FR-11.
- OQ-13: When does the "Capture..." palette entry show? — Owner decision, Gate 3, 2026-11-09, option (a): it is the first palette row when the query is empty or a prefix of "capture"; the "No resources match your search." empty state must not show while the Capture row is visible, and the "Enter to open" hint must fit a non-resource row. It needs a new prop (for example `onCapture`) and a row type (`ResourceCommandPalette.tsx:15-19, 56, 62, 113, 146, 186`). The row is hidden for other queries (lead's derivation, Gate 3, 2026-11-09, confirmed by the owner at Gate 3 approval, 2026-11-09). — Impact: FR-11, FR-24.
- OQ-14: What is the source of "most recently opened project"? — Resolved from evidence (triage), Gate 3, 2026-11-09, option (a): a second `localStorage` key written in `handleOpen` (`app/(app)/page.tsx:338`), the single open path (the import-complete and restore effects call it). — Impact: FR-12.
- OQ-15: How does the Capture box show a locked project? — Owner decision, Gate 3, 2026-11-09, option (a): a locked project appears as a selectable "Locked project" with its encryption date; choosing it leads to the unlock prompt (FR-9). A locked entry has only its id and encryption time, no name (`project-crud-core.ts:280-296`). — Impact: FR-9, FR-12.
- OQ-16: How is a text resource created with its body in one write, and what is left if the second write fails? — Resolved from evidence (triage), Gate 3, 2026-11-09, option (a): `CreateResourceOpts` already accepts `text.plainText` and `text.tiptap` (`resource-factory.ts:239-254`) and `writeResourceWithInitialRevision` writes them into `v-1` (`resource-initial-revision.ts:61-75`), so no shared change. A text create does not seed the compile exclusion (`resource-crud-core.ts:174-176`), so capture calls the `seedSourceCompileExclusion` mechanism directly. A narrow window between the resource write and the revision write remains; the box keeps the typed text until success (FR-17). — Impact: FR-1, FR-2, FR-5, FR-6.
- OQ-17: When the Inbox is in Trash and the writer chooses "restore it", and the restore relocates or renames the folder, is the capture still made? — Resolved from evidence (triage), Gate 3, 2026-11-09, option (a): `restoreFolder` (`trash.ts:1157-1215`) never refuses, keeps the id, and may relocate to the root or rename with a suffix; capture proceeds and reports where the item landed. A trashed Inbox is found by a direct read of `trashFolderManifestPath(projectRoot, folderId)` (`trash.ts:1167`); a missing manifest means purged. — Impact: FR-4.
- OQ-18: Does the Capture box need a project-list call at open time, and what does it show while pending or failed? — Resolved from evidence (triage), Gate 3, 2026-11-09, option (a): the project list is read when the box opens, with a loading state and a failed-with-retry state (precedent `app/(app)/page.tsx:150-219`); the store's list alone can be stale or empty. — Impact: FR-12, FR-17.
