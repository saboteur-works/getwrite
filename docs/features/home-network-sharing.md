## What it is

A writer can turn on one setting in the desktop app's App Settings and open their projects from another device's browser over the home network, with no account and no hosted service. Sharing is off by default. With it on, a device must be paired once by typing a short-lived, one-time code shown in the desktop window; the device then holds its own credential. The desktop window itself never needs pairing.

Sharing and hosted authentication are mutually exclusive. If sharing is on and both `DATABASE_URL` and `BETTER_AUTH_SECRET` are set, sharing is not started, the server stays on loopback, and the settings say so (`resolveSharingMode`, `electron/src/sharing/sharing-mode.ts`). The environment is not stripped.

## How a writer uses it

1. From the settings (gear) menu choose **App Settings**. Under "Home network sharing" turn on "Share my projects on this network". The setting is recorded at once, but the server's bind is fixed when it starts, so it takes effect on restart: "Restart now" restarts GetWrite (`getwrite:restart`, `app.relaunch(); app.quit()`). The restarting message is shown before the relaunch call. A pending workspace-folder change shares the same restart.
2. Once sharing is in effect, the settings show "Sharing is on", the addresses other devices open (`http://<ip>:<port>` for each private-range IPv4 address; "No network address found." when there is none), both plain-words statements (unencrypted HTTP; reachable only while GetWrite is running and this computer is awake, and the device is on the same network) and, since Feature 77, a summary of what paired devices may do and the limit switches (below). A "Sharing is on" indicator (`SharingStatus.tsx`) also shows at the top of the Start Page and of the project shell; since Feature 77 it carries the fixed line "What paired devices can do is set in App Settings." (`SHARING_LIMITS_POINTER`).
   On macOS, sharing keeps serving paired devices after the window is closed only if App Settings → "Keep GetWrite running after its window is closed" is on (PR #282, released in 2.3.0; see `electron-desktop.md`); otherwise closing the window quits GetWrite and stops the server.
3. "Show a pairing code" generates a 6-digit code with a 5-minute countdown. "Generate a new code" replaces the previous one.
4. On the other device, open one of the displayed addresses. An unpaired browser is sent to the `/pair` page, which explains that the device is not paired and takes the code. On success it goes to `/`.

## What is refused

With sharing on, a request that is not the desktop window's is refused unless it carries a valid device cookie, with these exceptions: the `/pair` page, `POST /api/sharing/pair`, `/_next/static/` assets and, since Feature 80, `GET /api/sharing/ready` (the fourth enumerated exception, owner-approved 2026-10-10; see [Desktop server port](#desktop-server-port-feature-80)).

- **No credential, unknown credential, or a damaged credential store:** an API request gets 401 JSON `{ "error": "not-paired", ... }` with header `x-getwrite-gate: not-paired`; a page request is redirected to `/pair`. A damaged store (`device-credentials.json` unreadable or invalid) refuses every non-window request, including the pairing page, with one exception since Feature 80: `GET /api/sharing/ready`, which reads no store (below). The pairing page then answers 401 (read in `gate.ts`: the pairing exception is skipped when the classification reason is `store-corrupt`; measured once against the unpacked app, `GET /pair` from the host answered 401 with the gate header). App Settings says so (the paired-devices message, below; Feature 75's separate `SHARING_STORE_CORRUPT` message no longer exists).
- **A `Host` that does not name this machine:** 403 plain text, header `x-getwrite-gate: host-not-allowed`, never a redirect. The accepted `Host` is exactly `<name>:<port>` with `<name>` one of `localhost`, `127.0.0.1`, an IPv4 address of one of the machine's own interfaces, or `<hostname>.local`, read from `os.networkInterfaces()` / `os.hostname()` at request time (`host-allowlist.ts`). A missing `Host`, a missing port, a wrong port, an IPv6 literal or any other name is refused. This applies to the exempt requests too.
- **A cross-origin state-changing request** from a paired device (POST, PUT, PATCH, DELETE whose `Origin`, falling back to `Referer`, does not match `Host`, or where both are absent): 403 `cross-origin`. `X-Forwarded-Host` is never read.
- **A server told it is bound beyond loopback while the gate is not on** (`GETWRITE_BIND` not a loopback name, `GETWRITE_SHARING` not `1`): every request that is not the window's gets 403 `bind-without-gate`.
- **A pairing code that is wrong, expired, used, or dead** (5 wrong attempts, counted per code): `POST /api/sharing/pair` answers 400 with `{ ok: false, reason: "wrong" }` or `"unusable"`; the internal reason is not sent. The pairing screen shows the matching working copy.
- **A refused in-app fetch** from a device whose credential is no longer valid: `DeviceNotPairedGuard.tsx` (mounted in the root layout, not on native) wraps `window.fetch` and sends the browser to `/pair?reason=unpaired` on a 401 carrying `x-getwrite-gate: not-paired`. A 401 without that header (for example a locked workspace) is not intercepted. On the `/pair` page itself the guard does not navigate (`components/Sharing/pairing-page.ts` holds the path and `isPairingPage()`); `SharingLimitsProvider` makes no limits read there either. Before that fix an unpaired browser on `/pair` was measured reloading continuously (792 navigations in 8 s, all from `GET /api/sharing/limits` answered 401 `not-paired`); after it, 2 navigations in 8 s and 0 `/api/` requests (a throwaway sharing-on standalone server, Playwright Chromium; what the 2 navigations are was not separated, and a sharing-off run gave 2 as well). Typing a code and pairing in a browser after the fix was not scripted.

With sharing off, `runGate` forwards and `POST /api/sharing/pair` answers 404, with one exception. When `GETWRITE_BIND` names loopback (the desktop's default; hosted and `pnpm dev` leave it unset), it refuses a `Host` that is not `localhost`, `127.0.0.1` or `[::1]` on the server's port (403 `host-not-allowed`), and a POST, PUT, PATCH or DELETE whose `Origin` (falling back to `Referer`) names another origin, `null` included (403 `cross-origin`). A write with neither header passes, unlike sharing mode, so non-browser local clients still work. Before this (POS note_d7d147d5, measured 2026-10-19 on the standalone server with the desktop's env): a cross-site `text/plain` POST created and deleted projects, a foreign `Host` was served the project list, and in Chromium a page on another local origin created a project.

## Where state lives

All in Electron's `userData` directory, which is also the server's `GETWRITE_SHARING_DIR`; none of it is under the workspace or projects folder, and none of it changes when the workspace folder changes.

| What                          | Where                                                                                                                                                                                                                                                                                                                  |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The on/off setting            | `sharingEnabled` in `workspace.json` (`readSharingEnabled` / `writeSharingEnabled`, `electron/src/projects-dir.ts`). Absent, corrupt or non-boolean reads as off.                                                                                                                                                      |
| The current pairing code      | Plain code in main-process memory only. `pairing-state.json` holds a salted HMAC-SHA256 of it plus `expiresAt`, `attempts`, `dead` and `used`. Main writes the file when generating a code; the server updates the counters under a lock file. After an app restart there is no in-memory code to show.                |
| Paired devices                | `device-credentials.json` (written by the server at pairing and by the Electron main process for rename and revoke, under one lock file): device id, derived name (for example "Safari on iPad"), creation time and the SHA-256 hash of the credential. Written mode 0600. A missing file means no devices are paired. |
| The credential in the browser | Cookie `getwrite_device`: HttpOnly, `SameSite=Strict`, `Path=/`, `Max-Age=31536000` (365 days, a working value pending owner confirmation, spec OQ-13). Not `Secure`, because the connection is HTTP. Re-issued with a fresh `Max-Age` on every confirmed request.                                                     |

Turning sharing off stops other devices reaching the server and does not delete paired-device credentials.

## How the gate works

- `frontend/proxy.ts` (Next 16's proxy convention; the repo has no `middleware.ts`) calls `runGate` (`frontend/src/lib/sharing/gate.ts`) for every request. It is the single interception layer; the logic is in `frontend/src/lib/sharing/`.
- The desktop window is recognised by the per-launch secret in the `x-getwrite-window` request header. Main generates the secret (`createWindowSecret`, 32 random bytes as hex), passes it to the server as `GETWRITE_WINDOW_SECRET`, and adds the header to every request the window's session makes to the local origin (`installWindowSecret`, `session.webRequest.onBeforeSendHeaders`). As of Feature 80 the readiness poll sends no header at all, and the header is installed on the window's session only after the forked server has proved its identity (below). The secret is not logged, not sent over IPC and not exposed on the bridge. Peer address and `X-Forwarded-For` are not used: a forged `X-Forwarded-For: 127.0.0.1` from another device reached the server unchanged (experiments section A (5), section C run 2).
- The gate reports its classification to route code in the `x-getwrite-classification` request header (`off`, `window`, `confirmed:<id>`, `not-confirmed:<reason>`) after deleting any client copy. A header set by the proxy reached a route and a client-sent copy did not, measured on a standalone build from loopback (section E). Module state set in the proxy was not visible to routes (section A (7)), so none is used.
- `next.config.mjs` sets `experimental.proxyClientMaxBodySize` to the media cap plus 1 MiB, because adding `proxy.ts` brought in Next's default 10485760-byte limit, under which a 12 MB upload returned 500 (security review). After the change, 12 MiB and 98 MiB audio uploads returned 200 with sharing off and with sharing on plus the window header (section G (c)); with sharing off, a file of 100 MiB plus one byte was refused by the media validation with 400 (not run with sharing on).
- `frontend/scripts/sharing-refusal-smoke.mjs` (`pnpm test:sharing-smoke`, from `frontend/`) starts a built standalone server (default `.next/standalone/frontend/server.js`; run `pnpm build` and copy `.next/static` first) with sharing on, walks `app/` for every `route.ts` and `page.tsx`, and checks that each is refused unconfirmed. Last recorded run, on the Feature 80 branch before its merge (2026-10-11, node v24.15.0, against a fresh build): 92 enumerated entries, 4 exceptions (3 enumerated plus `/_next/static/`, one of them store-independent), 34 checks, 0 failures, from the host to itself (loopback and its own LAN address). The baseline on `main` before Feature 80 was 91 entries, 28 checks, 0 failures. The difference is the one new route (`GET /api/sharing/ready`) and six new checks for it; which six was not listed. Under a corrupt store the smoke still requires every other enumerated URL to be refused, and requires `GET /api/sharing/ready` to answer exactly as it does with a healthy store (400 without a challenge, 200 with the proof the script computes itself).

## Desktop wiring

- `electron/src/server-config.ts` holds `PORT`; the bind env, the window load URL, the readiness check, the navigation guard, the IPC sender check and the displayed addresses read it. Feature 80 changed the value from 3000 to 7340; nothing else here depends on it (the single-source claim is held by `electron/tests/server-config.test.ts`).
- The bind: `resolveSharingMode(...).effective` is the one value. `buildServerBindEnv` derives `HOSTNAME` (`0.0.0.0` when effective, `127.0.0.1` otherwise), `GETWRITE_BIND` and `GETWRITE_SHARING` (`1` / `0`) from it, so a non-loopback bind always comes with the gate on.
- Sharing IPC channels (the three device-management channels are in the [Paired-device management](#paired-device-management-feature-76) section), registered in `electron/src/main.ts` and exposed on the bridge (`preload.ts`, `frontend/src/lib/desktop-bridge.ts`): `getwrite:sharing-get-status` (`getSharingStatus`), `getwrite:sharing-set-enabled` (`setSharingEnabled`), `getwrite:sharing-generate-code` (`generatePairingCode`), `getwrite:sharing-get-code` (`getPairingCode`). Each handler refuses a call whose `event.senderFrame?.url` is not on the local origin (`isTrustedSender`, `electron/src/navigation-guard.ts`), including a `null` sender. No HTTP route exposes any of this.
- The window may navigate only to the exact local origin (`isLocalOriginUrl` compares parsed origins; the previous `startsWith` test let `http://localhost:3000@evil.example/` and `http://localhost:30001/` through when evaluated in Node).
- `frontend/components/Sharing/` holds `SharingSettings.tsx` (App Settings section; renders nothing without the desktop bridge), `SharingStatus.tsx`, `PairingScreen.tsx` (the `/pair` page, `frontend/app/pair/page.tsx`), `DeviceNotPairedGuard.tsx`, `PairedDevices.tsx` (Feature 76), the Feature 77 limits files (`LimitSwitches.tsx`, `LimitReason.tsx`, `SharingLimitsContext.tsx`, `limit-gate.ts`, `unlock-prompt-gate.ts`) and `sharing-copy.ts`. The `pair` directory is excluded from the native export (`EXCLUDED_APP_SUBPATHS` in `frontend/scripts/build-native-static.mjs`).

## Desktop server port (Feature 80)

Merged to `main` (PR #267, merge commit `db052756`, 2026-10-11); released in 2.3.0. Spec and measurements: see the header. Every statement below is labelled by the kind of check it rests on: **read** (in code, not run), **built server** (a script against a built standalone server), **real app** (a script driving the real Electron app, either the development code path in a copied tree or an unpacked build), **Chromium** (Playwright Chromium 148.0.7778.96, headless), or **owner** (reported). Runs are dated 2026-10-10 and 2026-10-11, node v24.15.0, macOS, one run per case.

**What the code does (read).**

- `PORT = 7340` in `electron/src/server-config.ts`: a fixed constant with no override and no fallback port. The bind env, window load URL, readiness check, navigation guard, IPC sender check and displayed addresses read it. Saboteur apps own blocks of ten ports and GetWrite's is 7340 to 7349 (ADR-023, `docs/architecture/ADRs/adr-023-saboteur-port-blocks-of-ten.md`).
- Before forking the server the app probes the port on `127.0.0.1`, `::1`, `0.0.0.0` and `::` (`electron/src/port-in-use.ts`). If anything listens it forks nothing, makes no request to whatever holds the port, and the window shows a `data:` page whose text begins "GetWrite did not start. Port 7340 is already in use by another program on this computer" (working copy, not yet reviewed by the owner). An unexpected probe error also refuses, with a message that the check could not be done; a host without IPv6 is not refused for that. A bind failure by the child after a free check (a race) is recognised from the child's output; neither that path nor the could-not-check message was run.
- Readiness: the main process polls `GET /api/sharing/ready?challenge=<64 hex>` (`sharing/server-readiness.ts`, `readiness-identity.ts`, `readiness-http.ts`; server side `frontend/app/api/sharing/ready/route.ts` and `frontend/src/lib/readiness/readiness-proof.ts`). The poll sends no window-secret header. It accepts only the HMAC-SHA256 of its own challenge under a per-launch key, `GETWRITE_READINESS_KEY`, passed to the forked server's environment only and separate from the window secret; the key is never sent. Each poll has a timeout, and polling stops when the forked server exits (`sharing/server-launch.ts`). Only after a valid proof is the window secret installed and the local origin loaded (`main.ts`). The route returns 404 where no key is set, 400 for a malformed challenge, and reads no header, cookie, store or project.
- Gate: `GET /api/sharing/ready` is a fourth enumerated exception (owner-approved 2026-10-10): exact path, GET only, consulted after the `Host` allowlist. It is **store-independent**: it is consulted before the store-corrupt condition, so it answers with an unreadable credential store. This narrows Feature 75's rule that an unreadable store refuses everything by one route that reads no header, cookie, store or project. It is needed because the app's own start-up poll carries no window secret and must succeed for the app to start and show the unreadable-store message. The decision to treat the smoke script's earlier expectation as out of date was the pipeline lead's; the owner's first approval covered the exception without the narrowing being spelled out, and the owner confirmed the narrowing on 2026-10-11 ("Leave as built").
- Development: the development desktop app (`pnpm electron:dev`) follows the constant, because `main.ts` passes `PORT` to its dev server. Plain `pnpm dev` and `pnpm start` stay on 3000 (measured: they listen on `*:3000` with no `PORT` set), as do the hosted-auth fallbacks (`http://localhost:3000`). Known cost, accepted by the owner: a dev desktop app and a packaged app both want 7340.

**What a writer and a paired device meet.**

- The address another device opens now ends in `:7340`. A device paired before the port change normally stays paired on the new port and otherwise is paired again. Basis: Chromium, from the host machine to its own LAN address, two instances of one built server on two ephemeral ports sharing one device store: the cookie `getwrite_device` was host-only (no port in its attributes), the paired context got 200 on the second port's `/api/auth-status` and application page, and a never-paired context on the second port was sent to `/pair`. That run did not vary the browser's cookie scoping against the shared store, so it does not say which of the two would alone suffice; it did not use 3000 or 7340. `device-credentials.json` is not migrated or touched.
- Nothing listens on 3000 for the desktop app, and there is no redirector. The old address on `:3000` no longer answers: Chromium reported `net::ERR_CONNECTION_REFUSED` for both a LAN address and `localhost` with nothing on 3000 (Chromium, headless, so the text of the browser's own error page was not captured), and in the real-app runs TCP connects to 3000 were refused. A saved bookmark was not tried. `localStorage` and `sessionStorage` were separate per port in the same Chromium run.
- Host allowlist with the new port (built server, then the real app): `Host` values naming `:3000`, `:7341`, `:8080`, no port, or a foreign name were refused 403 `host-not-allowed` (10 of 10 on the built server; `<lan-ip>:3000` and `evil.example:7340` on both real-app builds), and the machine's own address with `:7340` was served.

**Measured behaviour of the changed app (real app, sharing off, one run per shape).** With a throwaway listener answering 200 on 7340 bound to `127.0.0.1` only, to all interfaces, or to `::1` only: the window stayed on the `data:` page naming 7340 for the whole 20 s observation (sampled every 400 ms), never showed the listener's page, the listener received 0 requests, no server was forked, and the app did not exit. Same result in the development path and in the unpacked build. A normal launch afterwards showed `http://localhost:7340`. With a second app running: with the unpacked app on 7340, a dev-mode app started with a different `--user-data-dir` also started, showed the same port-in-use message, forked nothing, and left the first app untouched; the reverse order was not run. No port was named in the message. Whether released builds behave this way was not checked, and the packaged server on 3000 was not measured.

Posting the code by `fetch` from inside that dev page worked (200).

## Paired-device management (Feature 76)

Merged to `main` (PR #264); released in 2.3.0. The writer sees, renames and revokes paired devices in App Settings on the desktop. Everything here is desktop-only: it runs through the bridge and the Electron main process, and **no HTTP route exists for any of it** (`frontend/tests/unit/sharing-no-device-routes.test.ts`; in the built-server run, `GET`, `POST`, `DELETE` and `PATCH` on `/api/sharing/devices` and its `rename`/`revoke` paths each answered 404 for a paired device, and the store file was byte-identical afterwards, verification A). A paired device therefore cannot list, rename or revoke devices.

**What the list shows.** Each row shows the device's name and the date it was paired (`createdAt`, formatted in the user's locale with a medium date and short time; a value that does not parse is shown as stored). Only `id`, `name` and `createdAt` ever cross to the renderer; the credential hash is never sent (`listDevices` in `device-management.ts` returns those three fields; verification A found no `credentialHash` and no 64-hex string in the serialized result). There is no "last used", and no "revoke all". Two devices from the same kind of browser get the same automatic name; the paired date tells them apart, and the row's button labels add the date when names collide.

**Rename.** The name is trimmed, then must be 1 to 64 Unicode code points (not UTF-16 units) with no control characters (`U+0000` to `U+001F` and `U+007F` to `U+009F`). An empty (or all-whitespace) name is refused. Duplicate names are allowed. A refusal names its reason (`not-a-string`, `empty`, `too-long`, `control-character`) and the UI shows matching text. Rename changes only that record's `name`. The list is re-read after every attempt and shows what is stored, not what was typed. Renaming did not affect the device's access: in verification A, a renamed device kept being confirmed, and in verification B a rename made while its editor held unsaved text did not interrupt that editor's save.

**Revoke.** Revoke deletes the device's record from `device-credentials.json`; no history is kept. The Revoke button opens a confirmation dialog (focus starts on "Keep <name>") whose text says the device "will be refused from now on", that it "can pair again with a new code", that other devices are not affected, and "Unsaved edits on that device will be lost." That last sentence is there because of a measurement (verification B): after a revoke, text typed in the revoked device's open editor was not saved (the file on disk and the latest revision held only the pre-revoke text), and the device was sent to the pairing screen when its save was refused, 3.2 s after the revoke in that run.

What was measured against a built server, driven from the host machine (not a second device): a revoked device is refused on its first request after the revoke with no server restart, on all 88 gated entries (6 pages redirected to `/pair`, 82 API routes answered 401 `x-getwrite-gate: not-paired`); a second, unrevoked device was unaffected; the old cookie was never accepted again; no refused response set a cookie; pairing again from the same browser replaced the cookie (new value, accepted; the old value still refused).

Limits, stated plainly:

- Revoke takes effect on the revoked device's **next request**. A revoked, idle browser made no request in 45 s of the measurement and kept showing the page it already had, so content already on its screen stays visible until it next talks to the server. A device sitting on the pairing screen when revoked also stayed there (verification B).
- The confirmation text is the only warning about unsaved work; nothing is recovered for the revoked device.
- A corrupt store cannot be repaired from the UI. App Settings says the list cannot be read and names the folder holding the file, in every sharing state (see "Where it appears"). With sharing on or in effect the sentence reads "The list of paired devices cannot be read, so every other device is refused until it is repaired." With sharing off it reads "The list of paired devices cannot be read. When sharing is turned on, every other device will be refused until it is repaired." Open point (spec OQ-18, undecided): with sharing switched on but the restart pending, the first sentence is used and says devices "are refused", which is not yet true in that state.
- Revoke with sharing off was exercised in the real app only with seeded test devices; it was not run on a real paired phone.

**Where it appears.** `PairedDevices.tsx` is rendered by `SharingSettings.tsx` (App Settings, the "Home network sharing" section, below the code controls) once the sharing status has loaded, and renders nothing without the desktop bridge. It is shown when sharing is enabled or in effect (`isSharingActive` is `isEnabled || isEffective`), or when the store holds at least one device; if the first read failed outright, it is shown too. It is also shown whenever the store exists but cannot be read, in every sharing state including sharing off (owner decision 2026-10-10, spec OQ-17): the area then shows exactly one unreadable-store message plus "The file is in <folder>." (the folder is the app's `userData`, obtained at runtime), and a list that was already showing is replaced by that message. With sharing off and a missing or empty store it is not shown. Once shown it stays shown for that mount, so revoking the last device does not remove its own confirmation message. Shown with no devices: "No devices are paired." The message is in a polite live region; the sharing-off wording is working copy not yet confirmed by the owner. Also undecided and unchanged: if the sharing status itself fails to load, `SharingSettings.tsx` does not mount the paired-devices area.

**Refresh.** The list is re-read on mount, after each action, and every 5 seconds (`PAIRED_DEVICES_POLL_INTERVAL_MS = 5000`), so a device paired from another room appears without the writer acting. Ticks are skipped while the document is hidden, and becoming visible triggers one read. A refresh replaces only the list, never the rename field's text or an open revoke dialog.

**IPC channels and bridge methods** (registered in `electron/src/main.ts`, exposed in `electron/src/preload.ts` and `frontend/src/lib/desktop-bridge.ts`; handlers in `electron/src/sharing/device-ipc.ts`):

| Channel                          | Bridge method                  |
| -------------------------------- | ------------------------------ |
| `getwrite:sharing-list-devices`  | `listPairedDevices()`          |
| `getwrite:sharing-rename-device` | `renamePairedDevice(id, name)` |
| `getwrite:sharing-revoke-device` | `revokePairedDevice(id)`       |

Each handler's first statement is the sender check (a frame not on the local origin is refused, as for the other sharing channels), and the id must be a non-empty string. Results are discriminated by `kind`: list returns `ok`, `missing` or `corrupt` (with `storeDirectory`); rename and revoke return `ok`, `not-found`, `corrupt`, `lock-not-acquired` or `write-failed`, and rename also `invalid-name` with a reason. A device removed by someone else first reads as `not-found` ("This device was already removed."). Main logs only counts and outcome kinds, never names or ids.

**The writer and its lock protocol** (`device-store-writer.ts`). Main writes `device-credentials.json` itself, serialised with the server by the same lock file the server uses (`frontend/src/lib/sharing/file-lock.ts`): the lock path is exactly `<store path>.lock`, created exclusively (`wx`, mode 0600); on contention it retries (200 attempts, 25 ms apart by default) and removes a lock older than 30 s; if the lock is not acquired the outcome is `lock-not-acquired` and nothing is written. The store is read inside the lock and handled as parsed JSON, so unknown fields survive a rewrite; a store that cannot be read cleanly (unreadable, invalid JSON, wrong `version`, or invalid records) is refused with its bytes untouched. The write goes to a temporary file (mode 0600, fsynced) and is renamed over the store; the lock is removed afterwards. `device-management.ts` never touches `pairing-state.json`. The agreement with the server's implementation is held by contract tests (`sharing-device-concurrency.test.ts`); a real Electron window running these handlers has not been observed.

**Status of the evidence.** Measured: the built-server results above, and the suites recorded in experiments "Final suites" at an earlier tip (frontend 595 files / 6035 passed, 1 skipped; electron 23 files / 322 passed; typecheck clean; sharing smoke 90 entries, 28 checks, 0 failures; not re-run for the Task 15 change in this document's sources). Also measured, by the pipeline lead with a scripted driver and a throwaway settings folder, in the real Electron app in development mode and in an unpacked build (experiments "Exercise in the desktop app" sections, 2026-10-09 and 2026-10-10), all with seeded test devices and sharing off: the list, a blank-rename refusal, a rename, the revoke dialog, cancel and revoke, a device added to the file appearing on the poll (0.79 s to 1.29 s later, where in the 5-second interval the write fell was not controlled), and the unreadable-store message with sharing off. Reported by the owner (not pasted, 2026-10-09, own unpacked build, Android phone, commit not stated, made before Task 15): pairing with sharing on, the phone appearing in the list, revoking the connected phone sending it to the pairing screen at its next action, and pairing again. Not verified: a rename surviving an app restart in the real app; revoke with sharing off on a real paired phone; the unreadable-store message with sharing on or pending in the real app (component tests only); the owner's review of the working-copy strings in `sharing-copy.ts` marked "Working copy" (about fourteen, plus the new sharing-off wording); Node 20 (no Node 20 on the build machine; CI is the check). Feature 77, now on `main`, limits a paired device's locking, unlocking and project deletion (next section).

## Paired-device limits (Feature 77)

Merged to `main` (PR #266, merge commit `fc730749`, 2026-10-10); released in 2.3.0. Spec and measurements: see the header. The owner's manual check with an Android phone (Task 31) was done on 2026-10-10 and is reported by the owner, not observed by the pipeline: steps 1 to 6, 8 and 9 were reported as "The other steps seem to work." with no per-step detail; step 5 (the confirmation for Limit unlocking) was seen and accepted; step 7 (creating the workspace passphrase from the phone is refused) was **not** done, because the owner's workspace already has a passphrase, so step 7 rests on scripted checks only; no observation was reported about the phone's open editor when the desktop locks the workspace. The check found the pairing page reloading (see the `DeviceNotPairedGuard` bullet near the top of this document). The working-copy strings are unreviewed (one copy pass is planned across the sharing features); every string named below is working copy.

**What it is.** Five switches, set on the desktop, that stop a paired device doing certain things. Each is on (restricted) by default, applies to all paired devices together (there is no per-device setting), and takes effect on the next request with no restart.

| Key                 | Label in App Settings    | What a paired device cannot do when it is on                                                                                                      |
| ------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `projectDeletion`   | Limit project deletion   | Delete a project (`POST /api/project/delete`)                                                                                                     |
| `unlocking`         | Limit unlocking          | Unlock the workspace, or resume interrupted conversions (`unlock`, `resume` on `POST /api/encryption`)                                            |
| `locking`           | Limit locking            | Lock the workspace (`lock`)                                                                                                                       |
| `encryptionChanges` | Limit encryption changes | Enable encryption on a project with an existing workspace key (`enable`), or export an unencrypted copy (`export`)                                |
| `permanentDeletion` | Limit permanent deletion | Purge from Trash or empty Trash (`POST /api/project/[project-id]/trash/purge`), delete a revision (`DELETE /api/resource/revision/[resource-id]`) |

Creating the workspace passphrase (`enable` with a non-null passphrase) from a paired device is always refused, whatever the five switches say (403, `limit: "encryptionChanges"`). The desktop window is never limited, and neither is a server with sharing off. There are no switches for sharing, pairing or device management; those are desktop-only IPC with no HTTP route (Feature 76).

**Where the state lives.** `sharing-limits.json` in `userData` (the server's `GETWRITE_SHARING_DIR`): `{ "version": 1, "limits": { ... five booleans ... } }`, `true` meaning restricted. A limit is off only when the file positively says `false`. A missing, unparseable, mistyped, other-version or unreadable file means all five are on, on both the server and the desktop side. The server reads the file fresh on every limited request and on every read of the limits (no cache). The desktop side (`electron/src/sharing/limits-store.ts` writer, `limits-ipc.ts`) writes it under the same lock-file protocol as the device store; the first change to a missing file writes all five keys; a change is refused while the file cannot be read, leaving it as it is. IPC channels `getwrite:sharing-get-limits` and `getwrite:sharing-set-limit`, bridge `getSharingLimits` / `setSharingLimit`, same sender check as the other sharing channels. The server side is `frontend/src/lib/sharing/limits-store.ts` (reader), `limits-check.ts` (`decideLimit`, `checkLimit`, `limitsRoleFor`) and `limits-copy.ts` (refusal messages). A shared fixture set in `frontend/tests/fixtures/sharing/` keeps the two readers in agreement.

**How it is enforced.** In the four route files (`app/api/project/delete`, `app/api/project/[project-id]/trash/purge`, `app/api/resource/revision/[resource-id]` for `DELETE`, `app/api/encryption` for `POST`, per action), by `checkLimit`, which reads the `x-getwrite-classification` header the gate sets. `window` and `off` are allowed; a missing, empty or unparseable header is refused for every limited action without reading the file (the fail-closed reading, owner decision 2026-10-10); a classified paired device is checked against the file. A refusal is HTTP 403 `{ "error": <text>, "limit": <key> }`, with no `x-getwrite-gate` header and no redirect, so it is not mistaken for the gate's 401. On the encryption route the body is read from a clone; an unreadable body or an unknown action from a paired caller is refused as `encryptionChanges`. `GET /api/sharing/limits` answers `{ "role": "exempt" }` for the window or sharing off, and `{ "role": "paired", "limits": { ... } }` otherwise (all five `true` for a missing or unparseable header or an unreadable file), with `Cache-Control: no-store`; it accepts no change to a limit. A walk-the-route-files test and `sharing-gate-enumeration.test.ts` keep the limit imports confined to those routes and the route counted by the gate smoke (91 entries).

**What a paired device sees.** Controls for a limited action are disabled with a visible reason (project Delete, Delete selected permanently, Empty trash, Delete Revision, Lock workspace, Export an unencrypted copy, Encrypt this project…). On the Start page, with Limit unlocking on and the workspace locked, the passphrase prompt is replaced by "This workspace is locked. It has to be unlocked on the computer where GetWrite is installed."; with Limit unlocking off the prompt is shown as before. When the limits read has failed (`didLastReadFail` on the limits hook; not while still pending), a locked workspace shows "This workspace is locked. This page could not check whether unlocking is allowed here." with a "Try again" button that re-reads, and still no passphrase field (`UNLOCK_CHECK_FAILED_MESSAGE`, `UNLOCK_CHECK_RETRY_LABEL`); this is covered by component tests only and was not measured in a browser. A paired browser is never offered the field to create the workspace passphrase. Project deletion now waits for the server and says "The project was not deleted." with the server's message if it is refused. A refused lock, resume, Trash purge or revision delete shows a line with the server's message; a refused revision delete says "Deleting a revision is turned off here. Do it at the desktop." (`REVISION_DELETE_REFUSAL_MESSAGE`; the 403 still carries `limit: "permanentDeletion"`). The strings are in `sharing-copy.ts` and `limits-copy.ts`.

**What the desktop shows.** The switches sit in App Settings' "Home network sharing" section (`LimitSwitches.tsx`, heading "What paired devices may do"), each persisting on change, plus a summary generated from the effective limits ("Paired devices can ... They cannot ..."). Switching Limit unlocking off opens a confirmation ("Turn off Limit unlocking?") and the three statements stay beside the switch: the passphrase is typed on the paired device; it is sent over the unencrypted connection, where others on the network could record it; a recorded passphrase also unlocks the files at rest. If the file cannot be read the section says every limit is on and gives the folder.

**Storybook and e2e.** Storybook had no limits provider, so the six components that read the limits state would throw in stories; `frontend/.storybook/preview.tsx` now wraps every story in `StaticSharingLimitsProvider` (`SharingLimitsContext.tsx`; default exempt, per-story override through `parameters.sharingLimits`). CI e2e failed on the PR before this; the failing names were not seen, so that this was the cause is inferred. `pnpm test:e2e` run locally after the change: 214 passed, 1 skipped. The CI re-run result was not seen by the pipeline before the merge; the owner reported afterwards that CI passed. The e2e suite was not part of the pipeline's final suites for this feature.

**What was measured, and by what.** All by scripts kept under `specs/features/paired-device-limits/scripts/`; none from a second physical device (the owner's phone check is separate and was not itemized, see above).

- Built servers (the standalone build and `next dev`, script from the host machine to loopback, node v24.15.0): 195 checks, 195 passed in each build. A paired device with all five on was refused 403 with the body keys exactly `error,limit` on every limited action and the action was not applied; with one key off only that key's actions went through, on the very next request; the window was never refused, also with the file unreadable; no cookie got 401 `not-paired`; a forged `x-getwrite-classification` from the client did not change the result. `pnpm test:sharing-smoke`: 91 enumerated entries, 28 checks, 0 failures.
- Playwright Chromium, a paired cookie against a built server (107 checks, 0 failed): no password input was ever in the document for a paired browser with Limit unlocking on, with the limits read normal, held 6 s or blocked; creating the workspace passphrase showed no field even with all five off; refusals were visible in the four stale-answer cases (the stale answer was simulated by answering the limits read in the browser, not a real flip in time).
- Two scripted paired clients and the window (31 checks, 0 failed): each client saw a change made by the other, or by the window, on its next request and after a reload.
- The real Electron app, scripted, in development mode and as an unpacked build (167 checks, 0 failed in each): each of the five switches clicked in the real App Settings changed the file, the paired device's next request and nothing else, with no restart; Limit unlocking off showed the confirmation and cancel left the file byte-identical; an unreadable file (mode 0, or a directory at the path) gave the message, all five on, and a refused change; a missing or invalid file was replaced by a valid one on the first change; the window was never refused.
- Suites at the final tip of the work (node v24.15.0): frontend 607 files, 6417 passed, 1 skipped; electron 25 files, 384 passed; cli 22 files, 144 passed; both typechecks and lint clean (0 errors).

**Limits, stated plainly.**

- An already-open page on a paired device does not change on its own when another client or the desktop locks or unlocks the workspace. Measured with two scripted clients: no change within 7 s without a reload (an open unlock dialog stayed; an Open button stayed); the next request and a reload showed the new state. Why was not looked at; a longer wait and a focus or visibility event were not run.
- With the limits read failing, a paired browser on a locked workspace showed neither the passphrase prompt nor the "unlock at the computer" message (Playwright, read blocked). That was the measurement before commit `ad25f1bd`; that commit adds the "could not check" message and "Try again" button (see "What a paired device sees"), covered by component tests only and not re-measured in a browser.
- Historical: before `ad25f1bd` the refusal text for a revision delete read "Permanently deleting from the trash is turned off here. Do it at the desktop." because the `permanentDeletion` message was shared. The revision route now passes its own message (see "What a paired device sees"); that is a code and unit-test change, not re-measured against a built server.
- Dialog text colour: text with no colour class placed directly under `<body>` (where Radix dialogs are portaled) was measured black in both themes (`getComputedStyle`, Playwright Chromium, throwaway server of `ad25f1bd`, theme class set by the script). Read, not measured in the rendered dialogs: the three warning lines in "Turn off Limit unlocking?", the "The project was not deleted. …" line and the revision-delete refusal line had no colour class; `ad25f1bd` gives them `text-gw-secondary`. - After another paired client locked the workspace (Limit unlocking and Limit locking off), a paired browser's open editor showed "Autosave failed" after typing, with no unlock prompt. ## Environment variables the desktop app sets

`GETWRITE_SHARING`, `GETWRITE_SHARING_DIR`, `GETWRITE_BIND`, `GETWRITE_WINDOW_SECRET` and, since Feature 80, `GETWRITE_READINESS_KEY` are set by the Electron main process for its own server. They are not meant to be set by hand. Only `GETWRITE_SHARING=1` turns the gate on in the server (`readSharingEnv`); any other value, or unset, leaves it off. `GETWRITE_BIND` unset means undeclared, so `pnpm dev`, hosted deployments and tests are unaffected.

## Accepted limits

Recorded by the owner on 2026-10-09 after the security review; no work is added for them in this feature.

- The connection is plain HTTP. A device cookie captured on the network works until that device is revoked (Feature 76); revoking is by the writer, from the paired-devices list, and there is no expiry short of the cookie's 365-day `Max-Age`.
- Any device on the network can make the current pairing code unusable with five submissions, including malformed ones. The attempt limit itself held under 200 parallel guesses (measured at gate level).
- The cookie is scoped to the host it was set on and is not port-scoped. If the desktop's address changes, the device must be opened at the new address and paired again. A router address reservation is the dependable remedy. For the port change see the next section: a device paired on 3000 normally stays paired on 7340, measured in Chromium only; the owner's Android phone also stayed paired (owner's report, 2026-10-11, browser not named).
- `<hostname>.local` is accepted by the gate but is not displayed in the window. Whether it resolves on a given phone, and whether `os.hostname()` returns the name a device resolves, is not measured. A name supplied by a router or reverse proxy (for example `nas.lan`) is refused.
- IPv6 is not in scope. Under a `0.0.0.0` bind (measured when the port was 3000), `curl -6 http://localhost:3000/` did not connect while `curl -4` did (cause not established).
- Uploads pass through the proxy, which buffers request bodies in memory up to the configured limit. The memory cost was not measured.
- A leftover lock file younger than 30 seconds delays pairing (measured). The pairing-state file is written by main without the lock, so a new code can be overwritten by a simultaneous wrong guess and stop working (reading, not run). There is no minimum secret length server-side, and the window header is forwarded to routes.
