## Implementation record (moved from CLAUDE.md)

Moved verbatim from the root `CLAUDE.md` "Electron Shell" section on the CLAUDE.md split. Statuses are as of that text.

- Port: `electron/src/server-config.ts`'s `PORT` is a fixed constant with no override and no fallback port. Feature 80 (PR #267, released in 2.3.0) changed it from 3000. A development desktop app (`pnpm electron:dev`) follows the constant, so a dev desktop app and a packaged app both want 7340 (the second one started shows the port-in-use message); plain `pnpm dev` / `pnpm start` and the hosted-auth fallbacks stay on 3000. Nothing listens on 3000 for the desktop app and there is no redirector. Saboteur apps own blocks of ten ports and GetWrite's is 7340 to 7349 (ADR-023).
- Start-up order (Feature 80): `port-in-use.ts`'s `createPortGuard` probes the port on `127.0.0.1`, `::1`, `0.0.0.0` and `::` before anything is forked, and when something listens it forks nothing and the window shows a `data:` page naming the port (an unexpected probe error also refuses, with a message that the check could not be done); `sharing/server-readiness.ts` (`waitForServer`, with `readiness-identity.ts`, `readiness-http.ts` and `server-launch.ts`'s `runLaunchSequence`) then polls `GET /api/sharing/ready?challenge=…` with no window-secret header and accepts only the HMAC proof under a per-launch key (`GETWRITE_READINESS_KEY`, passed to the forked server's env only, separate from the window secret), each poll with its own timeout and polling stopping when the child exits; only after a proof is the window secret installed and the local origin loaded.
- `electron/src/projects-dir.ts` decides the projects location and is unit-tested (`electron/tests/`, run in CI by `.github/workflows/electron-checks.yml`). A packaged build defaults to `~/Documents/GetWrite` — visible, backup-friendly, and where writers look — with a per-user override recorded in `userData/workspace.json` (`resolveProjectsDir` = override ?? default). A development build keeps using the repo's `projects/`. Packaged builds previously stored projects under `process.resourcesPath` — inside `GetWrite.app` — where a drag-to-Applications update silently destroyed every project and runtime writes invalidated the bundle's code signature. `migrateLegacyProjectsDir` drains each `legacyProjectsDirs()` entry on every packaged launch, never overwriting an existing entry and never deleting on failure. Changing the location needs a restart, because `GETWRITE_PROJECTS_DIR` is fixed when the Next server is forked.
- Feature 88 (branch `fix/desktop-defects`; PR #272, released in 2.3.0): `writeWorkspaceConfig` writes `workspace.json` through a temporary file in the same directory plus a rename (the temp file is fsynced before the rename and the directory after it, unit tests pin that order; an existing file's mode is kept, a new one gets the default; an injected failed write left the old bytes; a damaged file still reads as empty; a real crash or power loss was not tested), and the global noise-word IPC handlers (`noise-words-ipc.ts`'s `createGlobalNoiseWordsHandlers`) take `app.getPath("userData")` in both builds, since `projectsDirEnvironment().userDataDir` is `""` unpackaged (adding a global noise word in the dev app then succeeded and persisted across a restart, in a throwaway workspace.json; the pre-fix failure was not re-run in that setup). Compile in the desktop app: no product change; the earlier "no download seen" run used a verification-script hook that called `require` inside `app.evaluate` (`require is not defined`), and a require-free hook recorded `will-download` and a file in the dev app and an unpacked build (txt only); that the original run failed for this reason is a hypothesis, not repeated.
- DOCX import fork options (Feature 88): `docx-import/fork-options.ts`'s `buildDocxWorkerForkOptions` gives the fork the base environment plus `GETWRITE_PROJECT_TYPES_DIR` (the templates directory) and `cwd: getRepoRoot()`, in both builds; the Scrivener fork is unchanged (by reading, its worker does not read project types). Measured: Word import (Blank, Novel) completed in the dev app launched from a non-`electron` directory and in an unpacked arm64 build launched from `/` and from the repo root; the unfixed tree was not run in those runs, and a Finder/`.dmg` launch and non-arm64 were not run.
- Sharing main-process detail (Feature 75, released in 2.3.0): `pairing-code.ts`/`pairing-session.ts` generate a 6-digit code with `crypto.randomInt`, hold the plain code in memory only and persist a salted HMAC to `userData/pairing-state.json` (5-minute lifetime). `addresses.ts` lists the private-range IPv4 URLs the window shows (the same enumeration the server's `Host` allowlist starts from); `store-status.ts` reports whether `device-credentials.json` is `ok`/`missing`/`corrupt`; `sharing-status.ts` assembles the status. `will-navigate` compares parsed origins (`isLocalOriginUrl`) instead of a URL prefix. UI: a "Home network sharing" section in `AppSettingsDialog.tsx` (`SharingSettings.tsx`) and a "Sharing is on" indicator on the Start Page and in `AppShell.tsx` (`SharingStatus.tsx`).
- Paired-device limits main side (Feature 77, merged to `main`, PR #266): `limits-store.ts` (main-side writer of `userData/sharing-limits.json`; `setLimit`, read result kinds including unreadable; the first write of a missing file produces all five keys) and `limits-ipc.ts` (`createLimitsHandlers` — sender check first, then key/boolean validation; a change is refused while the file cannot be read); IPC channels `getwrite:sharing-get-limits` and `getwrite:sharing-set-limit`, bridge methods `getSharingLimits`/`setSharingLimit`.
- Import worker detail: the Scrivener worker reports one of four discriminated outcomes, the DOCX worker one of five; both are bundled by esbuild (`build:worker`) and shipped via `electron-builder.yml`'s `extraResources`, since `utilityProcess.fork` cannot fork a script packed inside `app.asar` (the same reason the Next server itself ships as `extraResources`). The Scrivener "Import" and DOCX "Import Word Document" buttons on `StartPage.tsx` render only when a desktop bridge is present.
- Closing the window (PR #282, released in 2.3.0): `main.ts`'s `window-all-closed` quits on every platform unless `keep-running.ts`'s `shouldQuitWhenAllWindowsClosed(process.platform, keepRunning)` says otherwise, which it does only on macOS with `keepRunningWhenWindowClosed: true` in `userData/workspace.json` (absent, non-boolean or a corrupt file reads as off). Before this, macOS always kept running after the window closed and other platforms always quit. The setting is read at each close, so a change needs no restart; the existing `activate` handler reopens the window from the Dock. App Settings shows the switch (`frontend/components/AppSettings/KeepRunningSetting.tsx`) through `getwrite:keep-running-get`/`-set`, which check the sender first and refuse a non-boolean; `get` reports `supported: false` off macOS and the switch is not shown. Windows and Linux would need a tray icon to reopen or quit a windowless app, so they always quit. Checked in unit and component tests; not run in the desktop app.
