# Word-count goals (developer)

Feature 61. Spec: [specs/features/word-count-goals.md](../../specs/features/word-count-goals.md).

Purpose

Two independent, optional, total-length word-count goals — one on the project, one on an individual text resource — with an in-app write path for both. The project-level `wordCountGoal` field already existed on `ProjectConfigSchema` (seedable from a project-type spec) before this feature, but the app had no way to set, change, or clear it short of hand-editing `project.json`; this feature adds that write path and introduces the new per-resource field. Both are distinct from Feature 59's `dailyWordGoal` (per-day, not total) and untouched by it.

## Project-wide goal

- Core: `frontend/src/lib/models/word-count-goal-core.ts` — `setWordCountGoalCore(projectId, goal)` sets (non-negative integer) or clears (`null`) `config.wordCountGoal` in `project.json`. It mirrors `writing-log-core.ts`'s `setDailyWordGoalCore` exactly: does a read-modify-write of `project.json` through `updateProjectJson` (the read happens inside the `project.json` file lock) inside `withMetaLock`, deletes the config key on `null` rather than ever writing `undefined`, and uses `atomicWriteFile` with the same options. Touches no other config key. `InvalidWordCountGoalError` maps to HTTP 400; locked/keyless-project errors are not caught here and propagate up unchanged.
- Route: `frontend/app/api/project/word-count-goal/route.ts` — `PUT /api/project/word-count-goal`, body `{ projectId, wordCountGoal }` (`wordCountGoal` a non-negative integer or `null`). `projectId` is validated as a UUID; no client-supplied path is accepted. Locked-access errors are rethrown for `withStorageContext` to map to 401/409.
- Client transport: `frontend/src/lib/api/word-count-goal.ts` — `setWordCountGoal(projectId, goal)`, resolved through `createTransport`: HTTP on web/desktop (`httpWordCountGoalTransport`), an in-process backend (`frontend/src/store/transport/native-word-count-goal-backend.ts`, + `.web-stub.ts`) on native, both running the same core. The HTTP path validates its response body against `SetWordCountGoalResponseSchema` (`lib/api/schemas.ts`) and rejects (reporting through `reportTransportValidationFailure`) on a malformed body, network error, or non-2xx status — the save has by then already succeeded server-side, so the caller re-reads rather than trusting a fabricated value.
- UI: `frontend/components/Layout/WordCountGoalField.tsx`, rendered in the "Writing Goals" tab of Project Settings (`ProjectSettingsDialog.tsx`) directly below `DailyWordGoalField.tsx`. An empty input parses to `null` (clear); anything else must be a non-negative integer or the field shows `INVALID_MESSAGE` ("Enter a whole number of words, 0 or greater.") without calling the transport. Errors and the saved-confirmation message are conveyed by text and `role="alert"`/`role="status"`, never by color (STYLING.md: red is reserved for position/canonical-state indicators, never used here).
- Staleness: `AppShell.tsx` passes `initialWordCountGoal={project?.config?.wordCountGoal}` into `ProjectSettingsDialog` the same way, and from the same unrefreshed `project` object, as `initialDailyWordGoal` (Feature 59). Reopening Project Settings after a save but before a project reload can show the old value, identically to the daily goal's known staleness — confirmed in the running app: the write itself reaches disk immediately, but the field re-populates from the stale value until a full reload.

**Copy strings (confirmed against `WordCountGoalField.tsx` and the running app):** heading "Project word-count goal"; label "Total word-count goal"; helper text "Total words you're aiming for across the whole project. Separate from the daily writing goal above. Leave empty for no goal."; button "Save word-count goal" / "Saving…"; saved messages "Project word-count goal saved." / "Project word-count goal cleared."; validation error "Enter a whole number of words, 0 or greater."

## Per-resource goal

- Schema: a new optional `wordCountGoal` field (non-negative integer) on `TextResourceSchema` (`frontend/src/lib/models/schemas.ts`) and the `TextResource` interface (`frontend/src/lib/models/types.ts`). Scoped to text resources only, mirroring `wordCount`'s own scoping.
- Transport: **no new transport module was needed.** This is the Task 3 finding this doc is here to record: the resource goal rides the _existing_ sidecar transport, `updateSidecar` (`frontend/src/lib/api/resources.ts`), because that transport's HTTP path never validated its response body for any field to begin with — it is fire-and-forget by design. Clearing goes through `updateSidecar`'s `clearKeys` parameter (`["wordCountGoal"]`), not an `undefined`-valued field in the body, since `JSON.stringify` drops an `undefined`-valued key before the request ever reaches the server (the same bug class Feature 61's own brief on `patchRevisionContent` names).
- UI: `frontend/components/Sidebar/WordCountGoalSection.tsx`, rendered from `frontend/components/Sidebar/MetadataSidebar.tsx` inside a `CollapsibleSection title="Word count goal"`, gated on `editableResource.type === "text"`. Inside that, the component's own `LabeledField` repeats the same "Word count goal" text as its label — so the string appears twice (section title, field label), both identical. Patterned on `EntitySection.tsx`'s persist-with-`clearKeys` approach: `updateResource` optimistically updates Redux, then `updateSidecar` writes the sidecar. Validation (non-negative integer, or blank to clear) happens client-side before any request; an invalid value shows a `role="alert"` message and calls no transport. There is no separate save action: setting a value persists immediately as it's typed.
- Progress: when a goal is set and greater than 0, the section renders `frontend/components/WorkArea/WordCountProgressBar.tsx` (`current`/`goal` props), and updates live as the resource's word count changes (confirmed: typing into the editor and letting autosave run updates the bar with no reload). The bar uses only `bg-gw-primary`/`bg-gw-chrome2` tokens — confirmed no red is used anywhere in its rendering, including when the goal is exceeded. Fixed (Task 12): clearing the goal now updates the Redux copy of the resource immediately. `withoutWordCountGoal` (`WordCountGoalSection.tsx`) sets `wordCountGoal: undefined` explicitly on the object dispatched to `updateResource`, rather than omitting the key — mirroring `EntitySection.tsx`'s `withEntityKind` clear precedent. This matters because `updateResource`'s reducer (`store/resourcesSlice.ts`) merges a dispatched partial update with a shallow `{ ...previous, ...payload }` spread, which only overwrites a key it sees _present_ on the payload; an omitted key silently left the previous value in place, so the progress bar kept showing the old goal until a full reload even though the on-disk sidecar clear (via the separate `clearKeys` parameter) had already completed. `JSON.stringify` still drops the `undefined`-valued key before the HTTP request body is built, so the wire payload and on-disk clearing mechanism (`clearKeys`) are unchanged — only the Redux-side merge behavior changed. A second, related defect is also fixed: `updateSidecar` (`lib/api/resources.ts`) now checks the HTTP response status and throws on a non-2xx response (400/401/409, including a locked or keyless project), mirroring `deleteResource`/`deleteFolder`'s existing pattern; `WordCountGoalSection.tsx`'s `persist()` surfaces that rejection as a visible `role="alert"` message ("Couldn't save the word count goal. Your input hasn't been lost — try again.") without rolling back the writer's typed input, since the optimistic Redux update is not reverted on a failed write.
- No aggregation: the resource goal does not appear in the Data view, the "By status" roll-up (Feature 60), or anywhere else outside that resource's own sidebar section. It is scoped purely to that one resource.

## Goal filter

Feature 98. Spec: [specs/features/writing-goal-filter.md](../../specs/features/writing-goal-filter.md). An optional filter chooses which documents count toward the project-wide total goal and the daily goal ([writing-log.md](./writing-log.md#goal-filter)). **The per-resource goal is not filtered or changed.**

- Storage: `config.goalFilter`, one query AST (the smart-folder query shape), never a reference to a saved query. Clearing deletes the key. Setting or clearing the filter touches no other config key, and setting a goal does not touch the filter. A project type never carries, seeds or captures a filter.
- Set and clear: `PUT /api/project/goal-filter`, body `{ projectId, goalFilter }` (`goalFilter` an AST, or `null` to clear). Core `goal-filter-core.ts` (`setGoalFilterCore`); route `app/api/project/goal-filter/route.ts`; native backend `native-goal-filter-backend.ts` (+ `.web-stub.ts`); client `lib/api/goal-filter.ts`. The response `{ goalFilter }` is validated by `SetGoalFilterResponseSchema`; `goalFilter` is absent after a clear. A refusal is HTTP 400 with the validator's message (`goal-filter-validation.ts`): not a valid AST, a `ref` or `param` node ("A goal filter can't refer to a saved query."), no condition, nesting deeper than 4 levels or more than 50 conditions, or a relative date, that is an "in the last N days" condition ("A goal filter can't use a relative date, because the figure would change without any edit."). Locked and keyless projects return 401 and 409.
- Read: `GET /api/project/goal-filtered-total?projectId=`. Core `goal-filtered-total-core.ts` (`evaluateGoalFilteredTotal`); route `app/api/project/goal-filtered-total/route.ts`; client `lib/api/goal-filtered-total.ts`. The body is validated by `GoalFilteredTotalResponseSchema`, whose members are strict, so an `unavailable` body carrying a `total` key is malformed. It is one of:
  - `{ status: "not-filtered" }`: no filter is stored; the caller keeps its unfiltered behaviour.
  - `{ status: "total", total }`: the sum over the matching documents.
  - `{ status: "no-match", total: 0 }`: the filter ran and selected no live text document. This is a real zero.
  - `{ status: "unavailable", reason: "invalid-filter", message }`: the stored filter fails validation or holds a `ref` or `param` node.
  - `{ status: "unavailable", reason: "missing-field", fields }`: a condition names a field the project no longer defines. A deprecated field still evaluates normally.
  - `{ status: "unavailable", reason: "read-failed", cause }`: `cause` is `locked`, `missing-sidecar`, `corrupt` or `unreadable`.

  An unavailable result carries no `total` key and is a 200 body, not an error status. An error the core does not recognise is rethrown to `withStorageContext`.

- What counts: membership is the smart folder's evaluator over the project's live resources, run on the server (one core for the route and native), restricted to `type === "text"`. A trashed resource is not listed, and a restored one (same id) counts again. Words per document are `userMetadata.wordCount ?? wordCount ?? 0` from the sidecar, the figure the Data view uses; the evaluator's content-derived counts are not summed. A `resources/<id>` directory with no sidecar makes the figure unavailable rather than being skipped. Nothing is cached; each read re-evaluates. Read time and files read for the total and the daily figure were measured at 500 to 20,000 documents on one machine, over HTTP on web and desktop and at core level in Node; the figures, the method and what was not measured (Android, cold disk, real projects) are in `specs/features/writing-goal-filter/experiments.md`. No limit is promised.
- Failure rule: a figure that cannot be computed is never returned as 0. A missing `resources/` directory (`ENOENT`) is an empty project; any other listing error, a sidecar read error or a project-config read error makes the figure unavailable.
- Writing Goals tab: `components/Layout/GoalFilterSection.tsx`, below the two goal fields, with "Save goal filter" and "Clear goal filter" buttons and no autosave. A stored filter that cannot be used shows "Your saved goal filter can't be used. Change it or clear it." and can still be cleared.
- Daily goal under a filter: see [writing-log.md](./writing-log.md#goal-filter). The aggregate carries `isFiltered` and `hasNoMatch`. A filtered daily figure that cannot be computed is HTTP 500 and shows no number. Entries count only when they carry a `documentId`. Canonical saves write it on every new word entry and skipped-save marker; entries written before that carry none and are left out under a filter.
- Data view goal bar (Task 16): `FilteredGoalBar` in `components/WorkArea/DataView.tsx` replaces the plain progress bar in the "Writing Goal" section only while a goal filter is set (the app shell passes `useDataViewFilteredTotal`, which wraps `useFilteredGoalTotal`, so a figure read for an earlier filter or project is not shown). The states: while the figure is being read, a status line "Loading word count…" and no progress value; on `total`, the label "Counting selected documents" above the progress bar showing the filtered total against the goal; on `no-match`, the same label, the real value 0 and "No documents match your goal filter"; on `unavailable`, an alert "Total word count is unavailable" and no progress value. The "Total words" overview tile, the status roll-up and the breakdown do not change under a filter. With no filter the bar is unchanged and keeps following the active smart folder.
- Paired devices use the same HTTP routes, and no new paired-device limit switch is added. `pnpm --filter getwrite-frontend test:sharing-smoke` exited 0 on the branch (enumerated entries 102, checks 34, failures 0), run before `8ac86b00`, which changed no sharing code (`experiments.md`, Task 26). A manual pairing check is not recorded.

## Locked/keyless projects

Both goals fail closed on a locked or keyless encrypted project (`isLockedAccessError`, `locked-access.ts`) rather than degrading to zero or absent — confirmed by `frontend/tests/unit/word-count-goal-core.test.ts`, `frontend/tests/unit/word-count-goal-route.test.ts`, and the existing generic `frontend/tests/unit/resource-crud-core-locked-sidecar.test.ts` (which already covers `updateSidecarCore` for any field, including `wordCountGoal`, with no field-specific case needed for the resource goal).

## Progress display is never red

Per FR-3, progress toward either goal is never shown in red anywhere in the UI — a measured property of the current markup (`WordCountProgressBar.tsx`'s classes), not a claim about future styling.
