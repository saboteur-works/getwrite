# Entities (developer reference)

Developer reference for the entity layer: declared entities, mentions, aliases, highlighting, roster, scoped compile, co-occurrence, authored relationships, the relationship graph, noise flagging and mention jump. Feature records are in `specs/features/entity-*.md`, `specs/features/remove-entity.md` and the related slugs.

## Implementation record (moved from CLAUDE.md)

The entries below were moved verbatim from the CLAUDE.md glossary when it was condensed.

**Entity** — A resource explicitly declared as such via its sidecar's `entityKind` field (an open, user-definable string like `"character"` or `"place"`, not an enum) plus an optional `aliases` array of alternate names. Declared in `EntitySidecarFieldsSchema` (`schemas.ts`). The sidebar's Remove Entity control (`RemoveEntityControl.tsx`) reverses this declaration by clearing both `entityKind` and `aliases`, with an optional opt-in to also delete the entity's authored relationship edges (see Entity relationship, below); the resource itself is never deleted. `EntitySection.tsx` also lets a writer clear just the Entity Kind field directly, independent of Remove Entity: that path clears only `entityKind` and leaves `aliases` in place but dormant (unmatched, since matching requires a declared entity). Both paths persist to disk via `updateSidecar`'s `clearKeys` parameter (`resource-crud-core.ts`'s `updateSidecarCore`) rather than an `undefined`-valued key in the update body, which a prior version relied on and which never survived the HTTP request.

**Mention** — A prose occurrence of an entity's name or one of its aliases, detected by `entity-detection.ts` (word-boundary, possessive, and simple-plural matching) and recorded with its character offset. A mention is _detected_, never authored — distinct from an explicit link (see Backlinks), which is authored. The two are stored separately and only ever merged for display, never conflated (`mentions-core.ts`).

**Mention index** — The persisted mention index at `meta/index/mentions.json` (`mention-index.ts`), keyed by `resourceId` and invertible to `entityId` → mentioning resources. Rebuilt incrementally on save by `indexer-queue.ts` and from scratch by the `reindex` CLI.

**Alias** — An alternate name for an entity, declared in its sidecar `aliases` array and matched by `entity-detection.ts` alongside the entity's `name`. Two entities claiming the same normalized alias are flagged ambiguous by `entity-alias-table.ts`; a short or noise-prone alias — and, as of entity-mention-noise-flagging, an equally noise-prone `name` — is flagged, non-blockingly, by `entity-noise-check.ts` (see the "Entity mention noise flagging" glossary entry below).

**Entity highlighting** — A view-layer-only decoration in the editor (`EntityHighlightDecorationExtension.ts` / `entityHighlightDecoration.ts`) that visually marks an entity's name/alias occurrences in the live, unsaved ProseMirror document as one of two states — plain match, or "needs attention" (ambiguous claim and/or a noise-flagged name/alias per `entity-noise-check.ts`). Distinct from a Mention: it never reads or writes the mention index or any persisted state, and it produces no data of its own — only CSS decorations recomputed on each document-changing transaction. Gated behind the `entityHighlighting` project feature flag. `entityHighlighting` and `entities` are independent optional booleans in the schema (`ProjectFeatureFlagsSchema`) with no schema-level dependency between them; the "highlighting needs entities on" relationship is enforced by convention at three separate points — `EntityFeatureToggles.tsx` (Project Settings' "Entities" tab; split out of `ProjectFeatureToggles.tsx`, which kept the Timeline/POV/Synopsis/Notes toggles in the Metadata tab) only renders the `entityHighlighting` toggle once `entities` is on, `TipTapEditor.tsx` re-checks both flags at the point of effect, and the spec states the dependency — not by the schema itself.

**Entity roster** — The project-wide, read-only sixth Work Area view (`EntityRosterView.tsx` / `EntityRosterRow.tsx`, "Entities" tab) listing every declared entity with its `entityKind`, aliases, mention count and the number of resources those mentions span (both shown, since a resource total hides how heavily an entity features and a mention total hides how widely it is spread), and the same ambiguous-alias / noise-flagged-term "needs attention" state entity highlighting surfaces. Rides the existing `entities` feature flag and adds none of its own. Distinct from a Mention or the mention index: it is a view over already-computed data (the cached `EntityAliasTable` plus a one-shot `getProjectMentionCounts` read, `mentions-core.ts`) and persists nothing itself. Activating a row selects that entity's resource and switches back to the edit view, where `EntitySection` remains the place to actually edit an entity's aliases.

**Entity-scoped compile** — Compiling every resource associated with a declared entity — the same merged Mention + Backlinks set `EntityMentionsSection.tsx` renders — into a single ordered document, ordered by resource-tree position (depth-first, siblings by `orderIndex`; `orderResourceIdsByTreePosition` in `compileSelection.ts`). Triggered from `EntityCompileSection.tsx` in the entity's own sidebar view via `CompilePreviewModal.tsx`'s entity mode, distinct from the whole-project/subtree compile flow in `AppShell.tsx`. `EntityCompileSection` renders outside the collapsible "Entity Mentions" section deliberately, so collapsing that section does not hide the compile action; it shares one `getEntityMentionedIn` fetch with `EntityMentionsSection.tsx` through `EntityMentionsContext.tsx`, which owns that fetch. Export-only: it reuses the existing compile client functions and writes nothing.

**Entity co-occurrence** — A derived, per-project observation that two declared entities were each detected as mentioned somewhere in the same resource (`getEntityCooccurrence`, `mentions-core.ts`). It is computed only from the mention index's `MentionRecord`s grouped by their shared `resourceId` — never from `backlinks.json` and never merged with `getEntityMentionedIn`'s output — so an explicit link with no corresponding detected mention does not count, and it is not conflated with the Mention+Backlinks set `EntityMentionsSection.tsx` otherwise renders. Same-resource is the whole unit of proximity; a mention's character offset within the resource is not consulted. It makes no claim of an authored relationship between the two entities, only that their names or aliases both surfaced in the same resource's prose — rendered as plain text ("Also appears with: …"), not the "Linked"/"Mentioned" badge markup a real relationship would use. Pairs are unordered and non-reflexive: if A co-occurs with B, B's entry lists A with the identical shared-resource count and ids, and an entity is never paired with itself. An entity sharing no resource with any other declared entity's mention is omitted entirely, not listed with a zero count.

**Entity relationship** — An authored, directed, typed edge between two declared entities, persisted at `meta/relationships.json` (`entity-relationships.ts`: `loadEntityRelationships`/`createEntityRelationship`/`removeEntityRelationship`/`removeEntityRelationshipsForEntity`), surfaced in an entity's own sidebar view by `EntityRelationshipsSection.tsx`. It is the fourth category alongside Mention, Backlinks, and Entity co-occurrence, and is distinct from each: unlike a Mention, it is authored, never detected or inferred; unlike a Backlink (also authored), it is entity-to-entity and typed and directed rather than resource-to-resource and untyped; unlike Entity co-occurrence, it is asserted rather than derived from shared prose proximity. `createEntityRelationship` is idempotent on the `(sourceEntityId, targetEntityId, relationshipType)` triple — a repeat call with the identical triple returns the existing edge rather than duplicating it — and rejects a same-entity edge (`SameEntityRelationshipError`) and a `relationshipType` outside the project's configured list (`InvalidRelationshipTypeError`). No inverse edge is created automatically; each direction must be authored separately. Relationship types come from a per-project extensible `relationshipTypes` list on the project config (`ProjectConfigSchema`), optionally seeded by a project type's own `relationshipTypes` array — the same shape as `statuses`. Deleting an entity's resource never touches its edges, mirroring how `backlinks.json` and `mentions.json` are left untouched on delete. The sidebar's Remove Entity control (`RemoveEntityControl.tsx`), which un-declares the entity without deleting the resource, also leaves edges untouched by default, and only deletes every edge naming the entity (via `removeEntityRelationshipsForEntity`) when the writer ticks an unchecked-by-default checkbox, shown only when at least one edge names the entity. When it does delete edges, it calls `notifyRelationshipsChanged()` on `EntityRelationshipsRefreshContext.tsx` — a narrow, write-signalling sibling to `EntityMentionsContext.tsx` that shares only a monotonic refresh token, never data — so `EntityRelationshipsSection.tsx` re-runs its own independent fetch without a remount. `EntityRelationshipsSection.tsx` renders a "Unknown entity" placeholder in place of a dangling edge's other-entity name rather than hiding, filtering, or crashing.

**Entity relationship graph** — The project-wide, read-only (for edge authoring — see below) seventh Work Area view (`EntityRelationshipGraphView.tsx`, "Graph" tab) that draws every declared entity as a node and layers edges from a per-project, customizable set of up to five connection types (Feature 68, superseding Feature 39/41's original fixed two-type/ephemeral-position behavior): `authored` (Entity relationship edges) and `cooccurrence` (derived Entity co-occurrence edges) are on by default, with `backlinks` (declared entities whose own resources share an explicit backlink, `getEntityBacklinkEdges`), `proximityMentions` (weighted by averaged mention-offset distance within a shared resource, `getProximityMentionEdges`), and `sharedMetadata` (declared entities sharing a tag or identical custom-metadata-field value, `getEntitySharedMetadataEdges`) available as opt-in additions — see the "Entity graph connection types" glossary entry below. Every active type renders visually distinguishable from every other active type and not by colour alone (`EntityGraphCanvas.tsx`, a hand-rolled SVG driven by a `d3-force` simulation for layout, with pan/zoom/selection); `proximityMentions`'s weighted edges use a visual encoding dimension (opacity/saturation) distinct from `cooccurrence`'s stroke-thickness scale, so the two weighted edge kinds never look alike. It ships a synchronized accessible list (`EntityGraphAccessibleList.tsx`) as its accessibility surface, generalizing the roster's semantic-list pattern — the same node and edge data rendered as a `<ul>` of activatable entity buttons plus a literal-text description of every edge, since thickness and arrowheads are not perceivable through a screen reader. Each edge's disclosure text is composed by a per-edge-kind `describe*Edge` function in the shared `edgeDescriptions.ts` module (not defined in `EntityGraphAccessibleList.tsx` itself) — one function per connection type, including the three Feature 68 added — so the accessible list's wording and the canvas's own hover/tap edge tooltip can never drift apart; edges themselves are not keyboard-focusable and show no tooltip on focus, so the accessible list remains the only keyboard/screen-reader route to that text. A per-project settings panel (`EntityGraphSettingsPanel.tsx`, reachable from the graph view near the reset-view button, not a Project Settings tab) toggles the five connection types and sets the focal-point hop radius, persisting each change immediately via `entity-graph-settings-core.ts`. It is read-only for edge authoring: edge authoring stays on Feature 38's `EntityRelationshipsSection.tsx` sidebar surface, not here. A writer can drag a node to reposition it: unlike Feature 41's original ephemeral-only drag, a dragged node's position now persists (`entity-graph-positions.ts`, `meta/entity-graph-positions.json`) across a reload or view switch, silently resetting to a freshly computed position only if the project's active connection-type list has changed since that position was saved (`isPositionInvalidated`); a position for a later-deleted/un-declared entity is dropped automatically, with no new confirmation step. Dragging itself is otherwise unchanged from Feature 41 — a static reposition with no simulation re-run, works via Pointer Events for mouse/pen/touch, a small-movement-threshold gesture still behaves as click-to-navigate, and there is no keyboard-operable equivalent for dragging. A writer can also select one node as a **focal point** — see the "Focal point" glossary entry below — a materially distinct gesture (shift-click/long-press) from the plain click-to-select/navigate above. Activating a node (canvas or list) selects that entity's resource and switches back to the edit view, mirroring the roster's `onEntityActivated` pattern. Rides the existing `entities` feature flag and adds none of its own.

**Entity graph connection types** (Feature 68) — The five connection-type keys the entity relationship graph knows how to draw (`entity-graph-connection-types.ts`'s `KNOWN_ENTITY_GRAPH_CONNECTION_TYPES`): `authored` and `cooccurrence` (Feature 39's original two, on by default), plus `backlinks`, `proximityMentions`, and `sharedMetadata` (Feature 68 additions, off by default). A project's active list is `config.entityGraphConnectionTypes` (`entity-graph-settings-core.ts`), writer-adjustable via `EntityGraphSettingsPanel.tsx`; an unrecognized key in a persisted list (e.g. written by a future version) is silently dropped via `filterToKnownConnectionTypes` rather than erroring the whole view. Each type is a distinct derivation with no shared code path: `backlinks` reads the existing backlink index (`backlinks.ts`), `proximityMentions` reads the mention index's character offsets (`mentions-core.ts`), and `sharedMetadata` reads tags and custom metadata fields (`entity-shared-metadata.ts`) — none of these three introduce a new persisted data source of their own, they only derive edges from data that already existed for other purposes.

**Focal point** (Feature 68) — A per-session, per-view role one declared entity's node can hold on the entity relationship graph, distinct from (and set by a materially different gesture than) the ordinary click-to-select/navigate: shift-click on desktop or long-press on touch sets the focal point, centering/panning the camera on that node and visually emphasizing its neighborhood within a configurable hop radius (`config.entityGraphFocalHopRadius`, default `1`, adjustable in the same settings panel as the connection-type toggles). Hop distance is standard BFS shortest-path over whichever connection types are currently active (`entityGraphHopDistance.ts`'s `computeHopDistances`), computed over the full graph with no special-casing for nodes beyond the radius. A node/edge outside the radius is **dimmed**, not hidden — SVG `opacity` only, so it stays exactly as selectable/activatable/draggable/tooltip-able as before, keeping the dim effect canvas-only and never suppressing the accessible list's own reachability. The accessible list provides a dedicated "Set as focal point" control per node plus a "Clear focal point" control in its own header, independent of the canvas gesture, giving keyboard/screen-reader users full parity. Unlike a dragged position, the focal point itself is not persisted to disk — it is UI state only, scoped to the current view session.

**Entity mention noise flagging** — The advisory (never-blocking, never-filtering) check that an entity's `name` or an `aliases` entry also reads as an ordinary English word, so detected matches of it (see Mention, above) may not really be about that entity. `entity-noise-check.ts`'s `checkNoiseFlag` replaced the prior `entity-alias-warnings.ts`/`getAliasWarning` — which checked only `aliases`, never `name`, against a hardcoded ~20-word list — applying one mechanism identically to both fields against the FR-7 union/exclusion formula: a bundled, static, ~2,000–3,000-word English frequency list (`bundled-noise-words.ts`, committed repo data, no npm dependency, mirroring `inverted-index.ts`'s `STOP_WORDS` precedent) UNION a per-project custom noise-word list (`config.customNoiseWords`, `ProjectConfigSchema`) UNION a cross-project global noise-word list, MINUS that project's own excluded-global-words list (`config.excludedGlobalNoiseWords`); a term under 3 characters is flagged independently of the union. The per-project custom list and global-word exclusions are managed from a new, dedicated Project Settings tab, "Noise Words" (`NoiseWordsSettingsTab.tsx`) — deliberately not folded into the "Writing Goals" or "Metadata" tabs. The cross-project global list is genuinely new per-runtime infrastructure, not an extension of an existing seam, with independent, unsynced storage in each: web/hosted reads/writes a tenant-root `.global-noise-words.json` via the existing `io.ts`/`storage-context.ts` seam (`global-noise-words.ts`, `app/api/global-noise-words/route.ts`); Electron desktop extends `userData/workspace.json` via a new `getwrite:global-noise-words-get`/`-set` IPC channel pair (`electron/src/main.ts`, `preload.ts`, `desktop-bridge.ts`), following the existing `workspace-dir` IPC precedent; native Android reads/writes a new device-level, unencrypted, app-private file with no project id in its path (`native-global-noise-words.ts`), outside the ADR-022 keyring's scope by construction. All three sit behind one `createTransport`-collapsed client API (`lib/api/global-noise-words.ts`, `store/transport/native-global-noise-words-backend.ts` + `.web-stub.ts`) with no sync/merge between the three stores — a word added on one device/runtime does not appear on another. The global list is managed from a new, standalone, account-agnostic "App Settings" surface (`components/AppSettings/AppSettingsDialog.tsx`, reachable from the settings (gear) menu, with or without an open project and with no login/account required — named to avoid implying hosted auth's account concept), distinct from the per-project Project Settings dialog. A writer can dismiss the observation for one specific term on one specific entity (`EntitySection.tsx`'s alias/name editor and `EntityRosterView.tsx`'s roster row both get an inline dismiss control); dismissal persists as the entity's own sidecar `dismissedNoiseTerms` array through the existing `updateSidecar`/`clearKeys` write path (no new transport), is scoped per-entity-per-term (the same term dismissed on one entity still surfaces on another), and does not carry over once the term's text changes. Observation copy (`entity-noise-copy.ts`'s `getNoiseObservation`) is deliberately non-imperative ("also reads as a common English word or name, so … may not be about this entity") and never styled in red/alert treatment, matching this codebase's reserved-red convention. This feature changes nothing about detection itself (`entity-detection.ts`), the mention index, or any mention list/count — every detected mention remains visible exactly as before; only the advisory layer is new or extended.

**Mention jump** (Feature 71) — Clicking a mention snippet in `EntityMentionsSection.tsx` navigates the TipTap editor to the exact character offset that snippet was built from, switching the selected resource first if the mention is in a different one, scrolling the match into view and marking it with a one-shot transient highlight (`MentionJumpHighlightExtension.ts`) that fades after a per-project configured duration (`config.mentionHighlightDurationSeconds`, 1-10 seconds, default 2 — see below). Distinct from a Mention itself: it reads the already-computed offset the mention index recorded (threaded through `getEntityMentionedIn`'s new `offsets` array, parallel to `snippets`/`ambiguousWith`) but adds no new detection and writes nothing to the index. The offset is resolved against the _live_ ProseMirror document via `offset-resolver.ts`'s `resolveOffsetToPosition`, which walks the document's text nodes accumulating plain-text character counts, since ProseMirror positions and plain-text character counts don't line up 1:1 once a document has more than one block/inline node. Before completing the jump, a staleness check re-matches the resolved position's surrounding text against the entity's own name/aliases (reusing `entity-detection.ts`'s word-boundary/possessive/plural primitives); when it fails — the underlying text changed since the mention index was last built — the click no-ops (no selection change, no scroll, no highlight) and shows a toast with a stable, deduplicated id rather than jumping to the wrong place. An explicit-link-only row (`isMentioned: false`, no detected mentions) keeps its prior click behavior unchanged — open the resource, nothing more; the jump mechanism only applies to an actual mention snippet. The highlight extension is new, one-shot decoration infrastructure deliberately separate from — and not a reuse or extension of — `EntityHighlightDecorationExtension.ts`'s persistent, continuously-recomputed entity-highlighting decoration (see the "Entity highlighting" glossary entry above); the two serve different purposes and share no code. The fade duration is the first writer-adjustable setting surfaced in a new "Entities" Project Settings tab (`MentionHighlightDurationField.tsx`), which this feature added solely to host that one field. A later change moved the `entities`/`entityHighlighting` toggles (`EntityFeatureToggles.tsx`) and Relationship Types (`RelationshipTypesSettings.tsx`) into the same tab; `entityKind` itself remains per-entity, edited from `EntitySection.tsx`, not here. Rides the existing `entities` feature flag; adds none of its own.
